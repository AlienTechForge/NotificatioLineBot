# 15 - 監控站台登入

> 讓監控自己去登入目標站台、拿到短效 token 再抓資料，取代「人工貼一次 header
> 就等它過期」的現況。

---

## 1. 問題

`Docs/plan/12-API監控易用性升級.md` §3.5 明確畫了一條界線：**不做自動登入**。
cookie jar（`monitor.session`）只接受使用者主動貼上的 cookie，不會自己去換新的。

那條界線在目標站台用長效 cookie 時是對的。但真實遇到的站台不是這樣：

| | 觀察到的事實 |
|---|---|
| 認證方式 | `Authorization: <token>`，**不是 cookie**，cookie jar 完全幫不上忙 |
| token 來源 | AWS Cognito user pool，前端存在 `localStorage["auth.idToken"]` |
| token 壽命 | Cognito idToken 預設 **1 小時** |
| 帳密直接登入 | `USER_PASSWORD_AUTH flow not enabled for this client` — **被停用** |
| 可用流程 | `USER_SRP_AUTH`（探測回 `PASSWORD_VERIFIER` challenge） |
| MFA | 關閉（`studentsMFAEnabled: false`） |
| app client secret | 無（不帶 `SECRET_HASH` 即可發起挑戰） |

結論：靜態 header 的監控**最多活一小時**。要無人值守就必須有登入能力，
而且必須是 SRP —— 帳密直傳那條路目標站台自己關掉了。

## 2. 範圍

**做**：一個可重複使用的「站台登入」設定，監控可以引用它；輪詢前自動取得
有效 token 並注入指定 header。第一個（也是目前唯一的）provider 是
`COGNITO_SRP`。

**不做**：

- 通用 OAuth2 / OIDC authorization code flow（沒有需求，且需要瀏覽器重導）
- MFA / SMS 驗證碼（目標站台關閉；有需要時是另一個 provider）
- SAML（同上）
- 把 token 開放給 `RequestTemplate` 當變數 —— 見 §6.3

## 3. 為什麼是獨立的一張表

`monitor_login` 獨立於 `api_monitor`，理由與 `monitor_secret` 當初獨立出來一樣，
但多一條更強的：

1. **一組帳號會服務多個監控**。同一個學生可能同時監控 CAS 狀態、文件要求、
   訊息。共用一份 token 快取代表登入一次、多個監控共用，而不是每個監控各自
   去登入 —— 對方會看到 N 倍的登入次數，也更容易觸發帳號鎖定。
2. **token 快取是狀態，不是設定**。塞進 `api_monitor.headers_ciphertext`
   會讓「使用者填的設定」與「系統寫回的狀態」混在同一個欄位，後台編輯時
   一存檔就把快取蓋掉。

## 4. 資料模型（V7）

```sql
CREATE TABLE monitor_login (
    id                    BIGSERIAL    PRIMARY KEY,
    name                  VARCHAR(100) NOT NULL UNIQUE,
    type                  VARCHAR(32)  NOT NULL,
    enabled               BOOLEAN      NOT NULL DEFAULT TRUE,

    -- provider 專屬的「非機密」設定：{"region":..., "userPoolId":..., "clientId":...}
    config                JSONB        NOT NULL,
    username              VARCHAR(320) NOT NULL,

    -- AES-256-GCM，AAD = "monitor_login:" + id + ":password"
    -- 可為 NULL 是被迫的，不是疏漏：AAD 含 id，而 id 是 BIGSERIAL，必須先 insert
    -- 拿到 id 才能加密。NOT NULL 會讓那第一次 insert 直接違反約束，兩段式儲存
    -- 根本走不完（這是實作時被整合測試抓出來的）。api_monitor.headers_ciphertext
    -- 當初可為 NULL 是同一個理由。收斂交給應用層：create 在同一交易內完成兩次寫入。
    password_ciphertext   BYTEA,
    password_iv           BYTEA,
    password_key_version  INT,

    -- 快取：refresh token（AAD 尾綴 ":refresh"）
    refresh_ciphertext    BYTEA,
    refresh_iv            BYTEA,
    refresh_key_version   INT,

    -- 快取：存取用 token（AAD 尾綴 ":token"）
    token_ciphertext      BYTEA,
    token_iv              BYTEA,
    token_key_version     INT,
    token_expires_at      TIMESTAMPTZ,

    -- 注入方式
    header_name           VARCHAR(64)  NOT NULL DEFAULT 'Authorization',
    header_value_template VARCHAR(200) NOT NULL DEFAULT '{token}',

    last_login_at         TIMESTAMPTZ,
    last_error            VARCHAR(200),
    consecutive_failures  INT          NOT NULL DEFAULT 0,
    created_at            TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at            TIMESTAMPTZ  NOT NULL DEFAULT now(),

    CONSTRAINT monitor_login_type_chk
        CHECK (type IN ('COGNITO_SRP')),
    CONSTRAINT monitor_login_header_chk
        CHECK (header_name ~ '^[A-Za-z0-9-]{1,64}$'),
    CONSTRAINT monitor_login_template_chk
        CHECK (header_value_template LIKE '%{token}%')
);

ALTER TABLE api_monitor
    ADD COLUMN login_id BIGINT REFERENCES monitor_login (id) ON DELETE SET NULL;
```

`header_value_template` 存在的理由：這個站台送的是裸 token（沒有 `Bearer `
前綴），但那是它自己的怪癖，不是通例。寫死任一種都會對另一種是錯的。

`ON DELETE SET NULL` 而非 `CASCADE`：刪掉登入設定不該連帶刪掉監控本身 ——
使用者想做的是「這個監控改成不需要登入」或「換一組帳號」，不是「把監控丟掉」。

## 5. Token 生命週期

`SiteLoginService.tokenFor(loginId)`：

```
1. 以 SELECT ... FOR UPDATE 鎖住該列（沿用 ApiMonitorRepository.lockDue 的慣例）
2. 快取仍有效（token_expires_at - 120s 安全邊際 > now）→ 直接回傳
3. 有 refresh token → REFRESH_TOKEN_AUTH 換新的 idToken
4. 沒有 refresh token，或第 3 步失敗 → 完整 SRP 登入
5. 寫回加密後的 token / refresh token / 到期時間
```

**為什麼要 `FOR UPDATE`**：多個監控可能同時到期。沒有鎖，N 個執行緒會同時發起
N 次登入 —— 浪費之外，更實際的風險是對方把這看成暴力嘗試。

**到期時間怎麼來**：解析 JWT payload 的 `exp` claim。**不驗章** —— 我們不是在
做授權判斷，只是決定快取何時失效；簽章由目標 API 自己驗。解析失敗時退化為
「現在 + 50 分鐘」，寧可早一點重新登入。

### 5.1 密碼錯誤必須停止重試

Cognito 對連續失敗會鎖帳號。若密碼被改掉或打錯，退避重試只會把使用者自己的
帳號鎖死。

規則：收到 `NotAuthorizedException`（帳密錯）或 `UserNotFoundException`
→ **立刻把 `monitor_login.enabled` 設為 false**、記錄 `last_error`，並透過既有的
`notifyOnFailure` 路徑通知使用者「登入失敗，已停用，請重設密碼」。

網路錯誤、5xx、限流則走一般退避重試 —— 那些不會鎖帳號。

## 6. 安全需求

### 6.1 機密不外流

密碼、refresh token、idToken：

- 加密後才落地（`SecretCipher`，與 `Client.secretCiphertext` 同一套金鑰管理）
- **絕不**出現在任何 DTO、log、`api_monitor_run`、LINE 訊息
- 後台只顯示「已設定」與到期時間，永遠不回傳值

**AAD 陷阱**：AAD 是 `monitor_login:{id}:password`，`id` 是 `BIGSERIAL`，
第一次 `save()` 之後才存在。呼叫端必須先 insert 拿到 id、用該 id 加密、再回寫 ——
與 `ApiMonitor.applyHeaders` 完全相同的順序要求。

### 6.2 沒有使用者可控的 host

Cognito 端點由我們自己組出來，不接受使用者填 URL：

```
https://cognito-idp.{region}.amazonaws.com/
```

`region` 以 `^[a-z]{2}-[a-z]+-[1-9]$` 驗證，`userPoolId` 以
`^[a-z]{2}-[a-z]+-[1-9]_[A-Za-z0-9]+$`，`clientId` 以 `^[a-z0-9]{1,64}$`。
使用者填不出 host，因此不需要（也不會繞過）`OutboundUrlGuard`。

### 6.3 token 不進 RequestTemplate

`RequestTemplate` 的類別註解已經說明：可用佔位符是封閉集合，**刻意不接受
`{{secret.*}}`**，因為那會讓機密散落到 URL／header 組裝邏輯裡。

token 遵守同一條界線：由 `ApiMonitorRunner` 在 `renderHeaders()` **之後**、
`ApiFetcher` **之前**直接寫入 header map，不經過模板系統。使用者只能選
「用哪個登入」與「注入哪個 header」，不能把 token 拼進 URL。

## 7. SRP 實作

不自己發明。移植 AWS 官方文件與 `aws-samples` 長期使用的 `AuthenticationHelper`
（Apache-2.0）—— 這段密碼學細節多，自己推導只會踩坑。

流程（RFC 5054 3072-bit group）：

```
InitiateAuth(USER_SRP_AUTH, {USERNAME, SRP_A})
  → ChallengeParameters {SALT, SRP_B, SECRET_BLOCK, USER_ID_FOR_SRP}

x    = H(salt ‖ H(poolName ‖ username ‖ ":" ‖ password))
u    = H(PAD(A) ‖ PAD(B))
s    = (B − k·g^x)^(a + u·x) mod N
key  = HKDF-SHA256(ikm = PAD(s), salt = PAD(u), info = "Caldera Derived Key")
sig  = HMAC-SHA256(key, poolName ‖ USER_ID_FOR_SRP ‖ SECRET_BLOCK ‖ timestamp)

RespondToAuthChallenge(PASSWORD_VERIFIER, {
    USERNAME: USER_ID_FOR_SRP,      ← 不是 email，見下
    PASSWORD_CLAIM_SECRET_BLOCK, PASSWORD_CLAIM_SIGNATURE, TIMESTAMP})
  → AuthenticationResult {IdToken, AccessToken, RefreshToken, ExpiresIn}
```

三個容易錯的地方，都要有對應的測試：

1. **`USERNAME` 要用 `USER_ID_FOR_SRP`**（Cognito 內部 id），不是登入用的 email。
   用 email 會得到看似隨機的 `NotAuthorizedException`。
2. **`poolName` 是去掉 region 前綴的部分**：`eu-west-2_FhQHPoX2z` → `FhQHPoX2z`。
3. **timestamp 格式固定**：`EEE MMM d HH:mm:ss z yyyy`，`Locale.US`、UTC，
   日期不補零。格式錯 → 簽章對不上 → 401。

**不新增依賴**：`BigInteger` + `javax.crypto` 就夠，兩個 API 呼叫是普通的
JSON POST，沿用專案既有的 HTTP client。不引入 AWS SDK（十幾 MB 換兩個
端點不划算）。

## 8. 驗證策略

CI 不可能有真實帳密，所以分兩層：

| 層 | 方法 | 實作 |
|---|---|---|
| SRP 數學 | 固定 `a`（不隨機）跑出中間值，與**獨立實作**（另寫的 Python 參考腳本）逐步比對。自己寫測試驗自己寫的實作，會把同一個錯誤編碼兩次 —— 必須是獨立來源 | `CognitoSrpTest`（20 項）；參考腳本與向量存在 `src/test/resources/srp/` |
| Cognito 互動 | `CognitoClient` 介面 + 測試用 fake，覆蓋：快取命中、refresh、refresh 過期退回完整登入、密碼錯停用、限流不停用 | `SiteLoginServiceTest`（13 項） |
| schema ↔ entity | 不另外寫測試：`ddl-auto: validate` 會在 context 啟動時擋下不一致，任何一支 IT 跑得起來就是那個保證 | 既有 IT |
| 密碼不外流 | 真的把 HTTP 回應撈出來逐字檢查 —— 單元測試看不到序列化後的 JSON | `AdminLoginIT`（11 項） |
| 端到端 | **人工**：使用者在後台按「測試登入」跑一次真的。不進 CI（CI 沒有、也不該有真實帳密） | 待使用者執行 |

> **這套驗證擋不住什麼**：兩個實作可能共享同一個對協定的誤解 —— 對拍能抓到 padding、
> 位元組順序、截斷長度這類實作錯誤（實務上最常出的那些），但抓不到「兩邊都照著同一個
> 錯誤的理解寫」。最終真相只有那顆「測試登入」按鈕。

## 9. 後台

- 新增「站台登入」管理區：新增／編輯／刪除／**測試登入**
  （測試只回報成功與到期時間，不回傳 token）
- 監控表單新增「站台登入」下拉：`（不需要）` 或選一組
- 密碼欄位：編輯時留空 = 不變更（沿用 header 欄位既有語意）

## 11. 已知限制

- 只支援 Cognito user pool 的 SRP。其他站台要另寫 provider（介面已預留 `type`）
- MFA 一旦被目標站台開啟，這條路立刻失效，需要人工介入
- refresh token 也會過期（Cognito 預設 30 天）；過期後自動退回完整 SRP 登入，
  使用者無感 —— 除非密碼同時也被改了，那時走 §5.1 的停用路徑
