# 13 — 監控計算欄位（簽章支援）

## 1. 已實作的用途

監控可在同一次請求內依序計算動態欄位，例如雜湊串接、HMAC 簽章與時間戳。
以下用示例說明相容某些目標協定所需的雙重雜湊，不記錄特定使用者的站台、裝置 ID 或密鑰：

```text
sign = MD5(MD5(SECRET + timestamp + DEVICE_ID).toUpperCase()).toUpperCase()
```

每段 hash／HMAC 可指定輸出編碼；較後欄位可使用較前欄位結果。這是目標協定相容功能，
不表示 MD5 適合新設計的安全簽章。演算法、驗證與語法以 ComputedFieldEvaluator／Validator 為準。

## 2. 資料模型（`V6__monitor_computed.sql`）

### 2.1 `monitor_secret`

```sql
CREATE TABLE monitor_secret (
    monitor_id   BIGINT       NOT NULL REFERENCES api_monitor (id) ON DELETE CASCADE,
    name         VARCHAR(32)  NOT NULL,
    ciphertext   BYTEA        NOT NULL,
    iv           BYTEA        NOT NULL,
    key_version  INT          NOT NULL,
    created_at   TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at   TIMESTAMPTZ  NOT NULL DEFAULT now(),
    PRIMARY KEY (monitor_id, name),
    CONSTRAINT monitor_secret_name_chk CHECK (name ~ '^[A-Za-z0-9_]{1,32}$')
);
```

`SecretCipher` 加密，AAD = `"monitor_secret:" + monitorId + ":" + name`。
**值絕不回傳到任何 DTO**，後台只顯示名稱與「已設定」。

### 2.2 `api_monitor.computed_fields`（JSONB，新增欄位）

```json
[
  {
    "name": "sign",
    "input": "{{secret.appsecret}}{{now.epochSeconds}}{{secret.deviceid}}",
    "steps": [
      { "algorithm": "MD5", "encoding": "HEX_UPPER" },
      { "algorithm": "MD5", "encoding": "HEX_UPPER" }
    ]
  }
]
```

`steps` 依序套用，**前一段的輸出字串就是後一段的輸入**。這是雙重雜湊的關鍵，
也是為什麼 `encoding` 掛在每一段而不是整體。

對應的 domain 型別：

- `ComputedField`：`record ComputedField(String name, String input, List<ComputedStep> steps)`。
  compact constructor 把 `steps` 轉成 `List.copyOf`（`null` → `List.of()`），所以拿到手的
  `steps` 一定不是 `null`、一定不可變。
- `ComputedStep`：`record ComputedStep(HashAlgorithm algorithm, HashEncoding encoding, String keySecret)`。
  `keySecret` **只有 HMAC 步驟能填**，非 HMAC 卻填了 → 存檔 400（見 §4.1）。

`HashAlgorithm`（**全部 6 個值，沒有第 7 個**）：

| 值 | JCA 實作 | 備註 |
|---|---|---|
| `MD5` | `MessageDigest("MD5")` | |
| `SHA1` | `MessageDigest("SHA-1")` | 列舉名沒有連字號，JCA 名稱有 |
| `SHA256` | `MessageDigest("SHA-256")` | |
| `SHA512` | `MessageDigest("SHA-512")` | |
| `HMAC_SHA1` | `Mac("HmacSHA1")` | `isHmac()` 為 `true`，必填 `keySecret` |
| `HMAC_SHA256` | `Mac("HmacSHA256")` | `isHmac()` 為 `true`，必填 `keySecret` |

`HashAlgorithm.isHmac()` 的定義就是「是不是後兩者」。取不到演算法時（`NoSuchAlgorithmException`）
轉成 `IllegalStateException` —— 這是環境問題，不是使用者輸入問題。

`HashEncoding`（**全部 3 個值**）：

| 值 | 實作 | 輸出樣子 |
|---|---|---|
| `HEX_UPPER` | `HexFormat.of().withUpperCase()` | `CE2201528168DAF1...` |
| `HEX_LOWER` | `HexFormat.of()` | `ce2201528168daf1...` |
| `BASE64` | `Base64.getEncoder()` | 標準字母表，**含 `=` padding**（不是 URL-safe、不是 no-padding） |

雜湊輸入一律先 `getBytes(UTF_8)`；HMAC 的金鑰是 `keySecret` 所指 secret 的**明文 UTF-8 位元組**。

## 3. ⚠️ 凍結時間戳（原為既有 bug，已修正）

原本的 `RequestTemplate` 在 `resolve()` 裡呼叫 `Instant.now(clock)`，
**每個佔位符各取一次時間**。

沒有簽章時這只是小瑕疵（URL 與 header 的 `{{now.epochSeconds}}` 可能差一秒）。
**有簽章時是硬故障**：sign 用 T1 算、`timestamp` header 送 T2 → 簽章不符 → 401。
幾百次輪詢才發生一次，看起來像對方 API 不穩，屬於最難查的那種。

**修法：`RequestTemplate.Session`。**

```java
public record Session(Instant instant, UUID uuid) { }

public Session newSession() {
    return new Session(Instant.now(clock), UUID.randomUUID());
}
```

呼叫端在處理一個請求的**最開始**呼叫一次 `newSession()`，之後 URL、每個 header、body、
全部計算欄位都共用同一個 `Session`：`render(String, Session, Map)` /
`renderHeaders(Map, Session, Map)`。`{{uuid}}` 同理 —— 同一次請求內所有 `{{uuid}}`
佔位符拿到的是同一個 UUID。`ApiMonitorRunner` 直接拿 `session.instant()` 當這一輪的時間基準。

> ⚠️ **無參數的 `render(String)` / `renderHeaders(Map)` 各自建立 ad-hoc session，
> 只可用於純語法驗證**（例如存檔時檢查佔位符合不合法）。拿它們去產生真的要送出去的請求，
> 就等於把上面那個 bug 原樣搬回來。型別上沒有任何阻擋，只有註解警告 —— 這是目前刻意接受的風險。

## 4. 求值順序

一次請求的整體流程：

1. 凍結 `Instant`（`RequestTemplate.newSession()`，見 §3）
2. 依序求值 `computed_fields`（`ComputedFieldEvaluator.evaluate(fields, secrets, session)`）
3. 套用到 URL、headers、body
4. **替換後的 URL 再過一次 `OutboundUrlGuard`**（沿用既有規則）

第 2 步內部，`evaluate()` 的細節：

- `secrets` 為 `null` → 當成 `Map.of()`；結果收在 `LinkedHashMap`，**保持定義順序**。
- **依 `fields` 陣列順序**逐一處理，每個欄位做三件事：
  1. **渲染 `input`**：用 `\{\{\s*([^{}]*?)\s*}}` 掃描並逐一決議。`input` 為 `null`／空字串 → `""`。
  2. **依序套用 `steps`**：`value = encode(digest(value, step), step.encoding())`——
     **前一段的輸出字串就是後一段的輸入**。
  3. 把 `name -> 最終值` 放進結果 map ——**此時之後的欄位才看得到它**。

`input` 裡佔位符的決議順序（`resolve()`）：

| 前綴 | 來源 | 查不到時 |
|---|---|---|
| `secret.NAME` | `secrets` map（該監控解密後的 secret） | 拋未知佔位符 |
| `computed.NAME` | **只查已求值完成的欄位**（陣列中更早的那些） | 拋未知佔位符 —— 前向引用、自我引用、名稱不存在都落在這裡 |
| 其餘 | `RequestTemplate.resolveNowOrUuid(key, session)`：`{{uuid}}`、`{{now.epochSeconds}}`、`{{now.epochMillis}}`、`{{now.iso8601}}`、`{{now.format:PATTERN}}`、位移語法 `now±N[smhd].<子指令>` | 拋未知佔位符 |

HMAC 步驟的金鑰另外決議（`hmacKey()`）：`keySecret` 為 `null`／空白 → `VALIDATION_ERROR`
（`HMAC step requires keySecret: ...`）；名稱查不到 secret → 當成未知佔位符 `secret.NAME`。

**不可前向引用**，也不可自我引用 —— 存檔時就要偵測並回 400（§4.1），不能等到輪詢才炸。

### 4.1 存檔時的驗證規則（`ComputedFieldValidator`）

`validate(fields, knownSecretNames)`。`fields` 為 `null`／空 → 直接通過。
以下每一條都是 400 `VALIDATION_ERROR`：

| 檢查 | 觸發條件 | 訊息 |
|---|---|---|
| 名稱格式 | 不符 `[A-Za-z0-9_]{1,32}`（`null` 也擋） | `computed field name must match [A-Za-z0-9_]{1,32}: X` |
| 名稱重複 | 陣列中先前已出現過 | `duplicate computed field name: X` |
| `steps` 為空 | `steps.isEmpty()` | `... must have at least one step` |
| 缺 algorithm | `step.algorithm() == null` | `... has a step with no algorithm` |
| 缺 encoding | `step.encoding() == null` | `... has a step with no encoding` |
| HMAC 缺 keySecret | `isHmac()` 且 `keySecret` 為 `null`／空白 | `... {ALGO} step requires keySecret` |
| HMAC keySecret 未知 | 不在 `knownSecretNames` | `... keySecret "X" is not a known secret name` |
| 非 HMAC 卻帶 keySecret | `keySecret != null` | `... keySecret is only valid for HMAC steps` |
| `input` 空 | `null` 或 `isEmpty()` | `... must have a non-empty input` |
| 未知 secret 引用 | `secret.NAME` 不在 `knownSecretNames` | `... references unknown secret: NAME` |
| 前向／自我引用 | `computed.NAME` 不在「更早已定義」的名稱集合 | `... references "NAME" which is not defined earlier in the list (forward or self reference)` |
| 未知佔位符 | `resolveNowOrUuid` 回 empty | `... has unknown placeholder: {{key}}` |

`now.format:PATTERN` 的合法性直接重用 `RequestTemplate.resolveNowOrUuid`（用一個丟棄結果的
假 `Session`），畸形 pattern 由那邊拋出。

**驗證器不會「真的算一次」** —— 存檔當下未必所有 secret 都有值（例如編輯時留空 = 不變更）。
要看實際算出來的值請用「試算」（§7）。

`knownSecretNames` 由呼叫端 `AdminService` 組出來：

- **建立監控**：只有這次請求裡新增的非空白 secret（當下沒有「既有值」）
- **編輯監控**：DB 既有的名稱 ∪ 這次請求裡非空白的新增／覆寫項目

> ⚠️ **已知不一致**：`validatePlaceholders()` 用的是 `input.isEmpty()` 而**不是**
> `input.isBlank()`（`ComputedFieldValidator.java:121`）。所以 `input` 只填空白字元
> （例如 `"   "`）**會通過驗證**，錯誤訊息卻寫著 `must have a non-empty input`。
> 這種欄位求值後就是把那串空白餵進雜湊，能算出一個固定值但幾乎肯定不是使用者要的。
> 現況如此，尚未修。

## 5. 安全約束

- secret 值**絕不**進 DTO、log、`api_monitor_run`、LINE 訊息
- 計算結果（如 sign）是雜湊，可以顯示在「試算」面板 —— 使用者需要拿它跟瀏覽器
  的真實值比對。**但試算面板絕不顯示 secret 值**。`MonitorTestOutcome.Success.computedValues`
  只放 `ComputedFieldEvaluator` 求出的最終結果
- `input` 模板裡未知的佔位符 → 存檔時 400（沿用 §12 請求模板的政策）
- 格式化 pattern 的字元白名單沿用既有規則

### 5.1 `{{secret.*}}` 只能寫在計算欄位的 `input`

這是整份設計的核心邊界，講白一點：

| 位置 | 認不認 `{{secret.*}}` |
|---|---|
| 計算欄位的 `input` | ✅ **唯一認得的地方** |
| 監控的 URL | ❌ 未知佔位符 → 存檔 400 |
| 監控的 header 值 | ❌ 未知佔位符 → 存檔 400 |
| 監控的 request body | ❌ 未知佔位符 → 存檔 400 |
| LINE 訊息模板 | ❌ 未知佔位符 → 渲染成 `—`（見 §9） |

`RequestTemplate` 是**刻意**不接受 `{{secret.*}}` 的：它的佔位符是一個封閉集合，
不提供任何使用者自訂變數。secret 只能**間接**經過計算欄位進入請求 —— 也就是說，
送出去的一定是雜湊後的結果，明文密鑰沒有任何一條路徑可以直接出現在 URL、header 或 body 裡。

想把某個 secret「原樣」放進 header？辦不到，這是設計，不是缺漏。

### 5.2 求值器本身不 log

`ComputedFieldEvaluator` **完全不依賴 `Logger`，一行 log 都沒有**。
例外訊息只回顯佔位符的**名稱**（超過 100 字截斷後補 `...`），不含任何值。
這樣即使 `input` 拼錯而拋錯，密鑰也不會因為錯誤訊息被寫進 log。

## 6. 使用者設定長什麼樣（實例）

### 6.1 雙重 MD5（示例協定）

```
密鑰   appsecret = YWHZ@&mxZge1A@
密鑰   deviceid  = 2b34aabc-6d14-490e-b76a-254097095055

計算欄位 sign
  輸入    {{secret.appsecret}}{{now.epochSeconds}}{{secret.deviceid}}
  第 1 段  MD5 → 十六進位大寫
  第 2 段  MD5 → 十六進位大寫

header  timestamp = {{now.epochSeconds}}
header  sign      = {{computed.sign}}
```

換一個站就換一組設定，不動任何程式碼。

### 6.2 HMAC-SHA256 簽章（完整走一遍）

假設要監控一支這樣規格的 API：

> `GET https://api.example.com/v1/orders?ts=<秒級時間戳>&nonce=<UUID>`
> header `X-Signature` = `Base64( HMAC-SHA256( key = API_SECRET,
> message = "GET\n/v1/orders\n" + ts + "\n" + nonce ) )`
> header `X-Key-Id` = 帳號的 access key id

**第一步：存兩個密鑰。**

```
密鑰   api_secret  = <對方後台給的 secret，只在這裡輸入一次>
密鑰   access_key  = AKIDEXAMPLE0001
```

`api_secret` 要當 HMAC 的金鑰，`access_key` 只是個要送出去的識別字串 ——
但它同樣是機敏值，所以一樣存成 secret（存進去之後就再也讀不回明文）。

**第二步：定義計算欄位。**（下面的 `⏎` 代表 `input` 這個字串裡一個真正的換行字元。
求值器只認 `{{...}}`，對反斜線不做任何處理；寫進 `computed_fields` JSON 時
換行照 JSON 規則寫成 `\n`。）

```
計算欄位 signature
  輸入    GET⏎/v1/orders⏎{{now.epochSeconds}}⏎{{uuid}}
  第 1 段  HMAC_SHA256（keySecret = api_secret）→ BASE64

計算欄位 keyid
  輸入    {{secret.access_key}}
  ↑ 不合法！見下方說明
```

⚠️ `keyid` 這種寫法**不成立**：每個計算欄位至少要有一段 `steps`（§4.1），
沒有「原樣輸出」這個選項。**計算欄位的出口一定是雜湊過的值** —— 這正是 §5.1 那條邊界的必然結果。
`X-Key-Id` 這種必須以明文送出的識別字串，只能直接寫死在 header 值裡，不要放進 `monitor_secret`：

```
header  X-Key-Id     = AKIDEXAMPLE0001
header  X-Signature  = {{computed.signature}}
```

**第三步：URL 帶上同一組 ts / nonce。**

```
URL     https://api.example.com/v1/orders?ts={{now.epochSeconds}}&nonce={{uuid}}
```

這裡是 §3 在發揮作用：URL 的 `{{now.epochSeconds}}`、`{{uuid}}` 與計算欄位 `input` 裡的
那兩個，來自**同一個 `Session`**，所以簽出來的訊息跟實際送出的 query string 保證一致。
沒有凍結機制的話，這支 API 會偶發 401，而且重現不了。

**第四步：按「試算」，把面板顯示的 `signature` 跟瀏覽器 DevTools 裡真實請求的
`X-Signature` 比對。**對不上就調整輸入字串的拼接順序或分隔符號 —— 面板永遠不會顯示
`api_secret` 的值，所以這個比對過程是安全的。

> 如果對方要的是十六進位小寫而不是 Base64，只要把那一段的 `encoding` 從 `BASE64` 改成
> `HEX_LOWER`，其他都不用動。

## 7. 後台

- 密鑰：可新增／覆寫／刪除。已存在的只顯示名稱，不顯示值
  - **編輯**監控時：留空 = 不變更（`AdminService.nonBlankEntries` 把空白值整筆濾掉）
  - **建立**監控時：沒有「既有值」可以不變更，所以同一條規則的實際效果是「留空 = 不建立」，
    不會生出一個空字串的 secret
  - 刪除走 `MonitorSecretService.delete(monitorId, name)`
- 計算欄位：可重複的列編輯器，`steps` 可增減、可排序
- **「試算」顯示每個計算欄位的最終值**（`MonitorTestOutcome.Success.computedValues`），
  讓使用者直接跟瀏覽器實際送出的值比對。對不上就調整輸入順序或演算法，不必猜

## 8. 測試要求

- **本文件 §1 的真實案例當回歸測試**：給定 `SECRET`、`DEVICE_ID` 與
  `timestamp=1787565614`，必須算出 `CE2201528168DAF1286F95CB1EAB39CD`；
  `timestamp=1787567699` → `DAD9F5DF984821CA0DDDA73F578FD989`
- 凍結時間戳：同一次請求中 URL 與 header 的 `{{now.epochSeconds}}` **必須相同**
  （用會跨越秒邊界的 `Clock` 測，不是固定 `Clock`）
- 前向引用／自我引用 → 存檔 400
- secret 值不出現在任何回應、log、run 紀錄
- 每種演算法 × 每種編碼各一組已知向量

## 9. ⚠️ 請求模板與訊息模板的佔位符不一樣，而且行為相反

同樣是 `{{...}}`，`RequestTemplate`（URL／header／body／計算欄位 `input`）與
`MessageTemplate`（LINE 通知內容）是**兩套獨立的佔位符集合**，踩錯的方式還特別隱蔽：

| | `RequestTemplate` | `MessageTemplate` |
|---|---|---|
| 用在哪 | 監控的 URL、headers、body、計算欄位 `input` | LINE 通知訊息 |
| 時間 | `{{now.epochSeconds}}`、`{{now.epochMillis}}`、`{{now.iso8601}}`、`{{now.format:PATTERN}}`、`{{now±N[smhd].<子指令>}}` | **只有裸的 `{{now}}`**（`MM/dd HH:mm`，`Asia/Taipei`） |
| 其他 | `{{uuid}}`、`{{computed.NAME}}` | `{{monitor.name}}`、`{{value.NAME}}`、`{{old.NAME}}`、`{{item.NAME}}` |
| `{{secret.*}}` | ❌（刻意不支援，見 §5.1） | ❌ |
| **打錯字會怎樣** | **存檔時直接 400**，錯誤訊息列出允許清單 | **靜靜渲染成 `—`**（U+2014）並記一筆 WARN log |

最容易踩的一種：在**訊息模板**裡寫 `{{now.epochSeconds}}`。那是 `RequestTemplate` 的語法，
在訊息模板裡是未知佔位符，結果不是報錯而是一條「（—）」的 LINE 通知。
訊息模板要時間就只能寫 `{{now}}`。

反方向也一樣要注意：請求模板**不會**放過任何拼錯的佔位符 —— 存檔就擋下來，
不會讓一個打錯字的監控每輪安靜地打去錯的地方。這是刻意的，兩邊的取捨不同：
訊息渲染失敗不該讓通知整條發不出去，請求打錯則必須當場攔住。

另外，`MessageTemplate` 沒有「輸出字面 `{{`」的跳脫語法 —— 任何符合正則的片段都會被替換。

## 10. 與站台登入及敏感資料的關係

`monitor_secret` 與 `monitor_login` 不同：前者供計算欄位，後者持有 Cognito 密碼與 token。
token 不透過 computed／訊息模板傳遞，詳見 [15](15-監控站台登入設計.md)。

密鑰輸入只能在計算欄位中引用，**但計算結果不會自動變成安全資料**：若欄位使用不做雜湊的
操作，結果可能仍等同秘密；把結果放 URL／body 仍可能明文落入外部存取日誌或測試回應。
