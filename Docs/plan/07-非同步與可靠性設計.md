# 07 — 非同步與可靠性設計

← [文件索引](README.md) ｜ 前一份 [06-LINE整合設計](06-LINE整合設計.md)

要回答的問題：**大量發送怎麼不塞爆呼叫端、不掉單、不重複、LINE 掛掉時不把整個佇列燒成灰。**

---

## 1. 為什麼要非同步

`target: ALL` 對 1200 人發送 = 3 次 LINE API 呼叫，每次數百毫秒，加上重試可能到數十秒。

同步做的話：呼叫端的 HTTP 請求要等這麼久，多半會先逾時；而逾時後呼叫端會重試，於是同一則通知被發送兩次。

所以 API 的語意是「**已受理**」（`202`），不是「已送達」。實際結果用 `GET /notifications/{id}` 查。

---

## 2. 完整流程

```text
┌─ 同步段（HTTP 執行緒）────────────────────────────────┐
│                                                        │
│  1. HmacAuthFilter        驗簽                          │
│  2. RateLimitFilter       per-client 速率               │
│  3. Controller            DTO 驗證                      │
│  4. TargetResolver        scope 檢查 → 收件人清單        │
│  5. QuotaGuard            client 每日配額 → LINE 月額度  │
│  6. @Transactional {                                    │
│       寫 notification (QUEUED)                          │
│       切批 500 → 寫 N 筆 notification_delivery (PENDING) │
│     }                                                   │
│  7. 回 202 + notificationId + batchCount                │
│                                                        │
└────────────────────┬───────────────────────────────────┘
                     │ 交易提交後（TransactionSynchronization）
                     ▼
┌─ 非同步段（@Async 執行緒池）──────────────────────────┐
│                                                        │
│  NotificationDispatcher                                 │
│    notification.status = SENDING                        │
│    for each batch:                                      │
│        RateLimiter (100 req/s)                          │
│        CircuitBreaker                                   │
│        → MessagingApiClient.multicast(retryKey, req)    │
│        → 更新 delivery: SENT + line_request_id           │
│           或 PENDING + next_attempt_at（暫時性錯誤）      │
│           或 FAILED（終局錯誤）                           │
│    回寫 notification 計數與最終狀態                        │
│                                                        │
└────────────────────┬───────────────────────────────────┘
                     │ 失敗或未處理的批次留在 PENDING
                     ▼
┌─ 補償段（@Scheduled 每 30 秒）─────────────────────────┐
│                                                        │
│  DeliveryRedriver                                       │
│    SELECT ... WHERE status='PENDING'                    │
│               AND next_attempt_at <= now()              │
│         ORDER BY priority, next_attempt_at              │
│         LIMIT 20 FOR UPDATE SKIP LOCKED                 │
│    → 交給同一個 BatchSender 處理                          │
│                                                        │
└────────────────────────────────────────────────────────┘
```

### 2.1 為什麼派送要在**交易提交後**才啟動

若在 `@Transactional` 方法內直接呼叫 `@Async` 派送，會產生競態：非同步執行緒可能在交易提交前就去查 `notification_delivery`，結果查不到任何資料。

用 `TransactionSynchronizationManager.registerSynchronization(...)` 的 `afterCommit` 回呼觸發，或更簡單地在 Controller 層（交易外）呼叫派送器。

**這是最容易寫錯且最難重現的 bug 之一**——在本機因為交易提交很快，多半不會出現；上線後在負載下才偶發。

## 3. DB Outbox 模式

`notification_delivery` **同時是投遞明細與工作佇列**。這是本設計的核心，理由見 [ADR-0007](adr/0007-非同步採-DB-outbox-而非訊息中介.md)。

### 3.1 取件查詢

```sql
SELECT *
  FROM notification_delivery
 WHERE status = 'PENDING'
   AND next_attempt_at <= now()
 ORDER BY priority, next_attempt_at
 LIMIT 20
   FOR UPDATE SKIP LOCKED;
```

| 子句 | 為什麼 |
|---|---|
| `FOR UPDATE` | 鎖住取到的列，避免其他工作者重複處理 |
| `SKIP LOCKED` | 跳過已被鎖的列而非等待。多個工作者可完全並行取件，互不阻塞 |
| `ORDER BY priority, next_attempt_at` | 高優先先送；同優先級依排隊順序 |
| `LIMIT 20` | 一次取一小批。取太多會讓單一工作者長時間持鎖 |

`idx_delivery_pickup` 這個 partial 複合索引精確覆蓋此查詢（見 [04 §6](04-資料模型.md#6-notification_delivery)）。

### 3.2 這個模式解決了什麼

| 問題 | 純記憶體佇列 | DB outbox |
|---|---|---|
| 應用重啟 | 佇列中的工作**永久消失** | 仍在 DB，重啟後 redriver 撿回 |
| 派送到一半當機 | 該批狀態不明 | 仍是 `PENDING`，會被重新取件 |
| 要查「現在積了多少」 | 需要額外暴露內部狀態 | 一句 SQL |
| 未來要多實例 | 需要整個重寫 | `SKIP LOCKED` 已經是多實例安全的 |

代價是每批多幾次 DB 往返。以本專案的量級（每批對應一次數百毫秒的 LINE API 呼叫）完全可忽略。

## 4. 重試

### 4.1 退避策略

| 次數 | 延遲 |
|---|---|
| 1 | 1 秒 |
| 2 | 2 秒 |
| 3 | 4 秒 |
| 4 | 8 秒 |
| 5 | 16 秒 |
| > 5 | 放棄，標 `FAILED` |

實作方式是寫 `next_attempt_at = now() + delay` 與 `attempt_count += 1`，然後**交還給 redriver**——不在原執行緒 sleep。sleep 會佔住執行緒，而執行緒池是有限資源。

實際延遲加上 ±20% 隨機抖動（jitter），避免大量批次在同一時刻同時重試造成尖峰。

### 4.2 哪些錯誤才重試

見 [06 §5.4](06-LINE整合設計.md#54-錯誤分類)。摘要：

| 類別 | 重試 | 計入斷路器 |
|---|---|---|
| `5xx`、連線逾時、`429` 速率限制 | ✔ | ✔ |
| `429` 月額度耗盡 | ✘ | ✘ |
| `401` / `403` 憑證問題 | ✘ | ✘（但要發告警） |
| `400` 請求格式錯誤 | ✘ | ✘ |

**把不可恢復的錯誤拿去重試，只是把同一個失敗重複 5 次然後得到同樣的結果**，還浪費了 API 配額。

## 5. 冪等

三層冪等，各自解決不同層級的重複：

| 層 | 機制 | 防止的重複 |
|---|---|---|
| **API 層** | `Idempotency-Key` + `UNIQUE (client_id, idempotency_key)` | 呼叫端因逾時而重送整個請求 |
| **LINE 層** | `X-Line-Retry-Key`，每批固定一把，重試時不變 | 我們重試時 LINE 端重複投遞 |
| **Webhook 層** | `webhook_event` 表主鍵 | LINE 重送 webhook 事件 |

### API 層的細節

```text
帶 Idempotency-Key 的請求進來
  → 嘗試 INSERT notification（含 idempotency_key）
  → 唯一鍵衝突？
       否 → 正常流程
       是 → 查出既有的 notification
            比對 payload_hash 是否相同
              相同 → 回傳既有結果（202，與第一次相同）
              不同 → 409 IDEMPOTENCY_CONFLICT
```

比對 `payload_hash` 而非整個 payload：payload 可能已被保留政策清空（見 [04 §11](04-資料模型.md#11-資料保留與清理缺口-g7)），但 hash 永遠保留。

## 6. Circuit Breaker（缺口 G4）

### 6.1 沒有它會怎樣

LINE API 掛掉或憑證失效時，初版設計的行為是：每批重試 5 次（1+2+4+8+16 = 31 秒）然後標 `FAILED`。

結果是**佇列裡所有東西在幾分鐘內全部燒成 `FAILED`**，同時對已經掛掉的 LINE 打出大量無用請求。服務恢復後，這些通知也不會自動補送——它們已經是終局失敗了。

### 6.2 設定

Resilience4j `CircuitBreaker` 包住所有 LINE API 呼叫：

| 參數 | 值 | 說明 |
|---|---|---|
| `slidingWindowSize` | 20 | 統計最近 20 次呼叫 |
| `failureRateThreshold` | 50% | 失敗率超過即開路 |
| `waitDurationInOpenState` | 60 秒 | 開路後等待多久進入半開 |
| `permittedNumberOfCallsInHalfOpenState` | 3 | 半開時試探 3 次 |
| `minimumNumberOfCalls` | 10 | 少於 10 次不做判定（避免冷啟動誤判） |

### 6.3 開路時的行為 —— 關鍵差異

> **斷路期間的批次是「延後」，不是「失敗」。**

```text
CircuitBreaker OPEN
  → 派送器停止取件
  → 已取出但未送的批次：status 維持 PENDING
                        next_attempt_at = now() + waitDuration
                        attempt_count 不遞增   ← 重點
  → 60 秒後 HALF_OPEN，試探性放行
  → 成功 → CLOSED，redriver 自動把積壓的批次全部送出
```

**`attempt_count` 不遞增**是關鍵：否則一次 LINE 端的長時間故障，會讓所有批次在斷路期間耗盡重試次數，變成永久失敗。斷路器擋下的呼叫根本沒送出去，不該算成一次嘗試。

### 6.4 告警

`CircuitBreaker` 狀態變化要發出告警（Phase 2 的自我監控），但**告警本身不能走同一條斷路的路徑**——否則 LINE 掛掉時告警也發不出去。詳見 [09-CICD與維運](09-CICD與維運.md) 的自我監控段落。

## 7. 速率控制

兩個方向，別搞混：

| 方向 | 機制 | 上限 | 文件 |
|---|---|---|---|
| 呼叫端 → 我們 | `RateLimitFilter`，per-client token bucket | 60 req/min | [03 §4](03-權限與認證設計.md#4-呼叫端速率限制與配額缺口-g2) |
| 我們 → LINE | Resilience4j `RateLimiter`，全域 | 100 req/s | 本節 |

LINE 的 multicast 上限是 200 req/s（[06 §1.1](06-LINE整合設計.md#11-發送端點)），我們設 100 是刻意留一半餘裕——因為：

- LINE 用 token bucket，突發流量的實際判定比平均值嚴格
- 同一 channel 的其他呼叫（Profile API、額度查詢、reply）共用整體配額
- 撞到 `429` 的代價（重試、延遲、可能的告警）遠大於慢一點的代價

以本專案量級，100 req/s 意味著 1200 人的全體發送（3 批）在毫秒級就能送完，速率限制根本不是瓶頸。留餘裕是零成本的保險。

## 8. 執行緒池

```yaml
app.async:
  core-pool-size: 4
  max-pool-size: 8
  queue-capacity: 200
  thread-name-prefix: notify-dispatch-
  rejection-policy: CALLER_RUNS
```

| 決策 | 理由 |
|---|---|
| 池不大 | 工作是 I/O bound（等 LINE 回應），不是 CPU bound。真正的併發控制在 `RateLimiter` |
| `queue-capacity` 有限 | 無界佇列會在異常時吃光記憶體。滿了就讓 `CALLER_RUNS` 產生自然的背壓 |
| `CALLER_RUNS` | 池滿時由呼叫者執行緒處理，變相減緩上游。**比丟棄工作好得多**——反正 DB outbox 已經保證不掉單，最壞情況只是變慢 |

### 8.1 MDC 傳遞（缺口 G3）

`@Async` 換執行緒後，**MDC（含 correlation id）不會自動帶過去**。必須設定 `TaskDecorator`：

```java
executor.setTaskDecorator(runnable -> {
    Map<String, String> context = MDC.getCopyOfContextMap();
    return () -> {
        if (context != null) MDC.setContextMap(context);
        try { runnable.run(); }
        finally { MDC.clear(); }
    };
});
```

漏掉這段的後果：非同步段的所有 log 都沒有 `requestId`，出事時無法把同步段與非同步段的日誌串起來。**這是最容易漏、也最容易在事故當下讓人抓狂的一個細節。**

`finally { MDC.clear(); }` 同樣重要——執行緒是重複使用的，不清會讓下一個工作繼承錯誤的 context。

## 9. 優先級（缺口 G10）

單一 FIFO 佇列有 head-of-line blocking：對 1200 人的全體公告切成 3 批排在前面，後面一則「伺服器當機」的緊急告警就得等。

`notification_delivery.priority`（0 高 … 9 低），取件時 `ORDER BY priority, next_attempt_at`。

### Phase 1 的自動指派

| target | priority |
|---|---|
| `OWNER` | 0 |
| `SELF` | 5 |
| `USER` | 5 |
| `ALL` | 9 |

理由：`OWNER` 幾乎都是系統告警（最需要即時）；`ALL` 幾乎都是公告（可以等）。

Phase 2 再開放 API 讓呼叫端指定（並限制一般 client 能設的最高優先級，避免大家都標 0）。

**欄位現在就加**：事後補要改索引定義與所有取件查詢，成本高得多；現在加幾乎是零成本。

## 10. 狀態一致性

### 10.1 `notification` 最終狀態

所有批次都到達終態後回寫：

```text
全部 SENT                   → SUCCEEDED
部分 SENT、部分 FAILED       → PARTIAL
全部 FAILED                 → FAILED
```

`success_count` / `failure_count` 以**收件人數**加總（不是批次數）——呼叫端關心的是幾個人收到，不是幾批送出。

### 10.2 卡在 `SENDING` 的偵測

若某批因為程序被 kill 而沒有寫回狀態，`notification` 會永遠停在 `SENDING`。

偵測：`SENDING` 且 `started_at < now() - 30 minutes` 的 notification 是異常訊號，納入監控指標與告警。

修復：redriver 會重新取件（因為對應的 delivery 仍是 `PENDING`），最終狀態會被正確回寫。**不需要人工介入**——這是 outbox 模式的自癒特性。

### 10.3 明細清理後的統計保留

`notification_delivery` 保留 90 天後刪除，但 `notification` 上的三個計數欄位是去正規化保存的，**刪除明細不影響統計查詢**。這是 [04 §5](04-資料模型.md#5-notification) 刻意冗餘的原因。

## 11. 已知限制與擴充路徑

| 限制 | 現況 | 何時要處理 | 怎麼處理 |
|---|---|---|---|
| 單實例假設 | `DeliveryRedriver` 已多實例安全，但其他 `@Scheduled` 未防重複 | 加第二個實例前 | 導入 ShedLock（PostgreSQL LockProvider） |
| 速率限制 per-instance | `RateLimitFilter` 用行程內 cache | 加第二個實例前 | 改用共享儲存，或按實例數等比下調上限 |
| 輪詢間隔 30 秒 | 首次派送走 `@Async`（即時），redriver 只是補償 | 若補償路徑的延遲成為問題 | 縮短間隔，或改用 PostgreSQL `LISTEN/NOTIFY` |
| 無死信處理 | `FAILED` 的批次留在表中，無自動重新派送 | 需要人工重送功能時 | Phase 2 Admin 提供「重送這筆」按鈕 |
| 無跨通知的合併 | 每筆通知獨立發送 | 若同一批人短時間收到大量通知 | [缺口 G15](02-架構設計.md#g15--通知抑制去重--phase-2-候選) 的抑制機制 |
