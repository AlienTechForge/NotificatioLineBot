# 07 — 非同步與可靠性設計

> 校訂日期：2026-09-21。依 2026-09-21 main 的程式碼核對；歷史方案與未實作項目另行標示。

← [文件索引](README.md) ｜ 前一份 [06-LINE整合設計](06-LINE整合設計.md)

要回答的問題：**大量發送怎麼不塞爆呼叫端、不掉單、不重複、LINE 掛掉時不把整個佇列燒成灰。**

系統裡有**兩條 outbox 管線**，用的是**同一套取件機制**：

| 管線 | 佇列表 | 取件方法 | 排序鍵 | 排程器 | 詳細設計 |
|---|---|---|---|---|---|
| 通知派送 | `notification_delivery` | `NotificationDeliveryRepository.lockPending` | `priority, next_attempt_at` | `DeliveryScheduler` + `DispatchKicker` | 本文件 |
| API 監控輪詢 | `api_monitor` | `ApiMonitorRepository.lockDue` | `next_run_at` | `ApiMonitorScheduler` | [11 §7](11-API監控輪詢設計.md#7-執行流程與交易邊界) |

兩者的取件都是 `@Lock(PESSIMISTIC_WRITE)` + `jakarta.persistence.lock.timeout = -2`（Hibernate 的 `SKIP_LOCKED`），Postgres 產生 `FOR UPDATE SKIP LOCKED`，並在**同一個交易內**寫租約。差別只在排序鍵與各自的退避規則——**不是兩套不同機制**。本文件 §3 的取件模型同時適用於兩者。

---

## 1. 為什麼要非同步

`target: ALL` 對 1200 人發送 = 3 次 LINE API 呼叫，每次數百毫秒，加上重試可能到數十秒。

同步做的話：呼叫端的 HTTP 請求要等這麼久，多半會先逾時；而逾時後呼叫端會重試，於是同一則通知被發送兩次。

所以 API 的語意是「**已受理**」（`202`），不是「已送達」。實際結果用 `GET /notifications/{id}` 查。

## 2. 完整流程

```text
┌─ 受理段（HTTP 執行緒，單一交易）──────────────────────────┐
│                                                            │
│  1. HmacAuthFilter       驗簽                               │
│  2. RateLimitFilter      per-client 速率                    │
│  3. NotificationController.create   DTO 驗證                │
│  4. NotificationService.submit  @Transactional {            │
│       a. Idempotency-Key 已存在？                            │
│            hash 相同 → replay()，回原結果                     │
│            hash 不同 → 409 IDEMPOTENCY_CONFLICT              │
│       b. MessageAssembler.assemble + UriHostValidator        │
│       c. TargetResolver.effectiveType / resolve（scope 檢查）│
│       d. BatchSplitter.split   去重 → 每 500 人一批           │
│       e. clients.lockById（悲觀鎖）+ enforceDailyQuota        │
│            （滾動 24h，以收件人數計）                          │
│       f. notifications.insertIfAbsent                        │
│            INSERT … ON CONFLICT DO NOTHING，status=QUEUED    │
│       g. persistBatches → notification_delivery (PENDING)    │

                     ▼
┌─ 派送段（DeliveryDispatcher.runOnce，三段式）──────────────┐
│                                                            │
│  ① DeliveryStore.claim(batchLimit)   @Transactional（短）   │
│       deliveries.lockPending                                │
│         PENDING AND next_attempt_at <= now                  │
│         ORDER BY priority, next_attempt_at                  │
│         FOR UPDATE SKIP LOCKED                              │
│       payload 不在 → markFailed(PAYLOAD_GONE)、跳過          │
│       payload 在   → notification.markSending(now)          │
│                      row.lease(now + app.dispatch.lease)    │
│                      → ClaimedBatch 不可變快照               │
│     COMMIT                                                  │
│                                                            │
│  ② DeliveryDispatcher.process        無交易                  │
│       LineMulticastClient.multicast                         │
│         CircuitBreaker( RateLimiter( POST …/multicast ) )   │
│         X-Line-Retry-Key = delivery.retry_key               │
│       LineErrorClassifier → SendOutcome                     │
│         SENT / RETRY / FATAL / DEFERRED                     │
│                                                            │
│  ③ DeliveryStore.writeBack           @Transactional（短）   │
│       markSent / markFailed / scheduleRetry                 │
│         / deferForCircuitBreaker                            │

│         pending == 0 → notification.complete(...)           │

│                                                            │
└────────────────────┬───────────────────────────────────────┘

                     ▼
┌─ 補償段（DeliveryScheduler）───────────────────────────────┐
│                                                            │
│  @Scheduled(fixedDelayString =                              │
│      "${app.dispatch.poll-interval:PT10S}")                 │
│    → 呼叫同一個 DeliveryDispatcher.runOnce()                 │
│                                                            │
└────────────────────────────────────────────────────────────┘
```

三段式（短交易 → 無交易的網路呼叫 → 短交易）是刻意的：`DeliveryDispatcher` **整個類別沒有 `@Transactional`**，因為 Hikari 只有 10 條連線，讓數百毫秒的 LINE 呼叫壓在交易裡會迅速吃光連線池。`DeliveryStore` 與 `DeliveryDispatcher` 拆成兩個 bean 也是必要的——同一個 bean 內的 self-invocation 會讓 `@Transactional` 完全失效。

`process` 的 `catch (Exception)` 只 `log.error` 並繼續下一批、不中斷整輪，這同樣是刻意的：outbox 保證不掉單，這一批下一輪自然會被重新取到。

### `DispatchKicker` 與 `DeliveryScheduler` 的分工

| | `DispatchKicker` | `DeliveryScheduler` |
|---|---|---|
| 觸發 | `NotificationService.kickAfterCommit` 註冊的 `afterCommit` 回呼 | `@Scheduled(fixedDelayString = "${app.dispatch.poll-interval:PT10S}")` |
| 執行緒 | `@Async("notifyTaskExecutor")` | Spring 排程執行緒 |
| 開關 | 方法內 `if (!properties.isEnabled()) return;` | 類別上 `@ConditionalOnProperty(matchIfMissing = true)` |
| 定位 | **延遲優化**。沒跑成只是慢一輪 | **正確性保證**。註解明言「永遠不要因為即時派送已經夠快而把它關掉」 |
| 例外 | `log.warn("即時派送失敗，交由排程重試")` | `log.error`；排程方法拋例外會讓 Spring 停掉後續執行 |

用 `fixedDelay` 而非 `fixedRate`：間隔從上一輪**結束**起算，避免 LINE 變慢時工作愈堆愈多。

### 排程發送

`Notification.scheduledAt`（`null` = 立即發送）**不另開一條派送路徑**，而是沿用租約：`persistBatches` 在 `scheduledAt` 尚未到期時對每一批 `delivery.lease(scheduledAt)`，把 `next_attempt_at` 推到排程時間，既有的 `PENDING AND next_attempt_at <= now` 取件邏輯原封不動適用。

入口只有管理台（`AdminService.sendTest`）；HTTP API 走的多載永遠 `scheduledAt = null`。驗證在 `AdminService.validateScheduledAt`：早於 `now + 30 秒` 或晚於 `now + 366 天` → 400。取消走 `DeliveryStore.cancel`，僅 `status == QUEUED` 才成功。

### 2.1 為什麼派送要在**交易提交後**才啟動

若在 `@Transactional` 方法內直接呼叫 `@Async` 派送，會產生競態：非同步執行緒可能在交易提交前就去查 `notification_delivery`，結果查不到任何資料。

實作在 `NotificationService.kickAfterCommit`，三個要點缺一不可：

1. 先檢查 `TransactionSynchronizationManager.isSynchronizationActive()`，否則在無交易情境下註冊會拋例外。
2. `afterCommit` 跑在 **HTTP 執行緒**上，所以裡面只能呼叫**另一個 bean**（`DispatchKicker`）的 `@Async` 方法——同 bean 呼叫不會經過代理，`@Async` 等於沒寫。
3. 整段要包 `try/catch`，否則踢派送失敗會讓一個**已經提交**的請求對外變成 500。

**這是最容易寫錯且最難重現的 bug 之一**——在本機因為交易提交很快，多半不會出現；上線後在負載下才偶發。

> 反向的窗口——「已送出但 commit 失敗」——是**存在**的，而且是刻意接受的風險，見 §5.2。

## 3. DB Outbox 模式

`notification_delivery` **同時是投遞明細與工作佇列**。這是本設計的核心，理由見 [ADR-0007](adr/0007-非同步採-DB-outbox-而非訊息中介.md)。

### 3.1 取件查詢

在 JPA 層寫成（`NotificationDeliveryRepository.lockPending`）：

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "-2"))
@Query("""
        select d from NotificationDelivery d
        where d.status = ...DeliveryStatus.PENDING
          and d.nextAttemptAt <= :now
        order by d.priority, d.nextAttemptAt
        """)
List<NotificationDelivery> lockPending(@Param("now") Instant now, Limit limit);
```

`lock.timeout = -2` 是 Hibernate 表示 `SKIP_LOCKED` 的魔術值。Postgres 端實際產生的是：

```sql
SELECT *
  FROM notification_delivery
 WHERE status = 'PENDING'
   AND next_attempt_at <= now()
 ORDER BY priority, next_attempt_at
 LIMIT :batchLimit          -- app.dispatch.batch-limit，預設 10
   FOR UPDATE SKIP LOCKED;
```

| 子句 | 為什麼 |
|---|---|
| `FOR UPDATE` | 鎖住取到的列，避免其他工作者重複處理 |
| `SKIP LOCKED` | 跳過已被鎖的列而非等待。多個工作者可完全並行取件，互不阻塞 |
| `ORDER BY priority, next_attempt_at` | 高優先先送；同優先級依排隊順序 |
| `Limit` | 一次取一小批。取太多會讓單一工作者長時間持鎖 |

`idx_delivery_pickup`（partial index `ON (priority, next_attempt_at) WHERE status = 'PENDING'`）精確覆蓋此查詢（見 [04 §6](04-資料模型.md#6-notification_delivery)）。

### 3.1.1 兩條管線是同一套機制

API 監控輪詢的取件（`ApiMonitorRepository.lockDue`）**逐字**是同一組註解：`@Lock(PESSIMISTIC_WRITE)` + `lock.timeout = -2` + 同交易內寫租約，一樣譯成 `FOR UPDATE SKIP LOCKED`。

| | 通知派送 | API 監控輪詢 |
|---|---|---|
| 表 | `notification_delivery` | `api_monitor` |
| 取件條件 | `status='PENDING' AND next_attempt_at <= now` | `enabled = true AND next_run_at <= now` |
| 排序鍵 | `priority, next_attempt_at` | `next_run_at` |
| 取件上限 | `app.dispatch.batch-limit`（10） | `app.monitor.claim-limit`（5） |
| 租約 | `lease(now + app.dispatch.lease)`，預設 `PT2M` | `lease(now + app.monitor.lease)`，預設 `PT2M` |
| 索引 | `idx_delivery_pickup` | `idx_api_monitor_due ON (next_run_at) WHERE enabled` |
| 快照型別 | `ClaimedBatch`（不可變，非 entity） | `ClaimedMonitor`（不可變，非 entity） |
| 退避 | `backoff(attempt)` 見 §4.1 | `interval × min(2^(fails-1), 16)` 見 §4.3 |

**讀這份文件時不要把它們想成兩套設計。** 取件、租約、快照、三段式交易邊界都一樣；差別只有排序鍵、上限值與退避公式。

### 3.1.2 租約與 `SKIP LOCKED` 解決的是不同問題

兩者缺一不可，程式註解在 `DeliveryStore.claim` 與 `ApiMonitorStore.claim` 都明寫：

| 機制 | 管什麼 |
|---|---|
| `FOR UPDATE SKIP LOCKED` | **同一瞬間**兩個工作者取到同一列 |
| 租約（把 `next_attempt_at` 推到 `now + lease`） | **這一輪還沒回寫、下一輪又取到**同一列 |

鎖只在 claim 那個短交易內存在，交易一提交鎖就沒了；此後到 `writeBack` 之間的數百毫秒，只靠租約擋住下一輪。

### 3.2 這個模式解決了什麼

| 問題 | 純記憶體佇列 | DB outbox |
|---|---|---|
| 應用重啟 | 佇列中的工作**永久消失** | 仍在 DB，重啟後排程輪詢撿回 |
| 派送到一半當機 | 該批狀態不明 | 仍是 `PENDING`，租約到期後被重新取件 |
| 要查「現在積了多少」 | 需要額外暴露內部狀態 | 一句 SQL |
| 未來要多實例 | 需要整個重寫 | `SKIP LOCKED` 已經是多實例安全的 |

代價是每批多幾次 DB 往返。以本專案的量級（每批對應一次數百毫秒的 LINE API 呼叫）完全可忽略。

## 4. 重試

### 4.1 派送的退避策略

`NotificationDelivery.MAX_ATTEMPTS = 5`。公式（`NotificationDelivery.backoff`）：

```java
static Duration backoff(int attempt, double jitterRatio) {
    long base = 1L << Math.min(attempt - 1, 10);
    long millis = (long) (base * 1000 * (1.0 + jitterRatio));
    return Duration.ofMillis(Math.max(500, millis));
}
```

`jitterRatio` 來自 `DeliveryStore.jitter()` = `ThreadLocalRandom.current().nextDouble(-0.2, 0.2)`，即 **±20%** 隨機抖動，避免大量批次在同一時刻同時重試造成尖峰。

`scheduleRetry` 是**先 `attempt_count++` 再判斷**：`attemptCount >= 5` → `FAILED`；否則 `next_attempt_at = now + backoff(attemptCount, jitter)`。因此實際排到的序列是：

| 第 n 次失敗後 `attempt_count` | 結果 | 退避基準（含 ±20% 抖動） |
|---|---|---|
| 1 | `PENDING` | ~1 秒（0.8–1.2 s） |
| 2 | `PENDING` | ~2 秒（1.6–2.4 s） |
| 3 | `PENDING` | ~4 秒（3.2–4.8 s） |
| 4 | `PENDING` | ~8 秒（6.4–9.6 s） |
| 5 | **`FAILED`** | 不再排程 |

> ⚠️ **註解與行為不符（doc drift）。** `NotificationDelivery` 的類別註解與 `backoff` 的 javadoc 都寫「1、2、4、8、16 秒」，但因為 `MAX_ATTEMPTS = 5` 且 `attempt_count++` 在判斷之前，**「16 秒」那一段永遠排不到**——第 5 次失敗直接判 `FAILED`。以本表為準。

實作方式是寫 `next_attempt_at` 與 `attempt_count`，然後**交還給排程輪詢**——不在原執行緒 sleep。sleep 會佔住執行緒，而執行緒池是有限資源。

`DEFERRED`（斷路器或限速器擋下）走完全不同的路：`deferForCircuitBreaker(now + 30 秒)`（`DeliveryStore.DEFER_SECONDS = 30`），**不遞增 `attempt_count`**。理由見 §6.3。

### 4.2 哪些錯誤才重試

分類器是 `LineErrorClassifier`，設計原則寫在類別註解：**預設偏向重試**，只有明確知道重試無用才判 `FATAL`。完整分類見 [06 §5.4](06-LINE整合設計.md#54-錯誤分類)。

`classify(HttpStatusCode, String body)`：

| 條件 | Kind | errorCode | 為什麼 |
|---|---|---|---|
| `429` 且 body 含 `"monthly limit"` | `FATAL` | `LINE_MONTHLY_QUOTA` | 重試到下個月也不會成功 |
| `429` 其他 | `RETRY` | `LINE_RATE_LIMITED` | 短時間打太快 |
| `401` / `403` | `FATAL` | `LINE_UNAUTHORIZED` | channel token 失效或被撤銷 |
| `400` | `FATAL` | `LINE_BAD_REQUEST` | 訊息格式／user id 無效，內容不會自己變好 |
| `5xx` | `RETRY` | `LINE_SERVER_ERROR` | **唯一**會被包成 `LineServerException` 餵給斷路器的碼 |
| `2xx` | `SENT` | — | 防禦性分支，正常呼叫端不會走到 |
| 其他狀態碼 | `RETRY` | `LINE_UNEXPECTED_STATUS` | 沒見過的碼偏向重試 |

`classify(Throwable)`：任何網路層例外（逾時、連線被拒、DNS 失敗）→ `RETRY` / `LINE_IO_ERROR`。

不經 classifier、由呼叫端自行產生的 outcome：

| 來源 | 條件 | Kind | errorCode |
|---|---|---|---|
| `LineMulticastClient` | `CallNotPermittedException`（斷路器開路） | `DEFERRED` | `CIRCUIT_OPEN` |
| `LineMulticastClient` | `RequestNotPermitted`（本地 RateLimiter 拿不到令牌） | `DEFERRED` | `RATE_LIMITER` |
| `DeliveryStore.claim` | payload 已被清空或通知已刪 | `markFailed` | `PAYLOAD_GONE` |
| `DeliveryStore.cancel` | 管理台取消排程 | `markFailed` | `CANCELLED` |

錯誤訊息一律經 `abbreviate`：壓縮連續空白，超過 500 字截成 497 字 + `"..."`；寫入 `error_message` 時再截到 1000 字。

**把不可恢復的錯誤拿去重試，只是把同一個失敗重複 5 次然後得到同樣的結果**，還浪費了 API 配額。

> **分類器不會停用使用者。** 沒有任何 error code 會改動 `line_user.status`——因為 LINE 對已封鎖使用者的 multicast **仍然回 200**，發送回應根本無法判斷名單有效性。標成 `BLOCKED` 只有兩條路徑：`UnfollowEvent` webhook，以及 `ProfileSyncService.reconcileDaily` 收到 Profile API 的 404。

### 4.3 監控輪詢的退避策略

不同的公式，不共用 `backoff()`（`ApiMonitor.recordFailure`）：

```text
next_run_at = now + effectiveIntervalSeconds × min(2^(consecutiveFailures - 1), 16)
```

- 指數**先夾在 `0..4` 再取冪**，避免長期故障時整數溢位。乘數序列為 `1, 2, 4, 8, 16, 16, 16, …`。
- `effectiveIntervalSeconds` = `max(monitor.intervalSeconds, app.monitor.min-interval)`，所以管理員調高全域下限後對既有監控立即生效。
- 沒有次數上限、**不會判定終局失敗**——監控是持續性任務，只會愈退愈慢，不像派送會標 `FAILED`。
- 成功時 `recordSuccess` 重設：`next_run_at = now + effectiveInterval`、`consecutive_failures = 0`、`failure_notified = false`。
- **沒有 in-process 重試**：一次失敗就記一列 `FAILED` 的 `api_monitor_run` 並退避排程。

## 5. 冪等

三層冪等，各自解決不同層級的重複：

| 層 | 機制 | 防止的重複 |
|---|---|---|
| **API 層** | `Idempotency-Key` + `UNIQUE (client_id, idempotency_key)` | 呼叫端因逾時而重送整個請求 |
| **LINE 層** | `X-Line-Retry-Key`，每批固定一把，重試時不變 | 我們重試時 LINE 端重複投遞 |
| **Webhook 層** | `webhook_event` 表主鍵 | LINE 重送 webhook 事件 |

`retry_key` 是 `NotificationDelivery` 建立時就固定的 `UUID.randomUUID()`（`NotificationService.persistBatches`），**每批一把**，所有重試沿用同一把。

### 5.1 API 層的細節

```text
帶 Idempotency-Key 的請求進來
  → 嘗試 INSERT notification（含 idempotency_key）
  → 唯一鍵衝突？
       否 → 正常流程
       是 → 查出既有的 notification
            比對 payload_hash 是否相同
              相同 → 回傳既有結果（202，與第一次相同）
              不同 → 409 IDEMPOTENCY_CONFLICT
```

比對 `payload_hash` 而非整個 payload：payload 可能已被清空（`persistPayload = false` 的通知在 `finalise` 成功後由 `applyPayloadRetention` 立刻清；另見 [04 §11](04-資料模型.md#11-資料保留與清理缺口-g7)），但 hash 永遠保留。

寫入用 `INSERT … ON CONFLICT DO NOTHING`（`notifications.insertIfAbsent`），把「檢查」與「寫入」壓在同一句 SQL，而不是先 `SELECT` 再 `INSERT`——後者在併發下會兩個請求都通過檢查。

### 5.2 「送出後 commit 失敗」的窗口

⚠️ **這個窗口存在，而且是刻意接受的風險。**

位置在 `DeliveryDispatcher.process`：`lineClient.multicast(...)` 已經回 `SENT`，但接下來的 `store.writeBack(...)` 失敗（DB 瞬斷、程序被 kill、寫回交易 rollback）。此時：

1. `notification_delivery` 仍是 `PENDING`，`next_attempt_at` 停在 claim 當時寫的租約（`now + app.dispatch.lease`，預設 2 分鐘）。
2. 租約到期後，下一輪會**重新取到同一批，再打一次 LINE**。
3. 緩解完全依賴 `X-Line-Retry-Key`：重試沿用同一把 key，由 **LINE 端去重**，使用者不會收到重複訊息。`NotificationDelivery` 與 `LineErrorClassifier` 的註解都明確寫出這個依賴。

同樣的道理適用於**逾時的雙重不確定**：`READ_TIMEOUT = 10s` 觸發時分類器判 `LINE_IO_ERROR` / `RETRY`，但請求其實可能已經送達 LINE。一樣靠 retry key 兜底。

> **TODO：待確認。** 程式碼中**沒有**任何針對 retry key 有效期的處理或校驗。若 LINE 端 retry key 的去重窗口短於 `app.dispatch.lease`（預設 2 分鐘）加上退避時間，重送就會真的變成重複投遞。`app.dispatch.lease` 與 LINE retry key 有效期的關係目前無人把關，需要查證官方時限後決定是否加上限制。

### 5.3 取消排程的窄視窗競態

`DeliveryStore.cancel` 讀 `notification.status` 判斷「還沒開始送」，但**沒有跟 `claim` 搶同一把鎖**。程式註解自承：取消判定通過的瞬間，派送器可能剛好取走同一批並標成 `SENDING`，之後仍照常送出。

**刻意不修**——這是管理台的便利功能，不值得為此把兩條路徑綁進同一把鎖的複雜度。

## 6. Circuit Breaker（缺口 G4）

### 6.1 沒有它會怎樣

LINE API 掛掉或憑證失效時，沒有斷路器的行為是：每批重試到 `MAX_ATTEMPTS` 用盡（約 1+2+4+8 = 15 秒）然後標 `FAILED`。

結果是**佇列裡所有東西在幾分鐘內全部燒成 `FAILED`**，同時對已經掛掉的 LINE 打出大量無用請求。服務恢復後，這些通知也不會自動補送——它們已經是終局失敗了。

### 6.2 設定

Resilience4j `CircuitBreaker` 包住所有 LINE 發送呼叫（`LineApiConfig.lineCircuitBreaker`）：

| 參數 | 值 | 說明 |
|---|---|---|
| `slidingWindowType` | `COUNT_BASED` | 以次數而非時間開窗 |
| `slidingWindowSize` | 20 | 統計最近 20 次呼叫 |
| `failureRateThreshold` | 50% | 失敗率超過即開路 |
| `waitDurationInOpenState` | **30 秒** | 開路後等待多久進入半開 |
| `permittedNumberOfCallsInHalfOpenState` | 3 | 半開時試探 3 次 |
| `minimumNumberOfCalls` | 10 | 少於 10 次不做判定（避免冷啟動誤判） |
| `automaticTransitionFromOpenToHalfOpenEnabled` | `true` | 不需要有呼叫進來才轉半開 |

**只有 `LINE_SERVER_ERROR`（5xx）會被 `LineMulticastClient` 包成 `LineServerException` 拋出，讓斷路器計入失敗。** `400` / `401` / `403` 是我們自己的問題，不代表 LINE 掛了，不計入。

包覆順序是 `circuitBreaker.executeCallable( RateLimiter.decorateCallable(rateLimiter, send) )`——**斷路器在外**，開路時立刻回覆而不先排隊等令牌。

HTTP 逾時另外設在 `LineMulticastClient`：`CONNECT_TIMEOUT = 5s`、`READ_TIMEOUT = 10s`。

### 6.3 開路時的行為 —— 關鍵差異

> **斷路期間的批次是「延後」，不是「失敗」。**

```text
CircuitBreaker OPEN
  → multicast 立刻拋 CallNotPermittedException
  → LineMulticastClient 轉成 SendOutcome(DEFERRED, "CIRCUIT_OPEN")
  → writeBack → deferForCircuitBreaker(now + 30s)
       status 維持 PENDING
       next_attempt_at = now + DeliveryStore.DEFER_SECONDS（30 秒）
       attempt_count 不遞增   ← 重點
  → 30 秒後自動 HALF_OPEN，試探性放行 3 次
  → 成功 → CLOSED，下一輪排程輪詢自動把積壓的批次全部送出
```

**`attempt_count` 不遞增**是關鍵：否則一次 LINE 端的長時間故障，會讓所有批次在斷路期間耗盡重試次數，變成永久失敗。斷路器擋下的呼叫根本沒送出去，不該算成一次嘗試。

本地 `RateLimiter` 拿不到令牌（`RequestNotPermitted`）走完全相同的路徑，只是 errorCode 是 `RATE_LIMITER`。理由一樣：從來沒送出去的呼叫不該算成一次嘗試。

**注意 `DEFER_SECONDS`（30 秒）與 `waitDurationInOpenState`（30 秒）是兩個各自寫死的常數**，程式沒有讓後者推導前者。改動其中一個時要記得另一個。

### 6.4 告警

`CircuitBreaker` 狀態變化要發出告警（Phase 2 的自我監控），但**告警本身不能走同一條斷路的路徑**——否則 LINE 掛掉時告警也發不出去。詳見 [09-CICD與維運](09-CICD與維運.md) 的自我監控段落。

⏳ **現況：尚未實作。** `LineApiConfig` 只建立 `CircuitBreaker` bean，沒有註冊任何 `onStateTransition` 監聽器，狀態變化目前只反映在 Resilience4j 自己的 metrics 上，不會主動通知任何人。

## 7. 速率控制

兩個方向，別搞混：

| 方向 | 機制 | 上限 | 設定鍵 | 文件 |
|---|---|---|---|---|
| 呼叫端 → 我們 | `RateLimitFilter`，per-client token bucket | 60 req/min | `app.rate-limit.default-per-minute`（`client.rate_limit_per_min` 可個別覆寫） | [03 §4](03-權限與認證設計.md#4-呼叫端速率限制與配額缺口-g2) |
| 我們 → LINE | Resilience4j `RateLimiter`，全域 | 100 req/s | `app.line.rate-limit-per-second` | 本節 |

`lineRateLimiter` 的完整參數（`LineApiConfig`）：`limitRefreshPeriod = 1s`、`limitForPeriod = app.line.rate-limit-per-second`、**`timeoutDuration = Duration.ZERO`**。

`timeoutDuration = ZERO` 是刻意的：拿不到令牌就**立刻**回 `RequestNotPermitted`，不阻塞執行緒等待。派送器收到後走 `DEFERRED` 路徑推遲 30 秒重排（§6.3），而不是讓一個池執行緒卡在那裡空等。

同一組保護也套用在斷路器外層，包覆順序見 §6.2。

LINE 的 multicast 上限是 200 req/s（[06 §1.1](06-LINE整合設計.md#11-發送端點)），我們設 100 是刻意留一半餘裕——因為：

- LINE 用 token bucket，突發流量的實際判定比平均值嚴格
- 同一 channel 的其他呼叫（Profile API、額度查詢、reply）共用整體配額
- 撞到 `429` 的代價（重試、延遲、可能的告警）遠大於慢一點的代價

以本專案量級，100 req/s 意味著 1200 人的全體發送（3 批）在毫秒級就能送完，速率限制根本不是瓶頸。留餘裕是零成本的保險。

> ⚠️ `LineLimits.MULTICAST_RATE_PER_SECOND = 200` 這個常數**沒有任何程式引用**，純粹是文件性質；實際限速讀的是 `app.line.rate-limit-per-second`。兩者若不同步，不會有任何編譯或執行期警告。
>
> ⚠️ Resilience4j 的 `RateLimiter` 與 `CircuitBreaker` 狀態都在 **JVM 內**。多實例下每個實例各算各的 100 req/s，總量會是 `實例數 × 100`。見 §11。

|---|---|

| 優雅關閉 | `waitForTasksToCompleteOnShutdown` + 30 秒等待，讓進行中的批次有機會 `writeBack`；沒寫完的靠租約到期後重取 |

### 8.1 MDC 傳遞（缺口 G3）

`@Async` 換執行緒後，**MDC（含 correlation id）不會自動帶過去**。實作是 `AsyncConfig::propagateMdc`：

```java
private static Runnable propagateMdc(Runnable task) {
    Map<String, String> context = MDC.getCopyOfContextMap();
    return () -> {
        Map<String, String> previous = MDC.getCopyOfContextMap();
        if (context != null) {
            MDC.setContextMap(context);
        }
        try {
            task.run();
        } finally {
            if (previous != null) {
                MDC.setContextMap(previous);   // 還原，不是清空
            } else {
                MDC.clear();
            }
        }
    };
}
```

漏掉這段的後果：非同步段的所有 log 都沒有 `requestId`，出事時無法把同步段與非同步段的日誌串起來。**這是最容易漏、也最容易在事故當下讓人抓狂的一個細節。**

⚠️ **收尾用「還原」而不是無條件 `MDC.clear()`**，這一點常被寫錯。因為 `CallerRunsPolicy` 下工作會跑在**呼叫者的 HTTP 執行緒**上：若無條件 clear，會把該 HTTP 請求後半段自己的 MDC 一併抹掉，導致後半段日誌無故失去追蹤碼——而且**只在池滿、也就是最需要查日誌的時候**發生。存下原本的 context 再還原，兩種情形都正確（非同步執行緒原本是空的，還原等同於清空）。

`monitorTaskExecutor` 用同樣手法。`ApiMonitorRunner.process` 另外自己 `MDC.put("monitorId", …)`。

## 9. 優先級（缺口 G10）

單一 FIFO 佇列有 head-of-line blocking：對 1200 人的全體公告切成 3 批排在前面，後面一則「伺服器當機」的緊急告警就得等。

`notification_delivery.priority`（0 高 … 9 低），取件時 `ORDER BY priority, next_attempt_at`。

### Phase 1 的自動指派

| target | priority |
|---|---|
| `OWNER` | 0 |
| `SELF` | 5 |
| `USER` | 5 |
| `ALL` | 9 |

理由：`OWNER` 幾乎都是系統告警（最需要即時）；`ALL` 幾乎都是公告（可以等）。

Phase 2 再開放 API 讓呼叫端指定（並限制一般 client 能設的最高優先級，避免大家都標 0）。

**欄位現在就加**：事後補要改索引定義與所有取件查詢，成本高得多；現在加幾乎是零成本。

## 10. 狀態一致性

### 10.1 `notification` 最終狀態

`DeliveryStore.finalise` 在**每次** `writeBack` 都跑一次（刻意冪等，不指定「最後一批負責結算」）：先 `deliveries.tally(notificationId)`，`pending == 0` 才呼叫 `notification.complete(...)`。

```text
全部 SENT                   → SUCCEEDED
部分 SENT、部分 FAILED       → PARTIAL
全部 FAILED                 → FAILED
```

`success_count` / `failure_count` 以**收件人數**加總（`sum(recipient_count) FILTER (…)`），不是批次數——呼叫端關心的是幾個人收到，不是幾批送出。

`complete()` 另有前置條件 `!status.isTerminal()`；程式中**沒有任何路徑**把終局狀態改回非終局。

> `SUCCEEDED` 的語意是「**LINE 接受了請求**」，不是「使用者看到了訊息」。`NotificationStatus` 的 javadoc 明載這一點。

### 10.2 卡在 `SENDING` 的偵測

若某批因為程序被 kill 而沒有寫回狀態，`notification` 會停在 `SENDING`。

規劃的偵測條件是：`SENDING` 且 `started_at < now() - 30 minutes` 的 notification 是異常訊號。

正常情況下這會自癒：對應的 delivery 仍是 `PENDING`，租約到期後 `DeliveryScheduler` 那一輪會重新取件，最終狀態被正確回寫。**不需要人工介入**——這是 outbox 模式的自癒特性。

⏳ **但偵測本身沒有實作。** 見 §11.1 缺口 D1：`NotificationRepository.findByStatusAndStartedAtBefore` 在 `main` 中沒有任何呼叫端，DB 索引 `idx_notification_stuck ON notification (started_at) WHERE status = 'SENDING'` 已經建好但沒人用。

### 10.3 `PAYLOAD_GONE` 不會 finalise（缺口 D3）

⚠️ **這是目前唯一會讓 `notification` 真的永久卡住的路徑。**

`DeliveryStore.claim` 在 payload 已被清空或通知已被刪除時，把該批 `markFailed("PAYLOAD_GONE", …)` 之後**直接 `continue`，不呼叫 `finalise`**——`finalise` 只出現在 `writeBack` 與 `cancel` 裡。

後果：若一則通知的**所有**批次都走這條路（沒有任何一批進到 `writeBack`），`notification.status` 會永遠停在 `QUEUED` 或 `SENDING`，`success_count` / `failure_count` 保持 0，而底下的 delivery 明明全都已經是 `FAILED`。

自癒機制救不了這個——delivery 已經是終局的 `FAILED`，不會再被取件，也就永遠不會有人去呼叫 `finalise`。修法是在 `claim` 的這條分支補上 `finalise`。

### 10.4 明細清理後的統計保留

`notification` 上的三個計數欄位是去正規化保存的，**刪除明細不影響統計查詢**。這是 [04 §5](04-資料模型.md#5-notification) 刻意冗餘的原因。

⚠️ **但「90 天保留期」目前沒有任何排程在執行**，見 §11.1 缺口 D2。這個設計是為了「將來真的開始清理時統計不會消失」而先做的，不是對現況的描述。

### 11.2 刻意接受的風險

| 風險 | 位置 | 為什麼不修 |
|---|---|---|
| 「送出後 commit 失敗」的重送窗口 | `DeliveryDispatcher.process` | 靠同一把 `X-Line-Retry-Key` 讓 LINE 端去重。**但程式碼沒有校驗租約時間與 LINE retry key 有效期的關係**——見 §5.2 的 TODO |

| 取消排程的窄視窗競態 | `DeliveryStore.cancel` | 管理台便利功能，不值得為此把兩條路徑綁進同一把鎖。見 §5.3 |

### 11.3 多實例（缺口 G12）

**取件本身已經是多實例安全的**：`lockPending` / `lockDue` 的 `FOR UPDATE SKIP LOCKED` 讓多個工作者完全並行，`NotificationDeliveryRepository` 的註解明言「現在寫的邏輯在未來加開第二個實例時不需要任何改動」。

問題全在其他地方：

| 元件 | 問題 | 加第二個實例前要做什麼 |
|---|---|---|
| `ProfileSyncService.reconcileDaily`（`0 0 3 * * *`） | 重複執行，浪費 LINE 速率配額 | 導入 ShedLock |
| `WebhookEventGuard.purgeExpired`（`0 15 3 * * *`） | 重複刪除（冪等，但浪費資源） | 導入 ShedLock |
| `ApiMonitorSweeper.runOnce`（`0 20 3 * * *`） | 同上 | 導入 ShedLock |
| `NonceStore.purgeExpired`（`fixedDelay PT5M`） | 同上 | 導入 ShedLock |
| `RateLimitFilter` | **per-instance 計數**，總量會變成 `實例數 × 上限` | 改用共享儲存，或按實例數等比下調上限 |
| `lineRateLimiter` / `lineCircuitBreaker` | Resilience4j 狀態在 JVM 內，各實例各算各的 | 改用共享狀態，或等比下調 `app.line.rate-limit-per-second` |

四個需要 ShedLock 的排程**目前都還沒導入**（PostgreSQL LockProvider）。`DeliveryScheduler` 與 `ApiMonitorScheduler` 不在此列——它們背後就是 `SKIP LOCKED` 取件，重複執行只是各取各的。

### 11.4 其他擴充路徑

| 限制 | 現況 | 何時要處理 | 怎麼處理 |
|---|---|---|---|
| 輪詢間隔 `PT10S` | 首次派送走 `DispatchKicker`（即時），排程只是補償 | 若補償路徑的延遲成為問題 | 縮短 `app.dispatch.poll-interval`，或改用 PostgreSQL `LISTEN/NOTIFY` |
| 無死信處理 | `FAILED` 的批次留在表中，無自動重新派送 | 需要人工重送功能時 | Phase 2 Admin 提供「重送這筆」按鈕 |
| 無跨通知的合併 | 每筆通知獨立發送 | 若同一批人短時間收到大量通知 | [缺口 G15](02-架構設計.md#g15--通知抑制去重--phase-2-候選) 的抑制機制 |
| 只有 multicast，沒有 push | 單一收件人（`target = SELF`）也走 multicast | — | 刻意如此，見 [ADR-0003](adr/0003-ALL-採-multicast-而非-broadcast.md) 與 [06 §5.1](06-LINE整合設計.md#51-為什麼全部走-multicast) |
