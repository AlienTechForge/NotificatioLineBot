## 2. 請求流程

### 2.1 通知發送（同步段）

```
1. HmacAuthFilter        驗時間戳 → 驗 nonce → 查 client → 常數時間比對簽章 → 建 ClientPrincipal
2. RateLimitFilter       per-client 速率限制（每實例計數，見 §6 G12）
3. NotificationController DTO 驗證（text 長度、userIds 格式與數量、message 數上限）
4. NotificationService.submit（@Transactional）
   4.1 Idempotency-Key   同 key 同 body → 重播既有結果；同 key 不同 body → 409
   4.2 MessageAssembler  簡易／進階模式組出 LINE messages（進階需 notify:raw）
                         UriHostValidator 檢查連結網域白名單
   4.3 TargetResolver    依 target 檢查 scope → 解析出收件人清單
                         target 省略時套用 client 的預設對象（default_target_*）
   4.4 BatchSplitter     去重 + 每 500 人切一批
   4.5 每日配額          以「實際收件人數」計、滾動 24 小時窗口，超過回 429
   4.6 寫入              notification（含 payload）+ 逐批寫 notification_delivery
5. 回 202 + notificationId
```

> 註：文件早期版本寫的 `QuotaGuard`（`target=ALL` 時查 LINE 月額度餘量）**未實作**。
> `ErrorCode.LINE_MONTHLY_QUOTA_EXCEEDED` 這個 enum 值存在，但全域沒有產生點。
> LINE 月配額查詢已存在於管理台（`admin/LineQuotaClient`）；尚未實作的是送出前的月額度阻擋。

### 2.2 通知派送（非同步段）

```
交易提交後（afterCommit）→ DispatchKicker.kick()  @Async，純延遲優化
                         ↘
DeliveryScheduler  @Scheduled(fixedDelay, 預設 PT10S)  ← 正確性保證
                         ↘
                     DeliveryDispatcher.runOnce()
                       → DeliveryStore.claim()
                           SELECT ... FOR UPDATE SKIP LOCKED
                           + 把 next_attempt_at 推到 now + lease（預設 2 分鐘）當租約
                       → LineMulticastClient  →  POST /v2/bot/message/multicast
                           RateLimiter（app.line.rate-limit-per-second，預設 100）
                           CircuitBreaker
                       → LineErrorClassifier 把 HTTP／例外分類成 SendOutcome
                       → DeliveryStore.writeBack()：更新 delivery 狀態 + line_request_id，
                         回寫 notification 計數與最終狀態

失敗批次留在 PENDING + 延後的 next_attempt_at，下一輪自然被撿回來重試。
重試沿用建立時就固定的同一把 X-Line-Retry-Key，讓 LINE 端去重。
```

`DeliveryDispatcher` 本身**完全沒有 `@Transactional`** —— 所有需要交易的 DB 動作都收斂在
`DeliveryStore`（`claim` / `writeBack` / `cancel`），避免長交易跨越 LINE API 呼叫。

`DispatchKicker` 是**另一個 bean** 的 `@Async` 方法，這是必要的：`@Async` 靠 Spring 代理生效，
類別內部自呼叫會安靜地退化成同步執行，讓呼叫端要等整批送完才拿到 202。

詳見 [07-非同步與可靠性設計](07-非同步與可靠性設計.md)。

### 2.3 API 監控輪詢（第二條 outbox 管線）

`monitor/` 子系統有**自己的一條 claim + 租約管線**，與通知派送並存但互不干涉：

```
ApiMonitorScheduler  @Scheduled
   → ApiMonitorStore.claim()
       ApiMonitorRepository.lockDue：@Lock(PESSIMISTIC_WRITE)
       + QueryHint jakarta.persistence.lock.timeout = -2（Hibernate 譯成 SKIP LOCKED）
       + 把 next_run_at 推到 now + lease（預設 2 分鐘）當租約
   → ApiMonitorRunner
       → ApiFetcher（https only、Redirect.NEVER、OutboundUrlGuard 擋內網位址）
           RequestTemplate 展開 {{now.*}} / {{uuid}} / {{computed.*}}
           SiteSessionService 從 site_session 取 cookie jar（AES-256-GCM，
           AAD = site_session:{host}）；MonitorSecretService 取 monitor_secret
       → JsonExtractor → ChangeDetector（CompareMode 三選一）
       → MessageTemplate 組出訊息文字
       → NotificationService.submit（**共用同一條派送管線，絕不繞過**）
   → 寫 api_monitor_run；NEW_ITEMS 模式另寫 api_monitor_seen_item 去重
```

**兩條管線的取件機制其實是同一套**：`NotificationDeliveryRepository.lockPending` 與
`ApiMonitorRepository.lockDue` 都用 `@Lock(LockModeType.PESSIMISTIC_WRITE)` 搭配
`jakarta.persistence.lock.timeout = -2`，由 Hibernate 產生 `FOR UPDATE SKIP LOCKED`；
兩者都在同一交易內寫入租約欄位（派送是 `next_attempt_at`，監控是 `next_run_at`）。
`ApiMonitorRepository` 的 javadoc 明白寫著「抄 `NotificationDeliveryRepository.lockPending` 的做法」。

差別在排序鍵：派送 `ORDER BY priority, next_attempt_at`（缺口 G10 的優先級），
監控 `ORDER BY next_run_at`。

詳見 [11-API監控輪詢設計](11-API監控輪詢設計.md)、[12-API監控易用性升級](12-API監控易用性升級.md)、
[13-監控計算欄位設計](13-監控計算欄位設計.md)。

1. HTTP API — `NotificationController.create`

3. API 監控告警 — `ApiMonitorStore.submit`（該處註解明言「絕不能繞過」）

### 4.1 ⚠️ 與 ADR-0005 的落差

[ADR-0005](adr/0005-Admin-UI-單一-repo-打包進-jar.md) 規劃的機制是「`server/pom.xml` 的
`with-admin-ui` profile 呼叫 frontend-maven-plugin 去 build `../admin-ui`」。

**這套機制從未實作。** `server/pom.xml` 裡 `with-admin-ui`、`frontend-maven-plugin`、
`admin-ui` 三個關鍵字的 grep 命中數都是 **0**。實際做法是把手寫的 `index.html` / `login.html` /
`assets/*` 直接放在 `src/main/resources/static/admin/`，由 Spring Boot 的預設靜態資源處理服務，
沒有任何 build step。

`admin-ui/` 目錄仍在 repo 裡，但只有 6 個 `.gitkeep`，**與實際運作中的後台毫無關聯**。
`docker/Dockerfile` 裡那個 `node:25-alpine` 階段是死路（`admin-ui/` 沒有 `package.json`，
`WITH_ADMIN_UI=true` 必定失敗）；而且若真有產物，`COPY --from=ui /ui/dist/ → static/admin/`
會覆蓋掉手寫後台。

→ 管理後台的實際技術棧見 §8。

### 5.1 Jackson 版本衝突（必須處理）

Spring Boot 4.1.0 BOM **同時管理兩套 Jackson**：

| Bom | 版本 | 使用者 |
|---|---|---|
| `com.fasterxml.jackson:jackson-bom` | 2.21.4 | 舊 API（`com.fasterxml.jackson.*`） |
| `tools.jackson:jackson-bom` | 3.1.4 | Spring MVC 預設（`tools.jackson.*`） |

但 `line-bot-jackson:10.1.0` 明確依賴 `jackson-databind:2.22.0`。BOM 的版本管理會壓過 transitive 依賴，把它降成 2.21.4。

**處理**：`server/pom.xml` 的 `<properties>` 覆寫

```xml
<jackson-2-bom.version>2.22.0</jackson-2-bom.version>
```

兩套 Jackson 是不同 groupId 與 package，**可以共存**（LINE SDK 走 retrofit + 自己的 ObjectMapper，Spring MVC 走 Jackson 3），不需要排除任何一方。

詳見 [ADR-0008](adr/0008-鎖定-Spring-Boot-4.1-並覆寫-Jackson-2-版本.md)。

### 5.2 Spring Boot 4 的 autoconfiguration 模組拆分（T1 實測）

Spring Boot 4 把原本單一的 `spring-boot-autoconfigure` **拆成一堆技術別模組**：`spring-boot-flyway`、`spring-boot-jpa`、`spring-boot-data-jpa`、`spring-boot-security`、`spring-boot-jdbc`、`spring-boot-actuator`…

後果：**只加函式庫本身不會啟動對應的 auto-configuration。**

實測踩到的：`flyway-core` 在 classpath 上，但 `FlywayAutoConfiguration` 住在 `org.springframework.boot:spring-boot-flyway`。少了它，應用**正常啟動、日誌毫無 Flyway 訊息、資料庫一張表都沒有** —— 沒有任何錯誤提示。

```xml
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-flyway</artifactId>   <!-- 這行才是 auto-config -->
</dependency>
```

`starter-*` 系列會自己帶對應模組（例如 `spring-boot-starter-data-jpa` 帶 `spring-boot-data-jpa`），所以問題只出在「直接依賴第三方函式庫」的情況。日後要加 Quartz、Liquibase、Redis 等等時要記得檢查。

## 6. 架構補強：資深架構師審查

以下是對初版設計的缺口盤點。**G1–G7 是 Phase 1 就會痛的，必須納入 MVP**；G8–G15 標註處置階段。

> **編號不可變動**：`server/` 的 javadoc 有 **15 處**以「缺口 G*n*」引用本節
> （涵蓋 G1、G2、G3、G5、G10、G12）。
> 各缺口的**實作現況**逐項標在下方，並彙整於 §6 末的處置總表。

### G1 — Webhook 事件去重 🔴 Phase 1

**問題**：LINE 在 webhook 回應逾時或非 200 時會**重送同一事件**。初版設計只說「把 follow/unfollow 寫成 upsert 保證冪等」，但這不夠——`FollowEvent` 還會**發歡迎訊息**，重送就會重複打招呼；`申請金鑰` 指令重送就會**發出兩個 enrollment token**。

**處置**：新增 `webhook_event` 表，以 LINE 提供的 `webhookEventId` 為主鍵。handler 進入時先嘗試 insert，違反唯一約束即代表已處理過，直接回 200 不做事。這是真正的冪等閘門，比「把每個操作寫成冪等」更可靠且更好推理。

→ 設計寫入 [06-LINE整合設計](06-LINE整合設計.md)、schema 寫入 [04-資料模型](04-資料模型.md)

### G2 — 呼叫端速率限制與配額 🔴 Phase 1

**問題**：初版只限制**我們對 LINE** 的速率（100 req/s），完全沒限制**呼叫端對我們**。一個有 bug 的 client 每秒打 100 次 `target: ALL`，可以在幾分鐘內燒光整月訊息額度。PRD 的 S4「停用失控來源」是**事後**補救，代價已經付出去了。

**處置**：兩層防護

| 層 | 機制 |
|---|---|
| 速率 | per-client token bucket（預設 60 req/min），超過回 `429 RATE_LIMITED` 並帶 `Retry-After` |
| 配額 | per-client 每日訊息則數上限（`client.daily_message_quota`，null = 不限）。以「實際收件人數」計，不是請求數 |

配額用完回 `429 CLIENT_QUOTA_EXCEEDED`。OWNER client 預設不限。

**現況**：兩層都已實作 —— 速率在 `auth/RateLimitFilter`（**每實例計數**，多實例會失效，見 G12）、
配額在 `NotificationService.enforceDailyQuota`（以收件人數計、滾動 24 小時窗口）。

→ 設計寫入 [03-權限與認證設計](03-權限與認證設計.md)

### G3 — Correlation ID 與結構化日誌 🔴 Phase 1

**問題**：一個請求跨越「HTTP 執行緒 → async 執行緒 → N 次 LINE API 呼叫 → 可能還有 redriver 在別的時間重試」。沒有貫穿的識別碼，出事時無法把 log 串起來。初版只寫「結構化日誌」，太模糊。

**處置**：

- `RequestIdFilter` 產生（或沿用呼叫端傳來的 `X-Request-Id`）並放進 MDC
- `@Async` 執行緒用 `TaskDecorator` 把 MDC 複製過去（**這步很容易漏，漏了非同步段就沒有 id**）
- 所有 log 固定帶 `requestId`、`clientId`、`notificationId`、`batchNo`
- LINE 回應的 `x-line-request-id` 一律記錄並存進 `notification_delivery`，這是跟 LINE 客服對帳的唯一憑據
- 回應 header 回傳 `X-Request-Id`，讓呼叫端能報給我們

### G4 — Circuit Breaker 🔴 Phase 1

**問題**：LINE API 掛掉或憑證失效時，初版行為是「每批重試 5 次然後標 FAILED」。結果是佇列裡所有東西在幾分鐘內全部燒成 FAILED，且對 LINE 打出大量無用請求。恢復後這些通知也不會自動補送。

**處置**：Resilience4j `CircuitBreaker` 包住 LINE API 呼叫。連續失敗達閾值後開路，派送器暫停取件（delivery 留在 PENDING 並延後 `next_attempt_at`），半開狀態試探恢復。**關鍵差異**：斷路期間的批次是「延後」不是「失敗」，服務恢復後 redriver 會自動補送。

同時區分錯誤類型：`401/403`（憑證問題）與 `429 monthly limit`（額度耗盡）是**終局失敗**不重試也不計入斷路器；`5xx`、逾時、`429 rate limit` 才進重試與斷路統計。

### G5 — `lineMessages` 逃生門的濫用風險 🔴 Phase 1

**問題**：初版設計 `lineMessages` 讓呼叫端直接傳 LINE message object。這代表一組外洩的 client 金鑰可以發送帶 `uri` action 的 template / flex message —— **等於一個釣魚訊息發送器**，而且訊息來自使用者信任的官方帳號。

**處置**：把逃生門本身變成一個 scope

- 新增 scope `notify:raw`，**預設不給任何 client**，只有 OWNER 能授予
- 沒有 `notify:raw` 的 client 送 `lineMessages` → `403 SCOPE_DENIED`
- 所有訊息內容（含純文字裡內嵌的連結）中的 http(s) 連結，網域需通過白名單（`app.allowed-uri-hosts`），不符合直接 400。
  白名單為空代表「不允許任何外部連結」—— 安全的預設值，正式環境務必設定 `APP_ALLOWED_URI_HOSTS`
- 一般 client 只能用 `message` 簡易模式（純文字），無法夾帶連結動作

### G6 — `APP_SECRET_ENC_KEY` 的災難場景 🔴 Phase 1（文件）

**問題**：這把 key 加密所有 client secret。初版只寫「外洩需輪替」，但**遺失**的後果更嚴重且沒提：key 一旦遺失，DB 裡所有 client secret 都無法解密，**所有呼叫端一起失效，且無法救回**，只能全部重新發金鑰。

**處置**：

- key 與 DB **分開備份**（放一起等於沒加密）
- `operations.md` 明確寫出兩套程序：**外洩** → 產新 key、以 `secret_key_version` 雙 key 並存期重加密、撤銷舊 key；**遺失** → 承認無法復原，走全體重發流程
- schema 預留 `secret_key_version` 讓輪替不需停機
- 啟動時 fail-fast 檢查 key 存在且解碼後恰為 32 bytes

**現況 ✅ 已實作**，但設定形狀與原規劃不同：不是單一 `APP_SECRET_ENC_KEY`，而是
`app.crypto.keys` 這個 **版本號 → base64 金鑰的 map**（`config/CryptoProperties`），
讓雙 key 並存期不必改程式。`config/CryptoConfig` 在啟動時做 fail-fast：金鑰未設定、
長度非 32 bytes、或加解密 round-trip 不符都直接拋 `IllegalStateException`。
`client.secret_key_version`（`client/Client`）記錄每筆 secret 用的是哪個版本。

### G7 — 資料保留政策 🔴 Phase 1

**問題**：`notification`（含 JSONB payload）與 `notification_delivery`（含 `TEXT[]` 收件人陣列）會**無限增長**。一個活躍系統跑一年後，這兩張表會主宰整個 DB 大小，備份與查詢都會變慢。初版只提到清 `request_nonce`。

**處置**：明確的保留期與清理排程

| 資料 | 保留 | 動作 |
|---|---|---|
| `request_nonce` | 10 分鐘 | 每 5 分鐘刪除過期 |
| `enrollment_token` | 24 小時 | 每日刪除過期或已消費 |
| `notification_delivery` | 90 天 | 每日刪除；保留前先把統計回寫到 `notification` |
| `notification` | 400 天 | 每日刪除；`payload` 在 90 天後先清空（保留 metadata） |
| `audit_log` | 2 年 | 不自動刪，滿期後人工歸檔 |
| `webhook_event` | 30 天 | 每日刪除（LINE 重送窗口遠短於此） |

清理任務走 `@Scheduled`，分批 DELETE（每批上限 10000 列）避免長交易鎖表。

**現況（部分實作）**：

| 資料 | 清理排程 |
|---|---|
| `request_nonce` | ✅ `NonceStore.purgeExpired` |
| `webhook_event` | ✅ `WebhookEventGuard.purgeExpired` |
| `api_monitor_run` / `api_monitor_seen_item` | ✅ `ApiMonitorSweeper` |
| `notification` / `notification_delivery` | ⏳ **沒有任何排程會清**。`NotificationRepository.clearPayloadsBefore` / `.deleteByCreatedAtBefore` 與 `NotificationDeliveryRepository.deleteByCreatedAtBefore` 都已實作但**無人呼叫**，這兩張表目前會無限增長 |
| `enrollment_token` / `audit_log` | ⏳ 表存在但零讀寫（見 §3.1），也就沒有清理需求 |

上表列的三支排程**都需要 ShedLock 才能多實例安全**（見 G12）。

### G8 — 稽核紀錄 🟡 Phase 1（表）／Phase 2（介面）

**問題**：完全沒有稽核設計。「誰把某個 client 的 scope 加上 `notify:all`」「誰把某人標記成 owner」「哪個 IP 兌換了 enrollment token」——這些都是安全事件，事後無法回答等於無法追責。

**處置**：`audit_log` 表，記錄 `actor`（client id 或 line user id 或 SYSTEM）、`action`、`target_type`、`target_id`、`detail` JSONB、`ip`、`occurred_at`。Phase 1 先落表（寫入點：client 建立/停用/scope 變更、owner 標記變更、enrollment 發放與兌換、client secret 重設），Phase 2 在 Admin 提供查詢。

稽核寫入**不得阻擋主流程**——寫失敗只記 error log。

**現況 ⏳ 尚未實作**：`audit_log` 表已由 `V1__init.sql` 建立，但 `audit/` 套件只有 `.gitkeep`，
全 codebase 對這張表零讀寫。上述所有寫入點都不存在，稽核紀錄實際上是空的。

### G9 — 指標與自我監控 🟡 Phase 1（指標）／Phase 2（告警）

**問題**：只有 `/actuator/health`。無法回答「現在佇列積了多少」「LINE 呼叫失敗率多少」「這個月額度還剩多少」。

**處置**：Micrometer 指標

| 指標 | 型別 | 標籤 |
|---|---|---|
| `notification.submitted` | Counter | `target_type`, `client_id` |
| `notification.recipients` | Counter | `target_type` |
| `delivery.batch.sent` | Counter | `status` |
| `delivery.batch.duration` | Timer | — |
| `delivery.queue.depth` | Gauge | — （PENDING 數） |
| `delivery.queue.oldest_age` | Gauge | — （最舊 PENDING 的等待秒數，比 depth 更能反映卡住） |
| `line.api.call` | Timer | `endpoint`, `outcome` |
| `line.quota.remaining` | Gauge | — （每小時更新） |
| `circuitbreaker.state` | Gauge | — |

**Health check 要分層**：`liveness` 只看 JVM，`readiness` 看 DB。**LINE API 不可達不能算 unhealthy**——否則 LINE 端故障會導致容器被反覆重啟，反而讓已排隊的通知永遠送不出去。LINE 狀態放 `/actuator/health` 的 `details` 供人判讀即可。

Phase 2 加自我監控告警（佇列積壓 / 失敗率 / 額度過低 → 發 LINE 給 OWNER）。**注意遞迴風險**：告警發送失敗時不得再產生告警，需走獨立的直接 push 路徑並加抑制。

**現況 ⏳ 上表指標全部尚未實作**：

- **零自訂 metric** —— `MeterRegistry` / `Counter.` / `@Timed` 在 `server/` 全域 grep 命中 0。
  `micrometer-registry-prometheus` 有在依賴裡，但只有 JVM／Tomcat 等內建指標。
- `management.endpoints.web.exposure.include` 開了 `health,info,prometheus`，
  但 `SecurityConfig.PUBLIC_PATHS` 只放行 `/actuator/health*`，其餘 `denyAll()`
  → **`/actuator/prometheus` 與 `/actuator/info` 對外 403，抓不到指標**。
- 佇列深度所需的 `countPending()` / `findOldestPendingAt()` 已實作但**無人呼叫**。
- **無告警**：這是一個通知服務，但它自己掛掉沒人會被通知。
- log 為純文字 pattern、無輪替上限、無集中收集；`/actuator/info` 未啟用 `build-info`，
  沒有版本／commit 資訊。

### G10 — 訊息優先級 🟡 Phase 1 欄位、Phase 2 分流

**問題**：單一 FIFO 佇列會有 head-of-line blocking。對 1200 人的全體公告切成 3 批排在前面，後面一則「伺服器當機」的緊急告警就要等前面送完。

**處置**：`notification_delivery` 加 `priority SMALLINT`（0 = 高，5 = 一般，9 = 低）。redriver 取件時 `ORDER BY priority, next_attempt_at`。Phase 1 先加欄位並讓 `target=ALL` 自動降為 9、`target=OWNER` 提為 0；Phase 2 再開放 API 指定。加欄位成本近乎零，事後補很麻煩。

### G11 — Admin UI 的認證方式 🟡 Phase 2（但現在要定）

**問題**：初版完全沒提。HMAC 是機器對機器的方案，人不可能手算簽章。如果另建一套帳號密碼系統，就多出密碼雜湊、重設流程、鎖定策略、2FA 等一整套要維護的東西。

**原處置（[ADR-0009](adr/0009-Admin-認證採-LINE-Login.md)）**：用 LINE Login (OAuth 2.0)，管理者用自己的 LINE 帳號登入，callback 取得 LINE User ID，系統查 `line_user.is_owner`，是才發 session。

**⚠️ 這個決策已被 [ADR-0011](adr/0011-管理介面採帳密登入.md) 取代，且從未實作。**
實際採用的是**帳號密碼 form login + session + CSRF**：`admin/AdminSecurityConfig` 定義
`/admin/**` 的 session-based 鏈，`admin/AdminAuthProperties` 提供憑證來源，前端從
`XSRF-TOKEN` cookie 讀 token 填 `X-XSRF-TOKEN` header。沒有 LINE Login channel。

（`Docs/plan/adr/0009-*.md` 與 `adr/README.md` 目前仍把 ADR-0009 標為 Accepted，
狀態應更正為 Superseded —— 該修正屬於 ADR 文件本身，不在本文件範圍。）

不變的是這條分界：`/admin/**` 走 session-based 鏈，`/api/v1/**` 走 HMAC 無狀態鏈，
**完全分離**（兩條 `SecurityFilterChain`，用 `securityMatcher` 分流）。這點實作與規劃一致。

### G12 — 多實例的排程重複執行 🟡 加第二個實例前必須解決

**問題**：派送取件用 `SKIP LOCKED` 已經是多實例安全的。但其他 `@Scheduled` 任務——資料清理、每日 Profile 校正、額度輪詢——在多實例會**同時執行**，造成重複的 LINE API 呼叫與競態。

**處置**：Phase 1 單實例，先在 `docker-compose.yml` 與文件明確標註「本設定僅支援單一 app 實例」。要水平擴充前導入 ShedLock（PostgreSQL LockProvider，與現有 DB 共用，不增加基礎設施）。

**現況**：單實例假設**沒有任何機制強制**。ShedLock ⏳ 尚未導入。多實例會壞掉的：

| 項目 | 問題 |
|---|---|
| `ProfileSyncService.reconcileDaily` | 重複的 LINE API 呼叫 |
| `WebhookEventGuard.purgeExpired` | 重複刪除（冪等，只是浪費） |
| `ApiMonitorSweeper` | 同上 |
| `NonceStore.purgeExpired` | 同上 |
| `auth/RateLimitFilter` | per-instance 計數，N 個實例等於放寬 N 倍 |
| Resilience4j RateLimiter / CircuitBreaker | 狀態在 JVM 內，不跨實例 |

**例外（已經是多實例安全的）**：`DeliveryStore.claim` 與 `ApiMonitorStore.claim`——
兩條管線的 `FOR UPDATE SKIP LOCKED` + 租約本身就撐得住多實例（見 §2.2、§2.3）。

### G13 — 內容大小與 PII 🟡 Phase 1

**問題**：兩個小洞。(a) LINE 文字訊息有 5000 字元上限，超過會被 LINE 退回——應該在我們這層就擋掉並給清楚錯誤。(b) 通知內容原文存進 `notification.payload`，若呼叫端送了機密資料（密碼、token、個資），DB 外洩就是內容外洩。

**處置**：(a) DTO 驗證 text ≤ 5000 字元、request body ≤ 64KB。(b) `api-contract.md` 明確聲明「通知內容會保存 90 天，請勿傳送機密資料」；並提供 `options.persistPayload: false` 讓敏感呼叫端選擇不落地內容（只存 metadata 與內容 hash）。

### G14 — 測試環境隔離 🟢 Phase 1（文件）

**問題**：只規劃了 dev/prod。但「dev 環境測發送」用的是**同一個 LINE Official Account**，測試訊息會發到真實使用者手機上。

**處置**：文件明確要求另建一個測試用 LINE Official Account 與 Channel，dev profile 指向它。本機自動化測試一律用 `MockWebServer` 打樁，不碰真 LINE。

### G15 — 通知抑制／去重 🟢 Phase 2 候選

**問題**：監控類來源的典型行為是「同一個 alert 每分鐘重發直到解除」。使用者會被洗版，額度也被吃掉。

**處置**（Phase 2）：可選的抑制窗口——同一 client + 相同內容 hash 在 N 分鐘內只送第一則，後續回 `200` 附 `suppressed: true`。放 Phase 2 是因為它需要 client 端配合定義「相同」的語意，而 Phase 1 還沒有實際使用資料可以調參。

## 7. 演進路徑

| 現在的設計 | 為什麼現在夠 | 何時要換 | 換成什麼 |
|---|---|---|---|
| DB outbox ×2（派送 + 監控輪詢）+ `@Scheduled` 輪詢 | 單實例、量小、不想多養一個 broker；兩條管線共用同一套 `SKIP LOCKED` + 租約模式 | 需要每日數十萬則 | 保留 outbox 表，改由 Kafka/Rabbit 消費 |
| 單一 app 實例 | 通知量小，重啟秒級 | 需要零停機部署 | 導入 ShedLock（G12）後可水平擴充。取件層已經撐得住，要補的是其他 `@Scheduled`、`RateLimitFilter` 與 Resilience4j 狀態 |
| `notification.scheduled_at` 排程發送（V3） | 排程數量少，靠既有輪詢就能撿 | 需要動態增刪大量排程 | Quartz + JDBC JobStore（BOM 已含 starter） |
| 只支援 LINE | 目前只需要 LINE | 要加 Discord/Email | `NotificationChannel` 介面 + 各管道實作；`notification` 表加 `channel` 欄位 |
| 手寫原生 JS 後台（見 §8） | 內部使用、功能導向、零建置鏈 = 零前端套件供應鏈 | `app.js` 再長下去（目前約 2,630 行）或需要多人並行開發 | 屆時開新 ADR；現況見 ADR-0012 |

**刻意不預先抽象的地方**：`NotificationChannel` 介面現在**不做**。只有一個實作的介面是負擔不是彈性；真要加第二個管道時，重構成本遠低於現在猜錯抽象邊界的成本。

## 8. 管理後台架構（實況）

管理後台不是獨立的前端專案，而是**由 server 直接服務的靜態檔**。

### 8.1 檔案位置與規模

| 檔案 | 行數 | 說明 |
|---|---|---|
| `server/src/main/resources/static/admin/index.html` | 804 | 單頁殼層，含登入設定與監控管理對話框 |
| `static/admin/login.html` | 80 | 登入頁 |
| `static/admin/assets/app.js` | 2630 | 全部邏輯，單一 IIFE |
| `static/admin/assets/app.css` | 889 | 手寫 CSS |
| `admin/AdminService.java` | 1183 | 後端主要邏輯 |
| `admin/AdminDto.java` | 911 | 請求／回應 DTO |
| `admin/AdminController.java` | 309 | `/admin/api/**` 共 30 個方法映射 |

### 8.2 前端技術決策

| 面向 | 做法 |
|---|---|
| 框架 | **無**。純原生 JS，零 `import` / `require`、零 npm 套件、零 CDN 引用 |
| build step | **完全沒有**。無 `package.json`、無 bundler、無 transpile、無 minify。檔案原樣放進 jar |
| 路由 | **hash 路由**。`VIEWS` 常數（8 個 view）+ `show(view)` 切 `hidden` 屬性，監聽 `hashchange`，預設 `#dashboard`，未知 hash fallback 回 dashboard。無 History API、無巢狀路由、無路由參數 |
| 狀態管理 | 一個 module-scope `state` 物件 + 數個 module 變數。**無響應式綁定** —— 改資料後手動呼叫 `renderClients()` / `renderMonitors()` 重繪 |
| DOM 建構 | 全部走 `document.createElement` + `textContent`（helper `el(tag, cls, text)`）。**全檔零 `innerHTML`**，包含把第三方 API 回應畫成樹的時候 |
| CSS | 單一手寫檔，CSS 自訂屬性（`--c-*` / `--sp-*` / `--radius` / `--motion`）當設計 token。**刻意不掛 Google Fonts CDN**（後台掛外部來源＝多一個可被竄改的點），字體用系統堆疊 |
| 認證 | Session cookie；寫入請求從 `XSRF-TOKEN` cookie 讀 token 填 `X-XSRF-TOKEN` header。`fetch` 用 `credentials: 'same-origin'` + `redirect: 'error'`，session 過期時 302 會讓 fetch 直接 throw → 導向 `/admin/login.html` |
| 回應格式 | 統一信封 `{ success, data, error }`，與 `/api/v1/**` 一致 |
| 持久化 | `localStorage` 唯一用途是記住每個 `<dialog>` 被拖曳後的寬度 |
| 瀏覽器需求 | `<dialog>` + `showModal()`、Pointer Events、`replaceChildren()`、CSS `color-mix()`、`:has()`、`backdrop-filter`、`100dvh`。**無 polyfill、無 fallback** |

**為什麼值得記在架構文件裡**：這代表整個專案只有**一個 build 單位**（`server/` 的 Maven），
本機開發與 CI 都不需要 Node。代價是後台的可維護性完全靠 `app.js` 的自律，
沒有型別檢查、沒有模組邊界、沒有元件測試。
