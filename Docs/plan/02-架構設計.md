## 2. 請求流程

### 2.1 通知發送（同步段）

```
1. HmacAuthFilter      驗時間戳 → 驗 nonce → 查 client → 常數時間比對簽章 → 建 ClientPrincipal
2. RateLimitFilter     檢查該 client 的 per-client 速率與每日配額           【缺口 G2】
3. Controller          DTO 驗證（text 長度、userIds 格式與數量、message 數上限）
4. TargetResolver      依 target.type 檢查 scope → 解析出收件人清單
5. QuotaGuard          若 target=ALL，查 LINE 月額度餘量，不足直接 429
6. @Transactional      寫 notification (QUEUED) + 切批寫 notification_delivery
7. 回 202 + notificationId
```

### 2.2 通知派送（非同步段）

```
交易提交後 → NotificationDispatcher(@Async)
   → 逐批呼叫 MulticastBatchSender
      → RateLimiter (100 req/s) → CircuitBreaker → LINE multicast API
      → 更新 delivery 狀態 + line_request_id
   → 回寫 notification 計數與最終狀態

失敗批次留在 PENDING + next_attempt_at
   → DeliveryRedriver (@Scheduled 30s, SELECT FOR UPDATE SKIP LOCKED) 重新取件
```

詳見 [07-非同步與可靠性設計](07-非同步與可靠性設計.md)。

## 3. 模組邊界

| 套件 | 職責 | 不該做的事 |
|---|---|---|
| `config` | Spring 組態、`@ConfigurationProperties`、啟動檢查 | 不放業務邏輯 |
| `auth` | HMAC 驗簽、nonce、secret 加解密、`ClientPrincipal` | 不決定「能不能發給誰」（那是 notification 的事） |
| `client` | Client 實體、scope、狀態管理 | 不碰 LINE API |
| `lineuser` | LINE User 實體、Profile 同步、owner 標記 | 不決定發送邏輯 |
| `enrollment` | 一次性 token 發放與兌換 | 不直接回覆 LINE 訊息（交給 webhook） |
| `notification.api` | Controller、DTO、驗證 | 不直接呼叫 LINE API |
| `notification.domain` | 實體、Repository、狀態機 | 不含 HTTP 概念 |
| `notification.dispatch` | target 解析、分批、送出、重試 | 不做認證 |
| `webhook` | LINE 事件接收與指令路由 | 不寫複雜業務（委派給對應 service） |
| `audit` | 稽核事件記錄 | 不阻擋主流程 |
| `observability` | MDC/correlation id、Micrometer 指標、自我監控 | 不改變業務行為 |
| `common` | `ApiResponse`、`ErrorCode`、例外處理、ID 產生 | 不依賴其他業務套件 |

依賴方向：`api → dispatch → domain`，`auth` 與 `client` 互不依賴（`auth` 透過介面取得 client 資料）。`common` 被所有人依賴但不依賴任何人。

### 5.1 Jackson 版本衝突（必須處理）

Spring Boot 4.1.0 BOM **同時管理兩套 Jackson**：

| Bom | 版本 | 使用者 |
|---|---|---|
| `com.fasterxml.jackson:jackson-bom` | 2.21.4 | 舊 API（`com.fasterxml.jackson.*`） |
| `tools.jackson:jackson-bom` | 3.1.4 | Spring MVC 預設（`tools.jackson.*`） |

但 `line-bot-jackson:10.1.0` 明確依賴 `jackson-databind:2.22.0`。BOM 的版本管理會壓過 transitive 依賴，把它降成 2.21.4。

**處理**：`server/pom.xml` 的 `<properties>` 覆寫

```xml
<jackson-2-bom.version>2.22.0</jackson-2-bom.version>
```

兩套 Jackson 是不同 groupId 與 package，**可以共存**（LINE SDK 走 retrofit + 自己的 ObjectMapper，Spring MVC 走 Jackson 3），不需要排除任何一方。

詳見 [ADR-0008](adr/0008-鎖定-Spring-Boot-4.1-並覆寫-Jackson-2-版本.md)。

### 5.2 Spring Boot 4 的 autoconfiguration 模組拆分（T1 實測）

Spring Boot 4 把原本單一的 `spring-boot-autoconfigure` **拆成一堆技術別模組**：`spring-boot-flyway`、`spring-boot-jpa`、`spring-boot-data-jpa`、`spring-boot-security`、`spring-boot-jdbc`、`spring-boot-actuator`…

後果：**只加函式庫本身不會啟動對應的 auto-configuration。**

實測踩到的：`flyway-core` 在 classpath 上，但 `FlywayAutoConfiguration` 住在 `org.springframework.boot:spring-boot-flyway`。少了它，應用**正常啟動、日誌毫無 Flyway 訊息、資料庫一張表都沒有** —— 沒有任何錯誤提示。

```xml
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-flyway</artifactId>   <!-- 這行才是 auto-config -->
</dependency>
```

`starter-*` 系列會自己帶對應模組（例如 `spring-boot-starter-data-jpa` 帶 `spring-boot-data-jpa`），所以問題只出在「直接依賴第三方函式庫」的情況。日後要加 Quartz、Liquibase、Redis 等等時要記得檢查。

### 5.3 依賴座標修正（T1 實測）

## 6. 架構補強：資深架構師審查

以下是對初版設計的缺口盤點。**G1–G7 是 Phase 1 就會痛的，必須納入 MVP**；G8–G15 標註處置階段。

### G1 — Webhook 事件去重 🔴 Phase 1

**問題**：LINE 在 webhook 回應逾時或非 200 時會**重送同一事件**。初版設計只說「把 follow/unfollow 寫成 upsert 保證冪等」，但這不夠——`FollowEvent` 還會**發歡迎訊息**，重送就會重複打招呼；`申請金鑰` 指令重送就會**發出兩個 enrollment token**。

**處置**：新增 `webhook_event` 表，以 LINE 提供的 `webhookEventId` 為主鍵。handler 進入時先嘗試 insert，違反唯一約束即代表已處理過，直接回 200 不做事。這是真正的冪等閘門，比「把每個操作寫成冪等」更可靠且更好推理。

→ 設計寫入 [06-LINE整合設計](06-LINE整合設計.md)、schema 寫入 [04-資料模型](04-資料模型.md)

### G2 — 呼叫端速率限制與配額 🔴 Phase 1

**問題**：初版只限制**我們對 LINE** 的速率（100 req/s），完全沒限制**呼叫端對我們**。一個有 bug 的 client 每秒打 100 次 `target: ALL`，可以在幾分鐘內燒光整月訊息額度。PRD 的 S4「停用失控來源」是**事後**補救，代價已經付出去了。

**處置**：兩層防護

| 層 | 機制 |
|---|---|
| 速率 | per-client token bucket（預設 60 req/min），超過回 `429 RATE_LIMITED` 並帶 `Retry-After` |
| 配額 | per-client 每日訊息則數上限（`client.daily_message_quota`，null = 不限）。以「實際收件人數」計，不是請求數 |

配額用完回 `429 CLIENT_QUOTA_EXCEEDED`。OWNER client 預設不限。

→ 設計寫入 [03-權限與認證設計](03-權限與認證設計.md)

### G3 — Correlation ID 與結構化日誌 🔴 Phase 1

**問題**：一個請求跨越「HTTP 執行緒 → async 執行緒 → N 次 LINE API 呼叫 → 可能還有 redriver 在別的時間重試」。沒有貫穿的識別碼，出事時無法把 log 串起來。初版只寫「結構化日誌」，太模糊。

**處置**：

- `RequestIdFilter` 產生（或沿用呼叫端傳來的 `X-Request-Id`）並放進 MDC
- `@Async` 執行緒用 `TaskDecorator` 把 MDC 複製過去（**這步很容易漏，漏了非同步段就沒有 id**）
- 所有 log 固定帶 `requestId`、`clientId`、`notificationId`、`batchNo`
- LINE 回應的 `x-line-request-id` 一律記錄並存進 `notification_delivery`，這是跟 LINE 客服對帳的唯一憑據
- 回應 header 回傳 `X-Request-Id`，讓呼叫端能報給我們

### G4 — Circuit Breaker 🔴 Phase 1

**問題**：LINE API 掛掉或憑證失效時，初版行為是「每批重試 5 次然後標 FAILED」。結果是佇列裡所有東西在幾分鐘內全部燒成 FAILED，且對 LINE 打出大量無用請求。恢復後這些通知也不會自動補送。

**處置**：Resilience4j `CircuitBreaker` 包住 LINE API 呼叫。連續失敗達閾值後開路，派送器暫停取件（delivery 留在 PENDING 並延後 `next_attempt_at`），半開狀態試探恢復。**關鍵差異**：斷路期間的批次是「延後」不是「失敗」，服務恢復後 redriver 會自動補送。

同時區分錯誤類型：`401/403`（憑證問題）與 `429 monthly limit`（額度耗盡）是**終局失敗**不重試也不計入斷路器；`5xx`、逾時、`429 rate limit` 才進重試與斷路統計。

### G5 — `lineMessages` 逃生門的濫用風險 🔴 Phase 1

**問題**：初版設計 `lineMessages` 讓呼叫端直接傳 LINE message object。這代表一組外洩的 client 金鑰可以發送帶 `uri` action 的 template / flex message —— **等於一個釣魚訊息發送器**，而且訊息來自使用者信任的官方帳號。

**處置**：把逃生門本身變成一個 scope

- 新增 scope `notify:raw`，**預設不給任何 client**，只有 OWNER 能授予
- 沒有 `notify:raw` 的 client 送 `lineMessages` → `403 SCOPE_DENIED`
- 所有訊息內容（含純文字裡內嵌的連結）中的 http(s) 連結，網域需通過白名單（`app.allowed-uri-hosts`），不符合直接 400。
  白名單為空代表「不允許任何外部連結」—— 安全的預設值，正式環境務必設定 `APP_ALLOWED_URI_HOSTS`
- 一般 client 只能用 `message` 簡易模式（純文字），無法夾帶連結動作

### G6 — `APP_SECRET_ENC_KEY` 的災難場景 🔴 Phase 1（文件）

**問題**：這把 key 加密所有 client secret。初版只寫「外洩需輪替」，但**遺失**的後果更嚴重且沒提：key 一旦遺失，DB 裡所有 client secret 都無法解密，**所有呼叫端一起失效，且無法救回**，只能全部重新發金鑰。

**處置**：

- key 與 DB **分開備份**（放一起等於沒加密）
- `operations.md` 明確寫出兩套程序：**外洩** → 產新 key、以 `secret_key_version` 雙 key 並存期重加密、撤銷舊 key；**遺失** → 承認無法復原，走全體重發流程
- schema 預留 `secret_key_version` 讓輪替不需停機
- 啟動時 fail-fast 檢查 key 存在且解碼後恰為 32 bytes

### G7 — 資料保留政策 🔴 Phase 1

**問題**：`notification`（含 JSONB payload）與 `notification_delivery`（含 `TEXT[]` 收件人陣列）會**無限增長**。一個活躍系統跑一年後，這兩張表會主宰整個 DB 大小，備份與查詢都會變慢。初版只提到清 `request_nonce`。

**處置**：明確的保留期與清理排程

| 資料 | 保留 | 動作 |
|---|---|---|
| `request_nonce` | 10 分鐘 | 每 5 分鐘刪除過期 |
| `enrollment_token` | 24 小時 | 每日刪除過期或已消費 |
| `notification_delivery` | 90 天 | 每日刪除；保留前先把統計回寫到 `notification` |
| `notification` | 400 天 | 每日刪除；`payload` 在 90 天後先清空（保留 metadata） |
| `audit_log` | 2 年 | 不自動刪，滿期後人工歸檔 |
| `webhook_event` | 30 天 | 每日刪除（LINE 重送窗口遠短於此） |

清理任務走 `@Scheduled`，分批 DELETE（每批上限 10000 列）避免長交易鎖表。

### G8 — 稽核紀錄 🟡 Phase 1（表）／Phase 2（介面）

**問題**：完全沒有稽核設計。「誰把某個 client 的 scope 加上 `notify:all`」「誰把某人標記成 owner」「哪個 IP 兌換了 enrollment token」——這些都是安全事件，事後無法回答等於無法追責。

**處置**：`audit_log` 表，記錄 `actor`（client id 或 line user id 或 SYSTEM）、`action`、`target_type`、`target_id`、`detail` JSONB、`ip`、`occurred_at`。Phase 1 先落表（寫入點：client 建立/停用/scope 變更、owner 標記變更、enrollment 發放與兌換、client secret 重設），Phase 2 在 Admin 提供查詢。

稽核寫入**不得阻擋主流程**——寫失敗只記 error log。

### G9 — 指標與自我監控 🟡 Phase 1（指標）／Phase 2（告警）

**問題**：只有 `/actuator/health`。無法回答「現在佇列積了多少」「LINE 呼叫失敗率多少」「這個月額度還剩多少」。

**處置**：Micrometer 指標

| 指標 | 型別 | 標籤 |
|---|---|---|
| `notification.submitted` | Counter | `target_type`, `client_id` |
| `notification.recipients` | Counter | `target_type` |
| `delivery.batch.sent` | Counter | `status` |
| `delivery.batch.duration` | Timer | — |
| `delivery.queue.depth` | Gauge | — （PENDING 數） |
| `delivery.queue.oldest_age` | Gauge | — （最舊 PENDING 的等待秒數，比 depth 更能反映卡住） |
| `line.api.call` | Timer | `endpoint`, `outcome` |
| `line.quota.remaining` | Gauge | — （每小時更新） |
| `circuitbreaker.state` | Gauge | — |

**Health check 要分層**：`liveness` 只看 JVM，`readiness` 看 DB。**LINE API 不可達不能算 unhealthy**——否則 LINE 端故障會導致容器被反覆重啟，反而讓已排隊的通知永遠送不出去。LINE 狀態放 `/actuator/health` 的 `details` 供人判讀即可。

Phase 2 加自我監控告警（佇列積壓 / 失敗率 / 額度過低 → 發 LINE 給 OWNER）。**注意遞迴風險**：告警發送失敗時不得再產生告警，需走獨立的直接 push 路徑並加抑制。

### G10 — 訊息優先級 🟡 Phase 1 欄位、Phase 2 分流

**問題**：單一 FIFO 佇列會有 head-of-line blocking。對 1200 人的全體公告切成 3 批排在前面，後面一則「伺服器當機」的緊急告警就要等前面送完。

**處置**：`notification_delivery` 加 `priority SMALLINT`（0 = 高，5 = 一般，9 = 低）。redriver 取件時 `ORDER BY priority, next_attempt_at`。Phase 1 先加欄位並讓 `target=ALL` 自動降為 9、`target=OWNER` 提為 0；Phase 2 再開放 API 指定。加欄位成本近乎零，事後補很麻煩。

### G11 — Admin UI 的認證方式 🟡 Phase 2（但現在要定）

**問題**：初版完全沒提。HMAC 是機器對機器的方案，人不可能手算簽章。如果另建一套帳號密碼系統，就多出密碼雜湊、重設流程、鎖定策略、2FA 等一整套要維護的東西。

**處置**：**用 LINE Login (OAuth 2.0)**。管理者用自己的 LINE 帳號登入，callback 取得 LINE User ID，系統查 `line_user.is_owner`，是才發 session。

好處：不用自建帳密系統、不用管密碼、身分與 `line_user` 表天然對齊、要加管理者只要標記 `is_owner`。

代價：需在 LINE Developers 額外建一個 LINE Login channel。

實作時 `/admin/**` 走 Spring Security 的 session-based 鏈，與 `/api/v1/**` 的 HMAC 無狀態鏈**完全分離**（兩條 `SecurityFilterChain`，用 `securityMatcher` 分流）。這條分界現在就要在 `SecurityConfig` 預留好。

### G12 — 多實例的排程重複執行 🟡 加第二個實例前必須解決

**問題**：`DeliveryRedriver` 用 `SKIP LOCKED` 已經是多實例安全的。但其他 `@Scheduled` 任務——資料清理、每日 Profile 校正、額度輪詢——在多實例會**同時執行**，造成重複的 LINE API 呼叫與競態。

**處置**：Phase 1 單實例，先在 `docker-compose.yml` 與文件明確標註「本設定僅支援單一 app 實例」。要水平擴充前導入 ShedLock（PostgreSQL LockProvider，與現有 DB 共用，不增加基礎設施）。

### G13 — 內容大小與 PII 🟡 Phase 1

**問題**：兩個小洞。(a) LINE 文字訊息有 5000 字元上限，超過會被 LINE 退回——應該在我們這層就擋掉並給清楚錯誤。(b) 通知內容原文存進 `notification.payload`，若呼叫端送了機密資料（密碼、token、個資），DB 外洩就是內容外洩。

**處置**：(a) DTO 驗證 text ≤ 5000 字元、request body ≤ 64KB。(b) `api-contract.md` 明確聲明「通知內容會保存 90 天，請勿傳送機密資料」；並提供 `options.persistPayload: false` 讓敏感呼叫端選擇不落地內容（只存 metadata 與內容 hash）。

### G14 — 測試環境隔離 🟢 Phase 1（文件）

**問題**：只規劃了 dev/prod。但「dev 環境測發送」用的是**同一個 LINE Official Account**，測試訊息會發到真實使用者手機上。

**處置**：文件明確要求另建一個測試用 LINE Official Account 與 Channel，dev profile 指向它。本機自動化測試一律用 `MockWebServer` 打樁，不碰真 LINE。

### G15 — 通知抑制／去重 🟢 Phase 2 候選

**問題**：監控類來源的典型行為是「同一個 alert 每分鐘重發直到解除」。使用者會被洗版，額度也被吃掉。

**處置**（Phase 2）：可選的抑制窗口——同一 client + 相同內容 hash 在 N 分鐘內只送第一則，後續回 `200` 附 `suppressed: true`。放 Phase 2 是因為它需要 client 端配合定義「相同」的語意，而 Phase 1 還沒有實際使用資料可以調參。

## 7. 演進路徑

| 現在的設計 | 為什麼現在夠 | 何時要換 | 換成什麼 |
|---|---|---|---|
| DB outbox + `@Async` | 單實例、量小、不想多養一個 broker | 需要多實例或每日數十萬則 | 保留 outbox 表，改由 Kafka/Rabbit 消費 |
| 單一 app 實例 | 通知量小，重啟秒級 | 需要零停機部署 | 導入 ShedLock（G12）後可水平擴充 |
| `@Scheduled` 排程通知（P3） | 排程數量少 | 需要動態增刪大量排程 | Quartz + JDBC JobStore（BOM 已含 starter） |
| 只支援 LINE | 目前只需要 LINE | 要加 Discord/Email | `NotificationChannel` 介面 + 各管道實作；`notification` 表加 `channel` 欄位 |
| Ant Design 後台 | 內部使用，功能導向 | 要給外部使用者用 | 屆時再評估，不預先設計 |

**刻意不預先抽象的地方**：`NotificationChannel` 介面現在**不做**。只有一個實作的介面是負擔不是彈性；真要加第二個管道時，重構成本遠低於現在猜錯抽象邊界的成本。
