## 2. `line_user`

Bot 好友。所有發送的最終依據都是這張表的 `line_user_id`。

```sql
CREATE TABLE line_user (
    line_user_id       VARCHAR(64)  PRIMARY KEY,          -- U[0-9a-f]{32}
    display_name       VARCHAR(200),
    picture_url        TEXT,
    status_message     TEXT,
    language           VARCHAR(16),
    is_owner           BOOLEAN      NOT NULL DEFAULT false,
    status             VARCHAR(16)  NOT NULL,             -- ACTIVE | BLOCKED
    followed_at        TIMESTAMPTZ,
    unfollowed_at      TIMESTAMPTZ,
    profile_synced_at  TIMESTAMPTZ,
    created_at         TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at         TIMESTAMPTZ  NOT NULL DEFAULT now(),
    CONSTRAINT line_user_status_chk CHECK (status IN ('ACTIVE','BLOCKED'))
);

CREATE INDEX idx_line_user_active  ON line_user (line_user_id) WHERE status = 'ACTIVE';
CREATE INDEX idx_line_user_owner   ON line_user (line_user_id) WHERE is_owner AND status = 'ACTIVE';
```

**設計說明**

- 用 LINE 給的 `line_user_id` 當主鍵而非代理鍵。它本來就是穩定且唯一的外部識別碼，多一層代理鍵只會讓每次發送都要多做一次 join
- 兩個 **partial index** 直接對應最熱的兩個查詢：`target: ALL`（撈所有 ACTIVE）與 `target: OWNER`（撈 owner）。partial index 只索引符合條件的列，比全表索引小得多
- `display_name` 等 profile 欄位可為 null——LINE Profile API 可能暫時失敗，此時先建立 user 記錄再背景補齊，不阻擋 follow 事件處理
- `status` 只有兩個值。刻意不加 `DELETED`：LINE 端沒有可靠的「帳號已刪除」事件，多一個猜測性的狀態只會製造不確定
- **`is_owner` 在 entity 端叫 `owner`**（`lineuser/LineUser.java`）。JPQL 與衍生查詢要寫 `owner`（例如 `findByOwnerTrueAndStatus`），原生 SQL 與索引 `idx_line_user_owner` 用的才是 `is_owner`

## 3. `client`

呼叫端憑證。

```sql
CREATE TABLE client (
    id                    BIGSERIAL    PRIMARY KEY,
    client_id             VARCHAR(64)  NOT NULL UNIQUE,      -- cli_xxxxxxxxxxxxxxxxxxxx
    name                  VARCHAR(100) NOT NULL,
    secret_ciphertext     BYTEA        NOT NULL,             -- AES-256-GCM 密文 + tag
    secret_iv             BYTEA        NOT NULL,             -- 12 bytes
    secret_key_version    INT          NOT NULL DEFAULT 1,
    bound_line_user_id    VARCHAR(64)  REFERENCES line_user(line_user_id),
    status                VARCHAR(16)  NOT NULL,             -- ACTIVE | DISABLED | REVOKED
    rate_limit_per_min    INT,                               -- null = 用系統預設
    daily_message_quota   INT,                               -- null = 不限
    created_at            TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at            TIMESTAMPTZ  NOT NULL DEFAULT now(),
    last_used_at          TIMESTAMPTZ,
    CONSTRAINT client_status_chk CHECK (status IN ('ACTIVE','DISABLED','REVOKED'))
);

-- V2 新增：請求未帶 target 時套用的預設對象
ALTER TABLE client
    ADD COLUMN default_target_type     VARCHAR(16),
    ADD COLUMN default_target_user_ids TEXT[];

ALTER TABLE client ADD CONSTRAINT client_default_target_type_chk CHECK (
    default_target_type IS NULL
    OR default_target_type IN ('SELF','OWNER','USER','ALL')
);

-- USER 必須帶 1..500 筆名單；其餘型別必須沒有名單
ALTER TABLE client ADD CONSTRAINT client_default_target_users_chk CHECK (
    (default_target_type = 'USER'
     AND default_target_user_ids IS NOT NULL
     AND array_length(default_target_user_ids, 1) BETWEEN 1 AND 500)
    OR (default_target_type IS DISTINCT FROM 'USER'
        AND (default_target_user_ids IS NULL
             OR array_length(default_target_user_ids, 1) IS NULL))
);

-- 一個 LINE user 同時只能有一組有效金鑰
CREATE UNIQUE INDEX uq_client_bound_active
    ON client (bound_line_user_id)
    WHERE status = 'ACTIVE' AND bound_line_user_id IS NOT NULL;

CREATE INDEX idx_client_lookup ON client (client_id) WHERE status = 'ACTIVE';
```

**設計說明**

- `secret_ciphertext` 是**加密**不是雜湊。理由見 [03 §3.1](03-權限與認證設計.md#31-為什麼不能雜湊)。AES-256-GCM，**AAD = `client_id`**
- **partial unique index** `uq_client_bound_active` 是關鍵約束：讓「一人一把有效金鑰」由資料庫保證，而不是靠應用程式記得檢查。`REVOKED` 的舊金鑰仍留在表中（稽核需要），但不佔用唯一性
- `bound_line_user_id` 為 null 即 SERVICE client
- `status` 三態的語意差異：`DISABLED` 是**可回復**的暫停（例如失控時緊急拔掉），`REVOKED` 是**不可回復**的作廢（例如使用者重設金鑰）
- `default_target_type` / `default_target_user_ids`（**V2**）讓 `POST /api/v1/notifications` 的 `target` 變成選填：省略時套用這裡的預設。`default_target_type` 為 null 代表該 client 每次都必須自己指定 `target`。V2 同時做了一次回填——已擁有 `notify:owner` scope 的 client 一律設為 `'OWNER'`
- 「名單長度 ≤ 500」這一半只在 DB 的 `client_default_target_users_chk`，`Client.setDefaultTarget()` 的應用層驗證只擋「USER 必須有名單」
- ⚠️ `last_used_at` **實務上永遠是 NULL**：`ClientService.markUsed` 有實作但沒有任何呼叫點，因此無法用它識別該撤銷的閒置憑證

### `client_scope`

```sql
CREATE TABLE client_scope (
    client_id  BIGINT      NOT NULL REFERENCES client(id) ON DELETE CASCADE,
    scope      VARCHAR(32) NOT NULL,
    granted_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (client_id, scope),
    CONSTRAINT client_scope_chk CHECK (
        scope IN ('notify:self','notify:owner','notify:user','notify:all','notify:raw')
    )
);

CREATE INDEX idx_client_scope_by_scope ON client_scope (scope);
```

scope 用獨立表而非 `client` 上的陣列欄位——因為要記錄授予時間，且日後 Admin 要能查「哪些 client 有 `notify:all`」，`idx_client_scope_by_scope` 就是為這個反查建的。

**兩個實作面的注意事項**

- 這張表沒有獨立 entity，是 `Client.scopes` 的 `@ElementCollection(fetch = FetchType.EAGER)`。enum `Scope` 的常數是 `NOTIFY_SELF`…`NOTIFY_RAW`，經 `ScopeConverter`（`@Converter(autoApply = true)`）才存成 `notify:self` 這類字串
- ⚠️ **`granted_at` 目前沒有被映射**：`@ElementCollection` 只映射 `scope` 一欄，授予時間靠 DB `DEFAULT now()` 填值，應用層讀不到。見 [§13](#13-entity-與-schema-的落差與陷阱)
- ⚠️ **`client_scope.client_id` 與 `client.client_id` 同名但不同東西**：前者是指向 `client.id` 的 `BIGINT`，後者是對外公開的 `VARCHAR(64)` 識別碼 `cli_…`。寫原生 SQL 時極容易誤用

## 4. `enrollment_token`

自助申請金鑰的一次性 token。

> ⏳ **表存在，但功能尚未實作。** V1 建了這張表，卻沒有任何 `@Entity`、Repository 或原生 SQL 讀寫它——`enrollment/` 套件目前只有 `.gitkeep`，`WebhookCommandRouter` 的 `handleIssue` / `handleReset` 只回「即將開放（T6）」。全 codebase 唯一相關的是 `common/Ids.java` 的 `newEnrollmentToken()`（產生 token 字串）。下面的 schema 是既成事實（migration 已套用、不可修改），但**執行期完全沒被使用**。

```sql
CREATE TABLE enrollment_token (
    id            BIGSERIAL   PRIMARY KEY,
    token_hash    BYTEA       NOT NULL UNIQUE,     -- SHA-256(raw token)，32 bytes
    line_user_id  VARCHAR(64) NOT NULL REFERENCES line_user(line_user_id),
    purpose       VARCHAR(16) NOT NULL,            -- ISSUE | RESET
    expires_at    TIMESTAMPTZ NOT NULL,
    consumed_at   TIMESTAMPTZ,
    consumed_ip   INET,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT enrollment_purpose_chk CHECK (purpose IN ('ISSUE','RESET'))
);

CREATE INDEX idx_enrollment_cleanup ON enrollment_token (expires_at);
CREATE INDEX idx_enrollment_user    ON enrollment_token (line_user_id, created_at DESC);
```

**設計說明**

- **只存 hash 不存明文**。資料庫外洩時攻擊者拿不到可用的連結
- `consumed_at` 而非 boolean——需要知道「何時」被消費，這是安全事件
- `consumed_ip` 用 PostgreSQL 原生 `INET` 型別，支援 IPv4/IPv6 且可做網段查詢
- `idx_enrollment_user` 支援 [03 §5.4](03-權限與認證設計.md#54-濫用防護) 的「每小時最多 3 個」檢查

## 5. `notification`

一次發送請求。

```sql
CREATE TABLE notification (
    id                UUID         PRIMARY KEY,
    client_id         BIGINT       NOT NULL REFERENCES client(id),
    idempotency_key   VARCHAR(128),
    request_id        VARCHAR(64),                   -- 對應 log 的 correlation id
    target_type       VARCHAR(16)  NOT NULL,         -- SELF | OWNER | USER | ALL
    payload           JSONB,                         -- 送出的 LINE message objects
    payload_hash      BYTEA        NOT NULL,         -- SHA-256，payload 清空後仍可比對
    status            VARCHAR(16)  NOT NULL,         -- QUEUED|SENDING|SUCCEEDED|PARTIAL|FAILED
    recipient_count   INT          NOT NULL DEFAULT 0,
    success_count     INT          NOT NULL DEFAULT 0,
    failure_count     INT          NOT NULL DEFAULT 0,
    created_at        TIMESTAMPTZ  NOT NULL DEFAULT now(),
    started_at        TIMESTAMPTZ,
    finished_at       TIMESTAMPTZ,
    CONSTRAINT notification_target_chk CHECK (
        target_type IN ('SELF','OWNER','USER','ALL')
    ),
    CONSTRAINT notification_status_chk CHECK (
        status IN ('QUEUED','SENDING','SUCCEEDED','PARTIAL','FAILED')
    )
);

-- V3 新增：排程發送
ALTER TABLE notification ADD COLUMN scheduled_at TIMESTAMPTZ;

CREATE UNIQUE INDEX uq_notification_idem
    ON notification (client_id, idempotency_key)
    WHERE idempotency_key IS NOT NULL;

CREATE INDEX idx_notification_client_time ON notification (client_id, created_at DESC);
CREATE INDEX idx_notification_cleanup     ON notification (created_at);
CREATE INDEX idx_notification_stuck       ON notification (started_at) WHERE status = 'SENDING';
CREATE INDEX idx_notification_scheduled   ON notification (scheduled_at)
    WHERE scheduled_at IS NOT NULL AND status = 'QUEUED';
```

**設計說明**

- 主鍵用 **UUID** 而非序號——`notificationId` 會回傳給呼叫端，序號會洩漏系統總量與成長速率
- `idempotency_key` 的唯一性由 **partial unique index** 保證，範圍是 `(client_id, key)`——不同 client 用相同 key 不衝突
- `payload` 可為 null：對應 [02 缺口 G13](02-架構設計.md#g13--內容大小與-pii--phase-1) 的 `persistPayload: false` 選項，以及規劃中的內容清空
- `payload_hash` 即使 payload 被清空仍保留，支撐日後的去重功能（[缺口 G15](02-架構設計.md#g15--通知抑制去重--phase-2-候選)）與事後驗證
- 三個計數欄位是**去正規化**的。正確來源是 `notification_delivery`，這裡冗餘是為了讓查詢與清理後的統計保留不需要 join
- `scheduled_at`（**V3**）：null = 立即發送。**刻意不新增第二條派送路徑**——建立時把所有批次的 `notification_delivery.next_attempt_at` 設成排程時間，派送器原本的取件查詢就自然會等到那個時間點。`idx_notification_scheduled` 只服務後台「待發清單」這類查詢
- ⚠️ `idx_notification_stuck` 是為卡在 `SENDING` 的 redriver 建的，`NotificationRepository.findByStatusAndStartedAtBefore` 也寫好了，**但沒有任何排程呼叫它**——索引目前沒有讀者
- ⚠️ **`Notification` 不能用 `save()`**：主鍵是應用程式產生的 UUID，Spring Data 會走 `merge()` 造成靜默 UPDATE。寫入一律走 `NotificationRepository.insertIfAbsent`（原生 `INSERT … ON CONFLICT DO NOTHING`）

### 狀態機

```text
QUEUED ──→ SENDING ──┬──→ SUCCEEDED   （全批成功）
                     ├──→ PARTIAL     （部分批次失敗且已用盡重試）
                     └──→ FAILED      （全部失敗，或終局錯誤如額度耗盡）
```

`SENDING` 停留過久（例如 > 30 分鐘）代表有批次卡住，是監控告警的訊號之一。

## 6. `notification_delivery`

**同時是投遞明細與 outbox 工作項**。這是 [ADR-0007](adr/0007-非同步採-DB-outbox-而非訊息中介.md) 的核心。

```sql
CREATE TABLE notification_delivery (
    id               BIGSERIAL   PRIMARY KEY,
    notification_id  UUID        NOT NULL REFERENCES notification(id) ON DELETE CASCADE,
    batch_no         INT         NOT NULL,
    line_user_ids    TEXT[]      NOT NULL,          -- 一批最多 500
    recipient_count  INT         NOT NULL,
    retry_key        UUID        NOT NULL,          -- X-Line-Retry-Key，重試時不變
    priority         SMALLINT    NOT NULL DEFAULT 5,-- 0 高 … 9 低
    status           VARCHAR(16) NOT NULL,          -- PENDING | SENT | FAILED
    attempt_count    INT         NOT NULL DEFAULT 0,
    next_attempt_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    line_request_id  VARCHAR(64),                   -- x-line-request-id
    error_code       VARCHAR(48),
    error_message    TEXT,
    sent_at          TIMESTAMPTZ,
    created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (notification_id, batch_no),
    CONSTRAINT delivery_status_chk     CHECK (status IN ('PENDING','SENT','FAILED')),
    CONSTRAINT delivery_priority_chk   CHECK (priority BETWEEN 0 AND 9),
    CONSTRAINT delivery_batch_size_chk CHECK (recipient_count BETWEEN 1 AND 500)
);

-- 派送器取件的唯一查詢路徑
CREATE INDEX idx_delivery_pickup
    ON notification_delivery (priority, next_attempt_at)
    WHERE status = 'PENDING';

CREATE INDEX idx_delivery_cleanup ON notification_delivery (created_at);
```

**設計說明**

- **一列 = 一批（最多 500 人）**，不是一列一個收件人。1200 人只產生 3 列而非 1200 列。LINE multicast 本來就是批次語意，個別收件人的成功／失敗 LINE 也不會告訴我們（見 [06](06-LINE整合設計.md)），所以逐人一列只會浪費空間卻換不到資訊
- `line_user_ids TEXT[]` 用 PostgreSQL 原生陣列。SQLite 沒有這個型別——這是選 PostgreSQL 的理由之一
- `retry_key` 在建立時就固定，**重試時沿用同一把**。這讓 LINE 端能識別出是重試而非新訊息，避免使用者收到重複通知
- `idx_delivery_pickup` 是 partial + 複合索引，精確對應派送器的取件查詢：

  ```sql
  SELECT * FROM notification_delivery
   WHERE status = 'PENDING' AND next_attempt_at <= now()
   ORDER BY priority, next_attempt_at
   LIMIT 10
     FOR UPDATE SKIP LOCKED;
  ```

  `SKIP LOCKED` 讓多個工作者可以並行取件而不互相阻塞，也讓 Phase 1 寫的程式在未來多實例時不必改寫
- `priority` 現在就加（[缺口 G10](02-架構設計.md#g10--訊息優先級--phase-1-欄位phase-2-分流)）。Phase 1 由系統決定，值來自 `TargetType.priority()`：`OWNER` → 0、`SELF` / `USER` → 5、`ALL` → 9；Phase 2 再開放 API 指定。事後補欄位要改索引與所有查詢，成本高得多
- `next_attempt_at` 兼作**租約欄位**：取件時先推到未來，讓同一列不會被下一輪重複取走
- 重試上限 `MAX_ATTEMPTS = 5`（`notification/domain/NotificationDelivery.java`），指數退避 1／2／4／8 秒並帶 ±20% 抖動
- `error_message` 在 SQL 是無上限的 `TEXT`，但 `NotificationDelivery.truncate()` 在應用層截到 **1000 字元**——這個上限只存在於 Java 端，DB 沒有任何約束表達它

## 7. `request_nonce`

HMAC 重放防護。

```sql
CREATE TABLE request_nonce (
    nonce      VARCHAR(64) PRIMARY KEY,
    client_id  BIGINT      NOT NULL,
    seen_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_nonce_cleanup ON request_nonce (seen_at);
```

靠**主鍵衝突**判定重放，不先查再插——避免併發下兩個請求都查到「不存在」然後都插入成功的競態。

實作對應 `auth/NonceStore.java`：

- 寫入走 `RequestNonceRepository.insertIfAbsent`（原生 `INSERT … ON CONFLICT (nonce) DO NOTHING`），回傳 1 才是首次出現。**不能用 `save()`**——主鍵是外部指定的字串，Spring Data 會走 `merge()` 把重放靜默覆寫掉
- `RequestNonce` entity 刻意不提供公開建構子與 getter，純粹是 schema 對應，所有讀寫都繞過實體實例
- `client_id` 是裸 `BIGINT`，SQL **沒有**宣告外鍵
- 保留期 `NonceStore.RETENTION = 600 秒`，由 `@Scheduled(fixedDelayString = "PT5M")` 的 `purgeExpired()` 清理

## 8. `webhook_event`（缺口 G1）

Webhook 冪等閘門。

```sql
CREATE TABLE webhook_event (
    webhook_event_id  VARCHAR(64) PRIMARY KEY,     -- LINE 提供
    event_type        VARCHAR(32) NOT NULL,
    line_user_id      VARCHAR(64),
    received_at       TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_webhook_event_cleanup ON webhook_event (received_at);
```

**為什麼需要這張表**

LINE 在 webhook 回應逾時或非 200 時會**重送同一事件**。有些操作天生冪等（upsert user），有些不是：

- `FollowEvent` 會發歡迎訊息 → 重送就重複打招呼
- 「申請金鑰」指令 → 重送就發出兩個 token

處理器進入時先嘗試 `INSERT`，違反主鍵即代表已處理過，直接回 200 不做事。這是**單一的冪等閘門**，比「把每個操作各自寫成冪等」更可靠，也更容易在 code review 時確認正確性。

實作在 `webhook/WebhookEventGuard.java`：與 `request_nonce` 同一套寫法，走 `WebhookEventRepository.insertIfAbsent`（`ON CONFLICT DO NOTHING`）而非 `save()`。保留期 `RETENTION = 30 天`，由 `@Scheduled(cron = "0 15 3 * * *")` 的 `purgeExpired()` 清理。`line_user_id` 未宣告外鍵。

## 9. `audit_log`（缺口 G8）

> ⏳ **表存在，但一列都沒寫過。** 與 `enrollment_token` 同樣的情況：無 `@Entity`、無 Repository、無原生 SQL，`audit/` 套件只有 `.gitkeep`。全 codebase 唯一提到這張表的地方是 `monitor/domain/ApiMonitorRun.java` 的一句註解。**稽核紀錄實際上是空的**，下面描述的是規劃中的 schema 而非運作中的機制。

```sql
CREATE TABLE audit_log (
    id           BIGSERIAL   PRIMARY KEY,
    actor_type   VARCHAR(16) NOT NULL,      -- CLIENT | LINE_USER | SYSTEM
    actor_id     VARCHAR(64),
    action       VARCHAR(48) NOT NULL,      -- CLIENT_CREATED, SCOPE_GRANTED, ...
    target_type  VARCHAR(32),
    target_id    VARCHAR(64),
    detail       JSONB,
    ip           INET,
    occurred_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_audit_time   ON audit_log (occurred_at DESC);
CREATE INDEX idx_audit_target ON audit_log (target_type, target_id, occurred_at DESC);
CREATE INDEX idx_audit_action ON audit_log (action, occurred_at DESC);
```

`detail` 用 JSONB 是因為不同 action 要記的欄位差異大（scope 變更記前後差異、enrollment 記 purpose、認證失敗記失敗類型）。強行正規化會產生大量 null 欄位。

## 10. Flyway 策略

| 項目 | 規則 |
|---|---|
| 位置 | `server/src/main/resources/db/migration/` |
| 命名 | `V{n}__{描述}.sql`，例如 `V1__init.sql` |
| Hibernate | `ddl-auto: validate`——啟動時比對 entity 與實際 schema，不一致就**拒絕啟動** |
| 已套用的 migration | **絕不修改**。要改就開新的 `V{n+1}` |
| 回滾 | 不用 Flyway undo（社群版沒有）。破壞性變更走「新增 → 雙寫 → 遷移 → 移除」四步 |
| 測試 | 整合測試用 Testcontainers 起乾淨 PostgreSQL 跑完整 migration，確保從零建置永遠可行 |

### 已套用的 migration

| 版本 | 檔案 | 內容 |
|---|---|---|
| V1 | `V1__init.sql` | 初始 schema：§2~§9 的 9 張表 + 18 個索引（含 2 個 partial UNIQUE：`uq_client_bound_active`、`uq_notification_idem`）+ 9 個 CHECK 約束。不寫入任何初始 owner 資料 |
| V2 | `V2__client_default_target.sql` | `client` 增 `default_target_type` / `default_target_user_ids` 兩欄 + 2 個 CHECK；回填已有 `notify:owner` scope 的 client 為 `'OWNER'`（[§3](#3-client)） |
| V3 | `V3__scheduled_send.sql` | `notification` 增 `scheduled_at` + partial 索引 `idx_notification_scheduled`（[§5](#5-notification)） |
| V4 | `V4__api_monitor.sql` | 建 `api_monitor` / `api_monitor_run` / `api_monitor_seen_item` 三張表 + 3 個索引 + 5 個 CHECK（[§12](#12-api-監控與站台登入相關表v4v6)） |
| V5 | `V5__site_session.sql` | 建 `site_session`（[§12.4](#124-site_session)） |
| V6 | `V6__monitor_computed.sql` | 建 `monitor_secret`；`api_monitor` 增 `computed_fields`（[§12.5](#125-monitor_secret)、[13-監控計算欄位設計](13-監控計算欄位設計.md)） |

**初始 owner 的標記「不」放在 migration 裡。** migration 應該與環境無關，而 `APP_OWNER_LINE_USER_ID`（設定鍵 `app.owner-line-user-id`）是環境設定；寫進 migration 會讓它只在第一次建置時生效，日後改環境變數不會反映，且會讓同一份 migration 在不同環境產生不同結果。改由應用啟動時 upsert——已實作於 `lineuser/OwnerBootstrap.java`。

## 11. 資料保留與清理（缺口 G7）

`notification` 與 `notification_delivery` 會無限增長。一年後這兩張表會主宰整個資料庫大小，讓備份變慢、查詢變差。

### 11.1 已實作的清理排程

| 資料 | 保留 | 排程 | 實作 |
|---|---|---|---|
| `request_nonce` | 10 分鐘（`NonceStore.RETENTION`） | `fixedDelay = PT5M` | `NonceStore.purgeExpired` |
| `webhook_event` | 30 天（`WebhookEventGuard.RETENTION`） | `cron = 0 15 3 * * *` | `WebhookEventGuard.purgeExpired` |
| `api_monitor_run` | 14 天（`app.monitor.run-retention`，`P14D`） | `cron = 0 20 3 * * *` | `ApiMonitorSweeper.sweep` |
| `api_monitor_seen_item` | 90 天（`app.monitor.seen-item-retention`，`P90D`） | 同上 | 同上 |

只有監控那兩項的保留期是設定值（可用 `APP_MONITOR_RUN_RETENTION` / `APP_MONITOR_SEEN_ITEM_RETENTION` 覆寫），`request_nonce` 與 `webhook_event` 是 Java 常數。

### 11.2 ⏳ 規劃了但還沒接線的

| 資料 | 規劃保留 | 現況 |
|---|---|---|
| `notification.payload` | 90 天，清空 payload（設 null）保留 metadata 與 `payload_hash` | `NotificationRepository.clearPayloadsBefore` 已實作，**沒有任何排程呼叫** |
| `notification` | 400 天，刪除整列 | `NotificationRepository.deleteByCreatedAtBefore` 已實作，**沒有任何排程呼叫** |
| `notification_delivery` | 90 天，刪除前先確認統計已回寫至 `notification` | `NotificationDeliveryRepository.deleteByCreatedAtBefore` 已實作，**沒有任何排程呼叫** |
| `enrollment_token` | 24 小時，刪除已過期或已消費 | 表本身就沒有程式讀寫（[§4](#4-enrollment_token)） |
| `audit_log` | 2 年，**不自動刪**，滿期後人工歸檔 | 表本身沒有程式寫入（[§9](#9-audit_log缺口-g8)） |

⚠️ 也就是說：程式碼註解與本文件多處寫的「90 天保留期」，目前**沒有任何東西真的在執行**。`notification` 與 `notification_delivery` 現在是無限增長的。這是接線缺口而非設計缺口——repository method 都在，缺的是一個 `@Scheduled` 的呼叫者。

**實作要點**

- 每個清理任務**分批 DELETE**（每批上限 10000 列，批間短暫讓出），避免長交易鎖表導致線上請求卡住
- 清理任務是 `@Scheduled`，在多實例下會重複執行（[缺口 G12](02-架構設計.md#g12--多實例的排程重複執行--加第二個實例前必須解決)）。重複刪除本身是冪等的，只是浪費資源；單實例故可接受，加第二個實例前需導入 ShedLock
- 排程方法必須自己 catch 例外。`@Scheduled` 方法拋出例外會讓後續執行靜悄悄停擺，保留期清理就永久失效——`ApiMonitorSweeper.sweep` 是照這個原則寫的範本
- 新增的保留期一律做成設定值而非硬編碼，便於依實際資料量調整

**尚未做但預留的路**：若 `notification` 成長超出預期，可改為按月 partition（`PARTITION BY RANGE (created_at)`），清理變成 `DROP PARTITION`，成本從 O(n) 降到 O(1)。現在不做是因為當前預估量用不到，而 partition 會讓 schema 與查詢複雜化。

## 12. API 監控與站台登入相關表（V4~V7）

這 5 張表支撐 API 監控輪詢子系統。設計理由見 [11-API監控輪詢設計](11-API監控輪詢設計.md)、[12-API監控易用性升級](12-API監控易用性升級.md)、[13-監控計算欄位設計](13-監控計算欄位設計.md)；這裡只記 schema 與資料模型層面的取捨。

### 12.1 `api_monitor`

**設定與執行狀態同一張表**。監控項目數量本來就小（十位數），拆兩張表只會讓每次輪詢多一次 join，換不到任何好處。

```sql
CREATE TABLE api_monitor (
    id                        BIGSERIAL    PRIMARY KEY,
    name                      VARCHAR(100) NOT NULL,
    client_id                 BIGINT       NOT NULL REFERENCES client (id),
    -- 請求定義
    url                       TEXT         NOT NULL,
    method                    VARCHAR(8)   NOT NULL DEFAULT 'GET',
    request_body              TEXT,
    headers_ciphertext        BYTEA,                    -- AES-256-GCM，AAD = monitor:{id}
    headers_iv                BYTEA,
    headers_key_version       INT,
    -- 排程
    interval_seconds          INT          NOT NULL,
    enabled                   BOOLEAN      NOT NULL DEFAULT true,
    -- 比對規則
    compare_mode              VARCHAR(16)  NOT NULL,    -- WHOLE_BODY | EXTRACTED | NEW_ITEMS
    extract_rules             JSONB        NOT NULL DEFAULT '[]',
    item_pointer              TEXT,
    item_key_pointer          TEXT,
    message_template          TEXT         NOT NULL,
    -- 防洗版
    notify_on_failure         BOOLEAN      NOT NULL DEFAULT true,
    cooldown_seconds          INT          NOT NULL DEFAULT 0,
    max_notifications_per_day INT,                      -- null = 不限
    -- 執行狀態
    next_run_at               TIMESTAMPTZ  NOT NULL,
    last_run_at               TIMESTAMPTZ,
    last_notified_at          TIMESTAMPTZ,
    last_fingerprint          BYTEA,                    -- SHA-256
    last_state                JSONB,
    consecutive_failures      INT          NOT NULL DEFAULT 0,
    failure_notified          BOOLEAN      NOT NULL DEFAULT false,
    notified_count            INT          NOT NULL DEFAULT 0,
    notified_day              DATE,
    created_at                TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at                TIMESTAMPTZ  NOT NULL DEFAULT now(),
    CONSTRAINT api_monitor_method_chk   CHECK (method IN ('GET','POST')),
    CONSTRAINT api_monitor_mode_chk     CHECK (compare_mode IN ('WHOLE_BODY','EXTRACTED','NEW_ITEMS')),
    CONSTRAINT api_monitor_interval_chk CHECK (interval_seconds >= 30),
    CONSTRAINT api_monitor_newitems_chk CHECK (
        compare_mode <> 'NEW_ITEMS'
        OR (item_pointer IS NOT NULL AND item_key_pointer IS NOT NULL)
    )
);

-- V6 新增：計算欄位（雜湊／簽章）
ALTER TABLE api_monitor ADD COLUMN computed_fields JSONB NOT NULL DEFAULT '[]';

CREATE INDEX idx_api_monitor_due ON api_monitor (next_run_at) WHERE enabled;
```

**設計說明**

- `next_run_at` 是**取件的唯一依據，同時兼作租約**：取件時先推到 `now + lease`，執行完再推到 `now + interval`（失敗則退避）。`idx_api_monitor_due` 是唯一服務這條路徑的 partial 索引
- `last_fingerprint` 只給 `WHOLE_BODY` / `EXTRACTED` 用；`NEW_ITEMS` 改比對 [§12.3](#123-api_monitor_seen_item)
- `last_state` 的取出值**一律轉字串存**，模板不做型別運算，避開數字精度與 locale 問題。null = 尚未執行過第一次
- `consecutive_failures` + `failure_notified` 是防洗版的一對：連續失敗達門檻且尚未通知過才發一則；成功時歸零，若先前通知過失敗則補發一則恢復通知
- `notified_count` + `notified_day` 做每日上限（`notified_day` 與今天不同時歸零）
- `extract_rules` / `computed_fields` 是 JSONB 而非子表：它們永遠整份讀寫、永遠有順序、也不需要被單獨查詢。`name` 限 `[A-Za-z0-9_]{1,32}`，模板用 `{{value.NAME}}` / `{{computed.NAME}}` 引用
- ⚠️ **`method` 是 `String` 不是 enum**（`monitor/domain/ApiMonitor.java`）。SQL 有 `api_monitor_method_chk` 守住值域，Java 端只靠 `validateAndNormalizeMethod()`。本專案其他有 CHECK 值域的欄位都有對應 enum，`method` 是唯一例外
- `name` **沒有** unique 約束，允許同名監控

### 12.2 `api_monitor_run`

每次輪詢一列的執行紀錄。

```sql
CREATE TABLE api_monitor_run (
    id              BIGSERIAL   PRIMARY KEY,
    monitor_id      BIGINT      NOT NULL REFERENCES api_monitor (id) ON DELETE CASCADE,
    started_at      TIMESTAMPTZ NOT NULL,
    duration_ms     INT,
    outcome         VARCHAR(16) NOT NULL,   -- CHANGED | UNCHANGED | FAILED | SKIPPED
    http_status     INT,
    error_message   TEXT,
    notification_id UUID,                   -- 指向 notification.id，刻意不設 FK
    CONSTRAINT api_monitor_run_outcome_chk
        CHECK (outcome IN ('CHANGED','UNCHANGED','FAILED','SKIPPED'))
);

CREATE INDEX idx_api_monitor_run_recent ON api_monitor_run (monitor_id, started_at DESC);
```

**設計說明**

- `notification_id` **刻意不設外鍵**：`notification` 有保留期會被清理，而這裡是歷史紀錄，不該被連動刪除
- `notification_id` 有值的情況有三種（以 migration 的 `COMMENT` 為準，`ApiMonitorRun` 的 javadoc 只寫了第一種、已過時）：
  1. `outcome = CHANGED` 的變更通知
  2. `outcome = FAILED` 且連續失敗達門檻而發出的失敗通知
  3. 接在一次已通知故障之後的成功執行所補發的恢復通知（此時 outcome 通常是 `UNCHANGED` / `SKIPPED`）
- `error_message` **只寫分類與長度，不得含目標 API 回應全文**——回應可能帶機敏資料

### 12.3 `api_monitor_seen_item`

`NEW_ITEMS` 模式已看過的項目鍵。

```sql
CREATE TABLE api_monitor_seen_item (
    monitor_id    BIGINT       NOT NULL REFERENCES api_monitor (id) ON DELETE CASCADE,
    item_key      VARCHAR(200) NOT NULL,
    first_seen_at TIMESTAMPTZ  NOT NULL DEFAULT now(),
    PRIMARY KEY (monitor_id, item_key)
);

CREATE INDEX idx_api_monitor_seen_age ON api_monitor_seen_item (first_seen_at);
```

- 複合主鍵直接當去重依據；entity 用 Java `record` 當 `@EmbeddedId`（`SeenItemId`）
- `item_key` 超過 200 字元時由**呼叫端取 SHA-256 十六進位字串**代入，**絕不截斷**——截斷會讓不同項目撞成同一把 key 而被誤判為「看過了」。DB 不強制這件事，是呼叫端約定
- `idx_api_monitor_seen_age` 只服務保留期清理（[§11.1](#111-已實作的清理排程)）

### 12.4 `site_session`

一個 host 一份 cookie jar，讓監控能打需要登入的站台。

```sql
CREATE TABLE site_session (
    host              VARCHAR(255) PRIMARY KEY,
    jar_ciphertext    BYTEA        NOT NULL,   -- AES-256-GCM，AAD = site_session:{host}
    jar_iv            BYTEA        NOT NULL,   -- 12 bytes，每次回寫重新產生
    jar_key_version   INT          NOT NULL,
    cookie_names      TEXT         NOT NULL,   -- 逗號分隔，純顯示用
    last_refreshed_at TIMESTAMPTZ,
    created_at        TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at        TIMESTAMPTZ  NOT NULL DEFAULT now()
);
```

無外鍵、無 CHECK、無額外索引——只有主鍵。

**設計說明**

- `host` 是**正規化後**才當主鍵：`IDN.toASCII` + `Locale.ROOT` 小寫，與 `OutboundUrlGuard` 的正規化方式一致
- ⚠️ 附加 cookie 前的比對規則在 `monitor/session/HostMatcher.java`，**不在 DB**：請求 host 必須與這裡的 host 完全相等，或以「`.` + 這裡的 host」結尾。**絕不可用不帶點號邊界的 `endsWith(host)`**——那會讓 `evil-example.com` 誤配到 `example.com` 的 cookie，把 session token 洩漏給第三方
- **cookie 值絕不明文落地，也絕不透過任何 API 回傳**；`cookie_names` 只存名稱，供後台顯示「這個站存了哪些 cookie」
- `jar_iv` 每次回寫都重新產生——GCM 在相同金鑰下重用 IV 會直接洩漏明文
- 相對 `api_monitor.headers_ciphertext`，這裡沒有「要先 insert 拿 id 才能算 AAD」的順序陷阱，因為 `host` 本身就是主鍵

### 12.5 `monitor_secret`

監控專屬的機敏常數（appsecret、device id 等），供計算欄位與模板引用。

```sql
CREATE TABLE monitor_secret (
    monitor_id  BIGINT      NOT NULL REFERENCES api_monitor (id) ON DELETE CASCADE,
    name        VARCHAR(32) NOT NULL,
    ciphertext  BYTEA       NOT NULL,   -- AES-256-GCM，AAD = monitor_secret:{monitor_id}:{name}
    iv          BYTEA       NOT NULL,
    key_version INT         NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (monitor_id, name),
    CONSTRAINT monitor_secret_name_chk CHECK (name ~ '^[A-Za-z0-9_]{1,32}$')
);
```

- **值絕不回傳到任何 DTO、log、`api_monitor_run` 或 LINE 訊息**，後台只顯示名稱與「已設定」
- `name` 用 `{{secret.NAME}}` 在請求模板引用，或當 HMAC 步驟的 `keySecret`。字元限制與 `api_monitor.extract_rules[].name` 同一套，並且**在 DB 端也有 regex CHECK**
- AAD 帶上 `monitor_id` 與 `name`，密文不能被搬到另一個監控或另一個名稱底下重用
- entity 同樣用 Java `record` 當 `@EmbeddedId`（`MonitorSecretId`）

### 12.6 `monitor_login`（V7）

`monitor_login` 保存可重用的站台登入設定，目前只接受 `COGNITO_SRP`。`config` 與 `username` 是明文設定；password、refresh token、短效 token 分別以 AES-256-GCM 加密，AAD 為 `monitor_login:{id}:password|refresh|token`。`api_monitor.login_id` 以 `ON DELETE SET NULL` 引用它，刪除登入設定不會刪除監控。

登入永久失敗會停用該設定並留下不含憑證片段的 `last_error`；同一 JVM 內以每筆登入鎖避免重複登入。這不是跨實例鎖，水平擴充前仍需補分散式協調。

## 13. Entity 與 schema 的落差與陷阱

`ddl-auto: validate` 只檢查「entity 有宣告的東西是否對得上 DB」，不檢查「DB 有的東西 entity 是否都宣告了」。以下都通得過 validate，但會誤導閱讀者或寫壞新程式碼。

### 13.1 有表但完全沒有程式讀寫

| 表 | 現況 |
|---|---|
| `enrollment_token` | 無 `@Entity`、無 Repository、無原生 SQL。`enrollment/` 套件只有 `.gitkeep` |
| `audit_log` | 同上，`audit/` 套件只有 `.gitkeep`。**稽核紀錄是空的** |

專案內無 `JdbcTemplate`、也沒有直接注入 `EntityManager`，所以這兩張表在執行期確實一列都不會被碰到。要動它們之前，先確認的是「功能要不要做」而不是「schema 對不對」。

### 13.2 Entity 未映射 SQL 已有的欄位

- **`client_scope.granted_at`**：SQL 是 `TIMESTAMPTZ NOT NULL DEFAULT now()`，但 `Client.scopes` 的 `@ElementCollection` 只映射 `scope` 一欄。值靠 DB 預設填，**應用層讀不到授權時間**——[§3](#3-client) 說「用獨立表是為了記錄授予時間」這個理由目前只兌現了一半

### 13.3 寫入時必須避開 `save()` 的三張表

`Notification`（PK 是應用產生的 UUID）、`RequestNonce`（PK 是字串）、`WebhookEvent`（PK 是 LINE 給的字串）**主鍵都是外部指定**。Spring Data 的 `save()` 對已賦值的 id 會走 `merge()`，結果是**靜默 UPDATE 而不是插入失敗**——冪等閘門會直接失效。

三者一律走各自 repository 的 `insertIfAbsent`（原生 `INSERT … ON CONFLICT DO NOTHING`，回傳 1 才是首次）。這是刻意設計不是缺陷，但**任何新增的寫入路徑都必須遵守**。

### 13.4 同名不同物

**`client.client_id`（`VARCHAR(64)`，對外識別碼 `cli_…`）與 `client_scope.client_id`（`BIGINT`，指向 `client.id` 的外鍵）同名但完全不同型別。** `notification.client_id`、`api_monitor.client_id`、`request_nonce.client_id` 也都是 `BIGINT` 的那一種。`client/Client.java` 的類別註解已明示這個陷阱——寫原生 SQL 或手動組 join 時最容易踩到。

### 13.5 其他值得知道的落差

| 項目 | 落差 |
|---|---|
| `line_user.is_owner` | entity 屬性叫 `owner`。JPQL 寫 `owner`，原生 SQL 寫 `is_owner` |
| `api_monitor.method` | `String` 不是 enum，值域只靠 DB CHECK + `validateAndNormalizeMethod()` |
| `notification_delivery.error_message` | SQL 無上限，Java 端 `truncate()` 截到 1000 字元 |
| `api_monitor_run.notification_id` | entity javadoc 只寫了「`CHANGED` 時有值」，migration 的 `COMMENT` 才是完整的三種情況（[§12.2](#122-api_monitor_run)） |
| 所有外鍵 | entity 端一律是純量（`Long` / `String` / `UUID`），**沒有 `@ManyToOne` / `@JoinColumn`**。級聯刪除只發生在 DB 層的 `ON DELETE CASCADE`，Hibernate 的一級快取不會同步 |
| 表層 UNIQUE 與 CHECK | entity 的 `@Table` 完全沒宣告 `uniqueConstraints`。`UNIQUE (notification_id, batch_no)`、`delivery_priority_chk`、`delivery_batch_size_chk`、`client_default_target_users_chk` 都只存在於 DB |
