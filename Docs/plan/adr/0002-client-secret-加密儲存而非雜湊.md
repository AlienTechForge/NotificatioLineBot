# ADR-0002 — Client secret 加密儲存而非雜湊

> 校訂日期：2026-09-21。依 2026-09-21 main 的程式碼核對；歷史方案與未實作項目另行標示。

**狀態**：Accepted ｜ 2026-08-18

## 背景

[初步SPEC.md](../../初步SPEC.md) §4 指定用 HMAC-SHA256 做客戶端認證：每個專案有自己的 Client ID / Secret，用 secret 對 request 產生簽章，伺服器驗證簽章。

一般的憑證儲存原則是「**只存雜湊，永不存明文**」——密碼、API token 都適用。直覺上 client secret 也該照辦。

**但 HMAC 讓這個原則不適用。**

HMAC 驗簽的流程是：伺服器拿 secret **重新計算**一次簽章，再與請求帶來的簽章比對。要重新計算，就必須拿得到 secret 本身。

雜湊是單向的。存了 `SHA-256(secret)` 之後就永遠拿不回 `secret`，也就無法重算簽章。**驗簽會直接做不出來。**

這不是實作偷懶，是 HMAC 這個方案的固有性質。

## 決策

**Client secret 以 AES-256-GCM 加密後儲存**，加密 key 來自環境變數 `APP_SECRET_ENC_KEY`。

| 項目 | 選擇 |
|---|---|
| 演算法 | AES-256-GCM（authenticated encryption） |
| Key | 環境變數，base64 編碼的 32 bytes |
| IV | 每筆記錄獨立，12 bytes，`SecureRandom` 產生，與密文一起存 |
| AAD | `client_id` |
| 版本欄位 | `secret_key_version`，支援不停機輪替 |

## 理由

- **GCM 提供完整性保護**。單純的 AES-CBC 只保證機密性，攻擊者若能寫入資料庫可以竄改密文而不被發現。GCM 的 authentication tag 讓竄改在解密時就會失敗。
- **AAD 綁 `client_id`** 防止「把 A 的密文複製到 B 的記錄上」。沒有 AAD 的話，能寫資料庫的攻擊者可以把已知 secret 的密文搬到高權限 client 上。
- **`secret_key_version` 欄位**讓新舊 key 可以並存並依 version 解密。現有程式尚無背景重加密任務，所以完整輪替程序仍需補工具。
- **啟動時 fail-fast** 檢查 key 存在且長度正確，寧可起不來也不要跑起來後每個請求都 500。

## 已考慮的替代方案

| 方案 | 為什麼沒選 |
|---|---|
| **雜湊儲存** | **技術上做不到**。HMAC 驗簽需要 secret 明文 |
| **非對稱簽章（Ed25519 / RSA）** | 伺服器只存公鑰，外洩無害，安全性明顯較佳。但要求**每個呼叫端都能做非對稱簽章與金鑰管理**。SPEC 的目標是「呼叫端只要複製一段簽章程式碼」，HMAC 在 bash 用 `openssl` 三行就能做，非對稱簽章在 shell script 中相當麻煩。接入成本是這個專案的核心考量 |
| **外部 KMS / Vault** | 安全性最佳，key 永不進應用記憶體。但多一個必須維運的服務，對單機部署的內部工具過重 |
| **明文儲存** | 資料庫外洩即全部憑證外洩，無任何緩解 |
| **對稱簽章但存明文 + 資料庫層加密（TDE）** | 依賴資料庫設定，備份檔案通常不受保護，且與應用層無關聯（無法做 AAD 綁定） |

若日後接入端都是內部 Java/Python 服務且不再需要 shell 一行接入，可以重新評估非對稱方案——屆時開新 ADR。

## 後果

**正面**

- 驗簽可行，且呼叫端接入成本極低（三行 shell）
- 資料庫外洩時，沒有加密 key 就拿不到 secret
- 資料模型允許多版本 key 並存；自動重加密尚未實作

**負面 —— 且必須嚴肅對待**

| 後果 | 說明 |
|---|---|
| **`APP_SECRET_ENC_KEY` 成為單點** | 這把 key 保護所有憑證。它外洩，等同所有 client secret 外洩 |
| **key 遺失無法復原** | 沒有 key 就解不開任何 secret。**所有呼叫端一起失效，只能全體重新發放金鑰** |
| **key 必須與 DB 備份分開存放** | 放在一起等於沒有加密。這件事很容易在做備份自動化時被忘記 |
| **secret 無法讀回給使用者** | 我們**選擇**不提供讀回功能（雖然技術上做得到），避免 Admin UI 成為集中的外洩點。使用者忘記 secret 只能重設 |

**必要的緩解措施**

1. key 存放於**至少兩個獨立位置**（例如密碼管理器 + 離線備份），且不與資料庫備份同處
2. [09-CICD與維運 §7.1](../09-CICD與維運.md#71-app_secret_enc_key) 明確寫出**外洩**與**遺失**兩套不同的處置程序
3. 啟動 fail-fast 檢查，避免「key 設錯但服務照跑」
4. `secret_key_version` 欄位從第一版就存在，不要等到要輪替時才加
