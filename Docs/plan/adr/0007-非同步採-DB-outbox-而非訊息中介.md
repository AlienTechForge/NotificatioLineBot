# ADR-0007 — 非同步採 DB outbox 而非訊息中介

**狀態**：Accepted ｜ 2026-08-18

## 背景

`target: ALL` 對 1200 人發送需要 3 次 LINE API 呼叫，加上可能的重試，總時間可達數十秒。同步處理會讓呼叫端逾時，而逾時後的重試會造成重複發送。

所以 API 必須是非同步的：立即回 `202`，實際發送在背景進行。

問題是：**背景工作放在哪裡？**

需求：

1. 應用重啟不能掉單
2. 失敗的批次要能自動重試
3. 要能查詢「現在積了多少、最舊的等了多久」
4. 未來可能需要多實例
5. 不想為此多養一個必須維運的服務

## 決策

**用資料庫表當 outbox**：`notification_delivery` 同時是投遞明細與工作佇列。

三段式：

| 段 | 機制 | 角色 |
|---|---|---|
| 即時派送 | `@Async` + `ThreadPoolTaskExecutor` | 正常路徑，低延遲 |
| 落地 | `notification_delivery` 的 `PENDING` 狀態 | 真相來源 |
| 補償 | `@Scheduled` 每 30 秒 + `SELECT … FOR UPDATE SKIP LOCKED` | 撿回沒送成的 |

取件查詢：

```sql
SELECT * FROM notification_delivery
 WHERE status = 'PENDING' AND next_attempt_at <= now()
 ORDER BY priority, next_attempt_at
 LIMIT 20
   FOR UPDATE SKIP LOCKED;
```

## 理由

### `@Async` 單獨用不夠

純記憶體的執行緒池佇列有一個致命問題：**應用重啟時佇列中的工作永久消失**。而重啟是常態（每次部署都會發生）。

使用者發了全體公告，部署剛好在此時進行，1200 人中有 800 人永遠收不到——而且沒有任何紀錄顯示發生了什麼。

### DB outbox 解決了什麼

| 問題 | 純記憶體佇列 | DB outbox |
|---|---|---|
| 應用重啟 | 工作**永久消失** | 仍是 `PENDING`，redriver 撿回 |
| 派送中途當機 | 該批狀態不明 | 仍是 `PENDING`，會被重新取件 |
| 查「積了多少」 | 需額外暴露內部狀態 | 一句 SQL |
| 查「最舊的等多久」 | 幾乎做不到 | `min(next_attempt_at)` |
| 未來多實例 | 需整個重寫 | `SKIP LOCKED` 已經是安全的 |
| 失敗批次的稽核 | 沒有 | 表中留有完整記錄 |

### `SKIP LOCKED` 是關鍵

`FOR UPDATE SKIP LOCKED` 讓多個工作者可以**完全並行**取件而不互相阻塞——每個工作者跳過已被別人鎖住的列，取自己的那一批。

這意味著 Phase 1 寫的取件邏輯，在未來加開第二個實例時**不需要任何改動**。這是幾乎免費的未來保險。

（也因此不能用 SQLite——它沒有等價機制。見 [ADR-0001](0001-採用-PostgreSQL-而非-SQLite.md)。）

### 為什麼不用訊息中介

Kafka / RabbitMQ / Redis Stream 都能做到，而且做得更好——但要付出：

- 多一個必須維運的服務（安裝、監控、備份、版本升級）
- 多一組故障模式（broker 掛掉怎麼辦、訊息積壓怎麼清）
- **多一個一致性問題**：「寫 DB」與「發訊息」是兩個系統的操作，中間可能不一致。要解決這個，標準做法正是……**transactional outbox 模式**——也就是本決策採用的東西

換句話說，引入 broker 之後，為了保證一致性仍然需要一張 outbox 表。既然表要有，且當前量級不需要 broker 的吞吐量，那就先不要 broker。

**本專案的量級**：每批對應一次數百毫秒的 LINE API 呼叫。DB 的幾次往返在這個尺度下完全可忽略。

## 已考慮的替代方案

| 方案 | 為什麼沒選 |
|---|---|
| **純 `@Async` 記憶體佇列** | 重啟掉單。這是不可接受的正確性問題，不是效能問題 |
| **Kafka / RabbitMQ** | 多一個服務要維運；仍需要 outbox 表解決雙寫一致性；當前量級用不到其吞吐量 |
| **Redis 佇列** | 比 Kafka 輕，但仍多一個服務；持久性保證弱於 PostgreSQL；且同樣有雙寫一致性問題 |
| **Quartz 當工作佇列** | Quartz 是排程器不是佇列。用它做一次性任務會產生大量 trigger 記錄，且語意不合。Phase 3 的定時通知會用 Quartz，但那是排程，不是派送 |
| **只用 `@Scheduled` 輪詢，不用 `@Async`** | 可行且更簡單，但所有通知都要等下一次輪詢（最多 30 秒延遲）。加上 `@Async` 讓正常路徑是即時的，輪詢只當補償 |

## 後果

**正面**

- 重啟不掉單；派送中途當機能自動恢復
- 佇列深度與等待時間可用 SQL 直接查，易於監控
- 失敗批次留有完整稽核紀錄
- `SKIP LOCKED` 讓多實例擴充不需改寫取件邏輯
- **零額外基礎設施**

**負面**

| 後果 | 影響 / 緩解 |
|---|---|
| 每批多幾次 DB 往返 | 相對於數百毫秒的 LINE 呼叫可忽略 |
| 輪詢間隔造成補償路徑的延遲（最多 30 秒） | 正常路徑走 `@Async`，即時。補償只在異常時生效 |
| 資料庫要承擔佇列負載 | 量級小；`idx_delivery_pickup` partial index 讓取件查詢很快 |
| **`notification_delivery` 會無限增長** | 必須有保留政策（[04 §11](../04-資料模型.md#11-資料保留與清理缺口-g7)）。這是本決策帶來的直接負債 |
| 沒有現成的死信佇列機制 | `FAILED` 狀態的批次留在表中，Phase 2 Admin 提供手動重送 |
| 高吞吐時 DB 會成為瓶頸 | 若真的到那個量級，outbox 表可以直接改由 broker 消費而不需重新設計資料模型 |

**設計上必須注意的兩個陷阱**

1. **派送必須在交易提交後才啟動**。若在 `@Transactional` 方法內直接呼叫 `@Async`，非同步執行緒可能在交易提交前就去查資料，結果查不到。用 `afterCommit` 回呼觸發。**這個 bug 在本機幾乎不會出現，上線後在負載下才偶發。**

2. **`SENDING` 狀態需要有偵測機制**。若程序被 kill 且沒寫回狀態，`notification` 會永遠停在 `SENDING`。對應的 delivery 仍是 `PENDING`，redriver 會撿回並最終回寫正確狀態——但要有監控指標能發現「有東西卡了 30 分鐘」。
