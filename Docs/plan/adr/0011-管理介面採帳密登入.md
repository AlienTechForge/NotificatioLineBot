# ADR-0011：管理介面採帳密登入，帳密來源為 GitHub Secrets

> 校訂日期：2026-09-21。依 2026-09-21 main 的程式碼核對；歷史方案與未實作項目另行標示。

## 狀態

Accepted（2026-08-19）。**取代 [ADR-0009](0009-Admin-認證採-LINE-Login.md)。**

## 背景

管理介面要讓管理者設定「每組憑證的預設通知對象」。這個介面能改變所有通知的
流向 —— 誰能開它，就等於能把任何服務的告警轉發給任何人，或讓它們安靜消失。
所以認證方式的選擇不是體驗問題，是權限邊界問題。

API 端已經有一套 HMAC 認證（見 [ADR-0002](0002-client-secret-加密儲存而非雜湊.md)），
但那是為「機器對機器」設計的：呼叫端持有長期金鑰、每個請求逐一簽章。

## 決策

管理介面用**帳號密碼 + session cookie**，帳密存在 GitHub Secrets
（`APP_ADMIN_USERNAME` / `APP_ADMIN_PASSWORD`），部署時寫進伺服器的 `.env`。

- 獨立的 Spring Security filter chain，`securityMatcher("/admin/**")`
- **CSRF 啟用**（API chain 是關的，理由見下）
- Spring Security 驗證器使用 bcrypt；原始密碼仍由環境設定載入，不能宣稱整個程序記憶體完全沒有明文
- 兩個 Secret 都留空 = 整個管理介面不註冊，連登入頁都不存在
- 換密碼不必重新部署：Admin workflow 的 `reload-admin-login` 動作重讀 Secrets、
  改寫 `.env` 的那兩行、重啟應用

管理 API 掛在 `/admin/api/**` 而非 `/api/v1/admin/**`，讓「路徑前綴」與
「認證方式」一一對應。

## 理由

**為什麼不用 LINE Login（ADR-0009 的原方案）**

LINE Login 是 OAuth 流程：要註冊 Login channel、處理 redirect callback、
換 token、驗 id_token、再對應到本地身分。它解決的是「多個使用者、各自的身分」，
而這裡只有一個管理者。為了一個人的登入引入一整條 OAuth 流程，增加的攻擊面
（callback 處理、state 驗證、token 儲存）比它消除的多。

**為什麼不沿用 HMAC**

技術上可行：管理頁用 WebCrypto 在瀏覽器裡簽章。但那需要把長期有效的 secret
貼進網頁並存在瀏覽器裡 —— 一個永不過期的憑證放在 XSS 打得到的地方，比 session
cookie 差。而且 HMAC 沒有「登出」這個概念。

**為什麼帳密放 GitHub Secrets**

`.env` 已經是所有機密的落點（`APP_SECRET_ENC_KEY`、DB 密碼、LINE token），
再多兩個不改變信任模型。而 Secrets 讓「換密碼」變成改一個欄位加跑一個 workflow，
不必登入伺服器編輯檔案 —— 需要 SSH 才能做的維運，實務上就是不會做。

**為什麼 CSRF 必須在這條 chain 開著**

API chain 關掉 CSRF 是因為它無 cookie、無 session：沒有「瀏覽器會自動附上憑證」
這回事，CSRF 就不成立。這條 chain 用 session cookie，前提整個反過來 ——
任何網站都能讓管理者的瀏覽器對這裡發出帶 cookie 的請求。照抄 API chain 的
`csrf.disable()` 會讓管理後台變成一個 CSRF 靶子。

## 已考慮的替代方案

| 方案 | 為什麼沒選 |
|---|---|
| LINE Login（ADR-0009） | 為單一使用者引入完整 OAuth 流程，增加的攻擊面多於消除的 |
| 沿用 HMAC，頁面用 WebCrypto 簽章 | 長期 secret 存在瀏覽器裡，且沒有登出概念 |
| 反向代理做 Basic Auth | 認證在應用之外，應用自己不知道是誰在操作，稽核記錄無從寫起 |
| 不做網頁，只用 GitHub Actions | 沒有新攻擊面，但選收件人要手打 33 字元的 user id，打錯無徵兆 |

## 後果

**正面**

- 只有一種面向人的認證方式，沒有兩套需要各自維護的驗證邏輯
- 換密碼是一個 workflow，不需要 SSH
- 忘記設定的預設結果是「後台不存在」，不是「後台沒有密碼」

**負面**

- **單一共用帳號，沒有個別身分。** 稽核日誌只能記「管理者做了什麼」，
  無法記「是誰」。若日後真的有第二個管理者，這個決策要重新檢視
- 密碼以明文存在伺服器的 `.env`（`chmod 600`）。與既有機密同一個信任層級，
  但確實比只存雜湊差 —— 換成存 bcrypt 雜湊會讓 `reload-admin-login` 需要
  管理者自己算雜湊，那個摩擦足以讓人乾脆不換密碼
- 應用層沒有帳號鎖定。範例 nginx 對 `/admin/login` 設每來源限速，但實際安全性取決於部署是否套用該設定與密鑰 header 門禁
