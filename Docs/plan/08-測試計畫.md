# 08 — 測試計畫

← [文件索引](README.md) ｜ 前一份 [07-非同步與可靠性設計](07-非同步與可靠性設計.md)

覆蓋率目標 **80%+**（line coverage），但覆蓋率只是下限指標。真正的驗收標準是下面的測試矩陣有沒有全部通過。

開發方式：**TDD**。步驟 2–9（見 [10-任務拆解](10-任務拆解.md)）一律先寫失敗的測試，再寫實作。

---

## 1. 測試分層

| 層 | 工具 | 跑在哪 | 數量級 |
|---|---|---|---|
| Unit | JUnit 5 + AssertJ | 純記憶體，毫秒級 | 多數 |
| Integration | `@SpringBootTest` + Testcontainers PostgreSQL | 真資料庫 | 中等 |
| LINE 打樁 | okhttp `MockWebServer` | 假的 LINE API | 中等 |
| 端到端 | 手動 + `curl` 腳本 | 真環境 | 少數，見 [10 §驗證](10-任務拆解.md) |

> **絕不在自動化測試中呼叫真實的 LINE API。** 測試會發訊息給真人、消耗額度、且結果不可重現。一律用 `MockWebServer` 把 `MessagingApiClient` 的 `apiEndPoint` 指向本機。

## 2. Unit 測試矩陣

### 2.1 `CanonicalRequest` / `HmacSigner`

| 案例 | 期望 |
|---|---|
| 固定輸入產生固定 canonical string | 與文件 [03 §2.2](03-權限與認證設計.md#22-canonical-string) 的範例逐字元相同 |
| 固定 (secret, canonical) 產生固定簽章 | 硬編碼的期望值（**測試向量**）。這防止日後有人「順手優化」而改變簽章結果 |
| 空 body | hash 是空位元組陣列的 SHA-256，不是空字串 |
| body 含 UTF-8 中文 | 以 UTF-8 bytes 計算，不受平台預設編碼影響 |
| body 含換行 | 不做任何正規化 |
| canonical string 無結尾換行 | 明確斷言最後一個字元不是 `\n` |

> **測試向量是這組測試的核心價值。** 簽章演算法的任何細節改動（欄位順序、分隔符、編碼）都會讓所有呼叫端同時失效，且錯誤訊息只會是「簽章不符」，極難診斷。用寫死的期望值把契約釘住。

### 2.2 `SecretCipher`

| 案例 | 期望 |
|---|---|
| 加密後解密 | 得回原文 |
| 同一明文加密兩次 | **密文不同**（IV 隨機） |
| 用錯誤的 key 解密 | 拋例外，不回傳垃圾資料 |
| 用錯誤的 AAD（別的 client_id）解密 | 拋例外 |
| 竄改密文任一 byte | 拋例外（GCM 的完整性驗證） |
| key 長度不是 32 bytes | 建構時就拋例外 |

### 2.3 `TargetResolver`

完整的 target × scope 矩陣。這是**權限的核心**，每一格都要有測試。

| target | 持有 scope | 期望 |
|---|---|---|
| `SELF` | `notify:self` + 有綁定 | 回傳該 user |
| `SELF` | `notify:self` + 無綁定 | `CLIENT_NOT_BOUND` |
| `SELF` | 無 `notify:self` | `SCOPE_DENIED` |
| `SELF` | 有綁定但該 user 為 BLOCKED | `NO_RECIPIENT` |
| `OWNER` | `notify:owner` | 回傳所有 ACTIVE owner |
| `OWNER` | `notify:owner`，系統無 owner | `NO_RECIPIENT` |
| `OWNER` | 無 `notify:owner` | `SCOPE_DENIED` |
| `USER` | `notify:user` | 回傳指定名單中的 ACTIVE 者 |
| `USER` | 只有 `notify:self` | `SCOPE_DENIED` |
| `USER` | 只有 `notify:self`，**userIds 只填自己** | **仍是 `SCOPE_DENIED`** ← 見 [03 §1.3](03-權限與認證設計.md#13-target--scope-允許矩陣) |
| `USER` | `notify:user`，501 個 id | `VALIDATION_ERROR` |
| `ALL` | `notify:all` | 回傳所有 ACTIVE user |
| `ALL` | 無 `notify:all` | `SCOPE_DENIED` |
| 任意 + `lineMessages` | 無 `notify:raw` | `SCOPE_DENIED` |

### 2.4 批次切分

| 收件人數 | 期望批數 | 每批大小 |
|---|---|---|
| 0 | — | 應在此之前就被 `NO_RECIPIENT` 擋下 |
| 1 | 1 | [1] |
| 499 | 1 | [499] |
| **500** | **1** | **[500]** ← 邊界 |
| **501** | **2** | **[500, 1]** ← 邊界 |
| 1000 | 2 | [500, 500] |
| 1200 | 3 | [500, 500, 200] |

每批的 `retry_key` 必須**互不相同**，且同一批多次取得時**保持不變**。

### 2.5 錯誤分類器

| LINE 回應 | 期望分類 |
|---|---|
| `429` + "You have reached your monthly limit." | 終局失敗，不重試，不計入斷路器 |
| `429`（其他訊息） | 暫時性，重試，計入斷路器 |
| `401` | 憑證問題，不重試，不計入斷路器，發告警 |
| `403` | 同上 |
| `400` | 終局失敗 |
| `500` / `502` / `503` | 暫時性 |
| 連線逾時 | 暫時性 |

**這組測試防止把不可恢復的錯誤拿去重試 5 次**，也防止把額度耗盡誤判成需要開路的故障。

### 2.6 URI 白名單掃描（`notify:raw`）

| 案例 | 期望 |
|---|---|
| 白名單內的 uri | 通過 |
| 白名單外的 uri | `URI_HOST_NOT_ALLOWED` |
| **深層巢狀在 Flex Message 內的 uri** | **仍被掃到** ← 遞迴掃描的關鍵測試 |
| `uri` 在陣列中的物件內 | 仍被掃到 |
| 大小寫不同的網域 | 正規化後比對 |
| 帶 port 或使用者資訊的 uri | 正確解析出 host |

### 2.7 退避計算

| `attempt_count` | 期望延遲（jitter 前） |
|---|---|
| 1 → 2 | 1s |
| 2 → 3 | 2s |
| 3 → 4 | 4s |
| 4 → 5 | 8s |
| 5 → 6 | 16s |
| 6 | 放棄，標 `FAILED` |

jitter 需驗證落在 ±20% 範圍內。

## 3. Integration 測試矩陣

`@SpringBootTest` + Testcontainers PostgreSQL 2.0.5。每個測試類別共用容器（`@Container static`），避免反覆啟動。

### 3.1 Flyway migration

| 案例 | 期望 |
|---|---|
| 對全新的空資料庫跑完整 migration | 成功，且 Hibernate `validate` 通過 |

**這個測試保證「從零建置永遠可行」。** 它會抓到「有人手動改了正式庫的 schema 但沒寫 migration」這類問題。

### 3.2 `HmacAuthFilter`

| 案例 | 期望 |
|---|---|
| 正確簽章 | `202` |
| 竄改 body 任一字元 | `401 AUTH_INVALID_SIGNATURE` |
| 竄改簽章任一字元 | `401 AUTH_INVALID_SIGNATURE` |
| 缺任一必要 header | `401 AUTH_MISSING_HEADER` |
| 時間戳偏移 +400 秒 | `401 AUTH_TIMESTAMP_SKEW` |
| 時間戳偏移 −400 秒 | `401 AUTH_TIMESTAMP_SKEW` |
| 時間戳偏移 +299 秒 | `202`（邊界內） |
| 同一 nonce 送第二次 | `401 AUTH_NONCE_REPLAY` |
| 不存在的 client_id | `401 AUTH_INVALID_SIGNATURE`（**不是 404**，見 [03 §2.3](03-權限與認證設計.md#23-驗證順序hmacauthfilter)） |
| `status = DISABLED` 的 client | `401 AUTH_CLIENT_DISABLED` |
| `status = REVOKED` 的 client | `401 AUTH_CLIENT_DISABLED` |
| body 超過 64KB | `413 PAYLOAD_TOO_LARGE` |
| 簽章正確但 nonce 已用過 | 驗證 `request_nonce` **沒有**被未驗簽的請求污染 |

### 3.3 Enrollment 全流程

```text
1. 建立 ACTIVE 的 line_user
2. 呼叫 EnrollmentService.issue()          → 取得 raw token
3. GET /enroll/{token}                      → 200，頁面含 clientId 與 secret
4. 驗證 DB：client 已建立、scope = {notify:self}、bound 正確
5. 再次 GET /enroll/{token}                 → 410 Gone
6. 用步驟 3 拿到的憑證打 API（target=SELF）  → 202
7. 用同一組憑證打 target=ALL                 → 403 SCOPE_DENIED
8. 用同一組憑證打 target=USER（填自己的 id） → 403 SCOPE_DENIED
```

補充案例：

| 案例 | 期望 |
|---|---|
| 過期的 token | `410` |
| 不存在的 token | `410`（**不是 404**——不洩漏 token 是否存在過） |
| 已有 ACTIVE client 的 user 再次 `issue()` | 拒絕並提示改用「重設金鑰」 |
| `RESET` 流程 | 舊 client 變 `REVOKED`，新 client 為 `ACTIVE`，舊 secret 立即失效（`401`） |
| 同一 user 一小時內 issue 第 4 次 | 拒絕 |
| 回應 header | 含 `Cache-Control: no-store` 與 `Referrer-Policy: no-referrer` |

### 3.4 冪等

| 案例 | 期望 |
|---|---|
| 同 `Idempotency-Key` + 同 body 送兩次 | 兩次都 `202` 且 `notificationId` 相同；DB 只有一筆 notification |
| 同 key + 不同 body | 第二次 `409 IDEMPOTENCY_CONFLICT` |
| 不同 client 用相同 key | 兩筆獨立的 notification（key 的範圍是 per-client） |
| 併發送出兩個相同 key 的請求 | 只產生一筆 notification（靠唯一鍵，不是靠先查後插） |

### 3.5 速率限制與配額

| 案例 | 期望 |
|---|---|
| 一分鐘內第 61 次請求 | `429 RATE_LIMITED` + `Retry-After` header |
| 配額剩 10，送給 20 人 | `429 CLIENT_QUOTA_EXCEEDED`，**且完全沒有發送**（不做半套） |
| 配額剩 10，送給 10 人 | `202`（邊界） |
| `daily_message_quota = null` 的 client | 不受配額限制 |
| 配額以收件人數計 | 一次發 200 人 = 消耗 200，不是 1 |

### 3.6 Webhook

| 案例 | 期望 |
|---|---|
| 正確 `x-line-signature` 的 follow 事件 | `200`，`line_user` 出現且 `status = ACTIVE` |
| 錯誤 `x-line-signature` | `4xx`，DB 無變化 |
| **`events: []` 的空事件請求** | **`200`** ← LINE 連線測試 |
| 相同 `webhookEventId` 送兩次 | 第二次不重複處理（歡迎訊息只發一次） |
| unfollow 事件 | `status = BLOCKED`，且該 user 的 ACTIVE client 變 `DISABLED` |
| unfollow 後再 follow | `status` 回 `ACTIVE`；**client 不自動恢復** |
| handler 內部拋例外 | HTTP 仍回 `200`（LINE 不重送），error log 有記錄 |
| header 名稱大小寫不同 | 兩種都能正確驗簽 |

### 3.7 資料保留清理

| 案例 | 期望 |
|---|---|
| 過期的 `request_nonce` | 被清除 |
| 未過期的 `request_nonce` | 保留 |
| 91 天前的 `notification_delivery` | 被刪除，但 `notification` 的計數欄位不變 |
| 91 天前的 `notification.payload` | 被設為 null，`payload_hash` 保留 |
| 401 天前的 `notification` | 整列刪除 |
| `audit_log` | **不被自動刪除** |
| 清理大量資料 | 分批執行，單一交易不超過 10000 列 |

## 4. LINE API 打樁測試

用 okhttp `MockWebServer`，`MessagingApiClient.builder(token).apiEndPoint(server.url("/").uri())`。

### 4.1 分批與發送

| 案例 | 期望 |
|---|---|
| 1200 人的 `ALL` | MockWebServer 收到 **3 次** multicast 請求 |
| 每次請求的 `to` 陣列 | 大小分別為 500 / 500 / 200 |
| 每次請求帶 `X-Line-Retry-Key` | 三個值互不相同 |
| 每個請求最多 5 個 message object | 斷言 |
| 回應中的 `x-line-request-id` | 被寫入 `notification_delivery.line_request_id` |

### 4.2 重試

| 案例 | 期望 |
|---|---|
| 第一次回 `500`，第二次回 `200` | 最終 `SENT`；**兩次請求的 retry key 相同** |
| 連續 5 次 `500` | 最終 `FAILED`，`attempt_count = 5` |
| 回 `429` + monthly limit 訊息 | **只呼叫一次**，直接 `FAILED` |
| 回 `401` | 只呼叫一次，`FAILED` |
| 重試間隔 | 遞增（用可控的時鐘驗證，不用真的 sleep） |

### 4.3 Circuit Breaker

| 案例 | 期望 |
|---|---|
| 連續失敗達閾值 | 斷路器 `OPEN` |
| `OPEN` 期間的批次 | 狀態維持 `PENDING`，**`attempt_count` 不遞增** ← 關鍵斷言 |
| `OPEN` 期間 | MockWebServer 不再收到請求 |
| 等待期滿後恢復正常 | 斷路器回 `CLOSED`，積壓批次全部送出 |
| 月額度耗盡的失敗 | **不計入**斷路器統計 |

### 4.4 額度守門

| 案例 | 期望 |
|---|---|
| quota 剩餘 < 收件人數，`target: ALL` | `429 LINE_MONTHLY_QUOTA_EXCEEDED`，**完全不發送** |
| quota 充足 | 正常發送 |
| quota 查詢本身失敗 | **放行**並記 warn（輔助檢查失敗不擋主功能） |
| 5 分鐘內第二次 `ALL` | quota API 只被呼叫一次（快取生效） |
| `target: SELF` | **不呼叫** quota API |

## 5. 非同步與併發測試

這類測試最容易寫成偶發失敗（flaky）。原則：**用確定性的同步點，不用 `Thread.sleep`**。

| 案例 | 期望 | 怎麼測 |
|---|---|---|
| 派送在交易提交後才啟動 | 非同步段能查到 delivery 記錄 | 用 `CountDownLatch` 在 `afterCommit` 卡住，斷言此時 DB 已可見 |
| MDC 傳遞到 `@Async` 執行緒 | 非同步段的 log 有 `requestId` | 自訂 `ListAppender` 捕捉 log 事件並斷言 MDC 內容 |
| MDC 在工作結束後清除 | 執行緒重用時不繼承舊 context | 連續跑兩個工作，斷言第二個的 MDC 不含第一個的值 |
| `SKIP LOCKED` 併發取件 | 兩個工作者取到**不重疊**的批次 | 兩條執行緒同時取件，斷言結果集無交集 |
| 應用重啟後恢復 | `PENDING` 批次被 redriver 撿回 | 直接在 DB 塞 `PENDING` 記錄，觸發 redriver |
| 卡在 `SENDING` 的 notification | 被 redriver 修復為終態 | 塞一筆 `SENDING` + 對應 `PENDING` delivery |
| 優先級排序 | 高優先批次先被取出 | 塞不同 priority 的批次，斷言取件順序 |

## 6. 覆蓋率

| 項目 | 目標 |
|---|---|
| 整體 line coverage | ≥ 80% |
| `auth` 套件 | ≥ 95%（安全關鍵） |
| `notification.dispatch` 套件 | ≥ 90%（可靠性關鍵） |
| DTO / entity 的 getter/setter | 排除計算 |

用 JaCoCo，`mvn verify` 時產出報告並執行 `check`，低於門檻時**讓 build 失敗**。門檻設定在 `server/pom.xml` 的 jacoco `check` execution。

### 覆蓋率門檻的排除項

| 排除 | 理由 | 何時移除 |
|---|---|---|
| `**/NotifyLineApplication.class` | `main()` + `@SpringBootApplication`，沒有可測的行為 | 永久 |
| `**/config/SecurityConfig.class` | 宣告式 bean 設定，行為只在 HTTP 層可觀察 | **T4**（整合測試涵蓋路徑分流後） |

> 排除只掛在 `check` 上，**report 仍完整顯示所有類別** —— 排除的目的是不讓門檻誤判，不是把數字藏起來。

### 95% 是 `auth` 的實際上限附近

實測（T2）後 `auth` 為 95.6%，剩餘未覆蓋的**全部是不可達的 catch block**：

```java
} catch (NoSuchAlgorithmException e) {          // SHA-256 是 JDK 必備演算法
    throw new IllegalStateException(...);
} catch (GeneralSecurityException e) {          // HmacSHA256 / AES-GCM 同理
    throw new IllegalStateException(...);
}
```

要覆蓋這些需要 bytecode 操作或自訂 `SecurityProvider`，換不到任何實質保障。**不要為了衝數字寫這種測試**——真正該做的是消除重複（T2 把兩處重複的 SHA-256 樣板合併到 `Ids.sha256(byte[])`，同時降低了不可達行數）。

### 門檻本身要驗

設好門檻後，**故意把它調高一次確認 build 真的會紅**。靜默通過的覆蓋率門檻比沒有門檻更糟——它會讓人誤以為有保護。

```
[WARNING] Rule violated for package com.jason.notifyline.auth:
          lines covered ratio is 0.95, but expected minimum is 0.99
[INFO] BUILD FAILURE
```

> 覆蓋率是**下限**不是目標。100% 覆蓋率的測試如果沒有斷言正確的行為，一樣抓不到 bug。上面的測試矩陣才是真正的驗收標準——覆蓋率只是用來確保沒有整塊程式碼從未被執行過。

## 7. 測試資料

| 項目 | 做法 |
|---|---|
| LINE User ID | 用符合 `U[0-9a-f]{32}` 格式的假 id，**不用真實 id** |
| Client secret | 測試專用的固定值，方便重現 |
| `APP_SECRET_ENC_KEY` | 測試 profile 用固定的 32 bytes（**這把 key 只能出現在測試設定，不可與任何環境共用**） |
| 大量資料 | 用 builder 產生，不寫死 1200 筆 SQL |
| 時間 | 注入 `Clock`，測試用 `Clock.fixed()`。**不在測試中呼叫 `Instant.now()`** |

注入 `Clock` 是刻意的設計要求——時間戳驗證、退避、保留期清理全都與時間有關，沒有可控時鐘就只能靠 sleep，測試會又慢又不穩。
