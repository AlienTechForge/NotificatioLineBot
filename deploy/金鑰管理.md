# APP_SECRET_ENC_KEY —— 它是什麼、怎麼備份、有沒有別的選項

## 它是什麼

一把 **AES-256 金鑰**，用來加密資料庫裡每一組 client secret。

```
呼叫端 ──簽章──▶ API
                  │
                  ├─ 從 DB 撈出該 client 的「密文 secret」
                  ├─ 用 APP_SECRET_ENC_KEY 解密 ──▶ 明文 secret
                  ├─ 用明文 secret 重算一次簽章
                  └─ 與呼叫端送來的簽章比對
```

## 為什麼非要有它不可

一般憑證儲存的原則是「**只存雜湊，永不存明文**」。密碼是這樣，API token 也是。

**但 HMAC 讓這個原則失效。**

HMAC 驗簽的做法是伺服器**重新計算**一次簽章再比對 —— 計算需要 secret 本身。
雜湊是單向的，存了 `SHA-256(secret)` 就永遠拿不回 `secret`，**驗簽根本做不出來**。

所以 secret 必須「可還原」→ 只能加密，不能雜湊。這不是實作偷懶，是 HMAC 這個方案的
固有代價。完整分析見 [ADR-0002](../Docs/plan/adr/0002-client-secret-加密儲存而非雜湊.md)。

## 遺失會怎樣

> **所有 client secret 都解不開了。**
> 每一個呼叫端的認證都會失敗，只能全部重新發放憑證。

**但這件事的嚴重度會隨時間變化：**

| 時機 | 損失 |
|---|---|
| **現在**（還沒有真實 client） | 幾乎是零 —— 重新產生一把 key、重跑一次 bootstrap 就好 |
| 發了 3～5 組憑證 | 小 —— 通知各服務改設定，一個下午 |
| 發了幾十組、有使用者自助申請的 | 大 —— 要通知每一個人重新申請 |

所以：**現在就把備份做好，但不必為它過度工程**。

## 怎麼產生

```bash
openssl rand -base64 32
```

輸出 44 個字元（32 bytes 的 base64）。應用啟動時會驗證長度，不對就直接拒絕啟動。

## 備份選項

### 選項 A：密碼管理器 + 一份離線副本 ⭐ 建議

| | |
|---|---|
| 做法 | Bitwarden / 1Password / KeePass 存一份；另外寫在紙上或存到一支離線隨身碟 |
| 成本 | 幾乎零 |
| 適合 | 單台 server、自架、client 數量不多 —— **也就是你現在的情況** |

> ⚠️ **鐵則：不可與資料庫備份放在同一個地方。**
> 加密金鑰和密文放一起，等於沒有加密。
> 如果 DB 備份丟到 NAS，key 就別放 NAS。

### 選項 B：雲端 KMS（AWS KMS / GCP KMS / Azure Key Vault）

| | |
|---|---|
| 做法 | key 存在 KMS，`.env` 裡不放金鑰。應用啟動時或每次解密時呼叫 KMS |
| 好處 | **不會遺失**（雲端商負責保管與備份）、有存取稽核、可設權限 |
| 代價 | 多一個外部相依（KMS 掛掉 = 認證全掛）、有費用、**要改 `SecretCipher` 的程式碼** |
| 適合 | 已經在用該雲、或 client 數量多到重發成本很高 |

### 選項 C：從 passphrase 推導（不建議）

用 Argon2/PBKDF2 從一段你記得住的通關密語推導出金鑰。

**看似解決了保管問題，實際上只是換一個問題**：通關密語的強度、以及推導參數
（salt、迭代次數、演算法）也必須一併保存 —— 參數變了金鑰就變了。等於還是要備份東西，
但多了一層可能出錯的環節。

### ❌ 不要做的

| 做法 | 為什麼不行 |
|---|---|
| 和 DB 備份放同一個位置 | 等於沒加密 |
| 進版控（git） | 歷史紀錄清不乾淨 |
| 只存在 server 的 `.env`，沒有第二份 | 磁碟壞掉就全沒了 |
| 貼在聊天室 / email / 便利貼 | 這些地方會被搜尋、被備份、被截圖 |

## 有沒有辦法「完全不需要這把金鑰」

有，但都要付代價。

### 替代方案 1：改用非對稱簽章（Ed25519）

伺服器**只存公鑰** —— 公鑰外洩無害，不需要備份任何機密，遺失也不會有災難。

| | |
|---|---|
| 好處 | 徹底消滅這個問題。伺服器端沒有任何值得偷的東西 |
| 代價 | **呼叫端接入成本大幅上升**。目前用 `openssl` 三行就能簽；換成 Ed25519 後，shell 腳本要簽章變得很麻煩，每個呼叫端都要處理金鑰對的產生與保管 |
| 何時值得 | 若日後接入端都是內部 Java/Python 服務、不再需要「shell 一行接入」 |

這是 [ADR-0002](../Docs/plan/adr/0002-client-secret-加密儲存而非雜湊.md) 當初評估後
放棄的方案，理由就是接入成本。若情況改變，開新 ADR 重新評估。

### 替代方案 2：改成 Bearer token（不建議）

呼叫端直接送 `Authorization: Bearer <secret>`，伺服器雜湊後比對 —— secret 就可以
只存雜湊了。

**但會失去 HMAC 的兩個保護：**

1. secret 在**每次請求**都完整送出（TLS 有保護，但會經過反向代理、可能進日誌）
2. **沒有 body 防竄改** —— HMAC 簽的是整個請求內容，中間人改了 body 會被抓到；
   Bearer token 只證明「你有金鑰」，不保護內容

不值得為了省一把備份而放棄這兩點。

## 建議

**你現在的情況（單台 server、自架、還沒有真實 client）：**

1. 用 `openssl rand -base64 32` 產生
2. 存進密碼管理器
3. 再抄一份放在離線的地方（紙本或隨身碟）
4. **確認這兩份都不在 NAS/雲端硬碟等「DB 備份會去的地方」**
5. 就這樣。不用上 KMS

**什麼時候該重新考慮：**

- 自助申請的使用者超過十幾人（重發成本開始痛）
- 開始有其他人維運這台 server（需要存取稽核）
- 搬到雲端（KMS 就在手邊，成本低）

## 輪替（不需停機）

schema 有 `secret_key_version` 欄位，支援新舊金鑰並存：

```bash
# 1. 產生新金鑰
openssl rand -base64 32

# 2. .env 加上，舊的保留
APP_SECRET_ENC_KEY=<舊的>
APP_SECRET_ENC_KEY_V2=<新的>
APP_SECRET_ENC_KEY_VERSION=1     # 還是用 v1 加密

# 3. 重啟 —— 此時能用 v1、v2 解密
# 4. 改成 VERSION=2 再重啟 —— 新資料用 v2 加密，舊資料仍讀得到
# 5. 逐筆重加密，確認沒有 secret_key_version=1 的資料
# 6. 清空 _V2，把新金鑰移到 APP_SECRET_ENC_KEY，VERSION 改回 1
```

查還有多少舊版本的資料：

```sql
SELECT secret_key_version, count(*) FROM client GROUP BY 1;
```

## 外洩時怎麼辦

金鑰外洩 ≠ 只換金鑰就好。**舊的 client secret 已經可能被解出來了**，所以：

1. 立刻依上面的程序輪替金鑰
2. **同時**把所有 client 標記為 `REVOKED`，要求全部重新取得憑證
3. 檢查 `audit_log` 有無異常的發送紀錄

只換金鑰而不重發 secret，等於什麼都沒做。
