# 加密金鑰、憑證與備份

> 校訂日期：2026-09-21；依 `SecretCipher`、`CryptoProperties`、各 entity 與部署 workflow 核對。

## 1. APP_SECRET_ENC_KEY 保護什麼

這是 Base64 編碼的 32-byte AES-256-GCM 金鑰。HMAC 驗簽需要還原 client secret，
因此只能加密儲存，不能用不可逆雜湊取代。每次加密產生新的 12-byte IV，AAD 綁定資料身分。

| 資料 | 版本欄位 | AAD |
|---|---|---|
| client secret | `client.secret_key_version` | client 的公開 `client_id` |
| 監控 headers | `api_monitor.headers_key_version` | `monitor:{id}` |
| cookie jar | `site_session.jar_key_version` | `site_session:{host}` |
| 監控計算密鑰 | `monitor_secret.key_version` | `monitor_secret:{monitorId}:{name}` |
| 站台登入密碼 | `monitor_login.password_key_version` | `monitor_login:{id}:password` |
| refresh token | `monitor_login.refresh_key_version` | `monitor_login:{id}:refresh` |
| id token | `monitor_login.token_key_version` | `monitor_login:{id}:token` |

遺失金鑰會影響表中所有仍使用該版本的資料，不能只重建 client 就視為復原完成。
通知內容、監控 URL／request body／last_state、登入 username／config 沒有受此欄位加密保護。

## 2. 產生與保存

```bash
openssl rand -base64 32
```

把輸出存入密碼管理器與另一份獨立的離線備份，再設定 GitHub Secret `APP_SECRET_ENC_KEY`。
部署 workflow 以 `umask 077` 產生由 runner 使用者擁有的 `.env`，權限為 600。
金鑰與 DB 備份應分開授權及保存，並一併記錄版本號；不要把真值貼入文件、issue 或 commit。

應用只驗證金鑰格式、長度與目前版本存在，無法在啟動時證明每筆舊資料都解得開。
還原演練要在隔離環境使用匹配的 DB 與金鑰版本，且不得連正式 LINE 帳號發訊息。

## 3. 輪替：目前有多版本解密，沒有自動重加密工具

現有設定把 `APP_SECRET_ENC_KEY` 映射為版本 1，`APP_SECRET_ENC_KEY_V2` 映射為版本 2；
`APP_SECRET_ENC_KEY_VERSION` 指定新資料用哪一版。套用設定需重新啟動，單實例會短暫中斷。

1. 備份舊 key、版本對照與 DB；新增版本 2 的 key，保留版本 1。
2. 先部署兩把 key 並仍以版本 1 寫入，驗證既有資料可讀。
3. 將 `APP_SECRET_ENC_KEY_VERSION=2` 後部署，新寫入使用版本 2，舊資料仍用版本 1 解密。
4. 本專案**沒有**批次重加密 CLI／排程。完成專用工具、隔離驗證與可還原備份前，必須保留兩把 key。
5. 工具需遍歷上表所有欄位，用原 AAD 解密後重新加密，原子更新 ciphertext／IV／key_version；
   驗證每種資料可讀且舊版引用為零，再考慮移除舊 key。備份仍可能需要舊 key。

**不可把新版 key 搬回版本 1 並清空 V2。** 已標 `key_version=2` 的資料仍會尋找版本 2；
重新編號或覆蓋版本 1 會破壞版本對照。新版本需保持穩定編號，第三版以上需擴充設定映射。

僅列出各版本的引用數，不輸出密文或真值：

```sql
SELECT 'client' AS source, secret_key_version AS version, count(*) FROM client GROUP BY 2
UNION ALL SELECT 'monitor headers', headers_key_version, count(*) FROM api_monitor
  WHERE headers_key_version IS NOT NULL GROUP BY 2
UNION ALL SELECT 'cookie jar', jar_key_version, count(*) FROM site_session GROUP BY 2
UNION ALL SELECT 'monitor secret', key_version, count(*) FROM monitor_secret GROUP BY 2
UNION ALL SELECT 'login password', password_key_version, count(*) FROM monitor_login
  WHERE password_key_version IS NOT NULL GROUP BY 2
UNION ALL SELECT 'login refresh', refresh_key_version, count(*) FROM monitor_login
  WHERE refresh_key_version IS NOT NULL GROUP BY 2
UNION ALL SELECT 'login token', token_key_version, count(*) FROM monitor_login
  WHERE token_key_version IS NOT NULL GROUP BY 2;
```

## 4. 外洩或遺失

- key 遺失：先找可信備份；找不到時重發受影響 client，重建 headers／cookie／監控密鑰／登入設定。
- key 外洩：確認攻擊者可能取得哪些密文，撤銷及更換受影響 client secret、站台密碼／session／token，
  再依版本流程換加密 key。只換 AES key 不會撤銷已被解出的憑證。
- LINE Channel Token／Secret 與管理密碼是獨立憑證，疑似外洩時各自輪替。
- `audit_log` 尚無寫入，不能拿空表作為「無異常」證明。可對照通知、投遞、監控紀錄與受限存取的日誌。
- Git 刪除只影響新版本；歷史、Actions logs、artifacts、備份與其他 clone 需另行清理。

## 5. Client secret 的一次顯示

後台建立 client 只在該回應顯示明文。CLI 會印到終端；Admin workflow 目前把 CLI 輸出寫入 raw log，
因此「只顯示一次」不等於 log 已刪除。優先使用後台建立並直接存進密碼管理器；
既有 Actions log 是否含仍有效 secret 需由有權人員另行核對與處理。
詳見 [隱私與敏感資訊檢查](../Docs/隱私與敏感資訊檢查.md)。
